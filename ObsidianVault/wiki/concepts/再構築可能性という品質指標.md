# 再構築可能性という品質指標

## 要旨

[[Approval_Engineeringと構造化された意図]]の議論から派生した、より具体的で検証可能な仮説。元のプログラムを見ずに、構造化された意図データだけから新しいプログラムを再構築し、元と同じ振る舞いになるかどうかを**構造化された意図の完全性を測る試験**として使う、という考え方。

> 再構築可能性 = 構造化された意図の品質指標

## 基本構造

```text
Original Program
      ↓ 意図を抽出
Structured Intent
      ↓ 再生成
New Program
      ↓
Behavior Diff
```

`Behavior Diff = 0` に近づくほど、`Structured Intent ≒ System Essence` という仮説を強く支持できる、と位置づけられている。完全な数学的証明ではないが、対象とした入力空間・責務・振る舞いについて実験的に確認できる、という留保つき。

重要なのは、**同じソースコードを復元する必要はない**という点。元のProgram Aと新しいProgram Bの実装が違っていても、同じ入力に対して同じ責務・同じ制約・同じ期待結果・同じ外部振る舞いになるなら、「システムとしては再構築された」とみなす。

## 再構築の失敗こそが価値を生む

再構築したプログラムにDiffが出た場合、それは失敗ではなく**まだコードに閉じ込められている暗黙の意図を発見する装置**として扱われる。

```text
保存順序だけ違った       → 保存順序というBehavior契約が不足していた
エラー表示のタイミングが違った → UI責務または状態遷移が不足していた
特定条件だけ結果が違った   → Constraint / Decision Axis / Expectedのどこかに未構造化の意味が残っていた
```

これは品質改善ループとして次のように回せる。

```text
Structured Intent → Program再生成 → Behavior Diff
  → 差分あり → 不足している意図を特定
  → Responsibility/Behavior/Constraint/Expectedを追加 → 人間承認
  → Structured Intent更新 → 再生成 → Behavior Diff縮小
```

## レガシーマイグレーションへの接続

同じ構造をレガシーコードの逆解析に適用できる、という主張。

```text
Legacy Program
  ↓ 意図抽出
Approved Structured Intent
  ↓ 再生成
New Program
  ↓
Legacy / New / Expected Diff
```

三者比較のパターン:

```text
Legacy = New = Expected     → 移行OK
Legacy = New ≠ Expected     → 古いバグ/古い仕様をそのままコピーしている可能性
Legacy ≠ New = Expected     → 意図的改善の可能性
Legacy ≠ New ≠ Expected     → 要調査
```

ここで、レガシーの現行挙動をそのまま「正しい仕様」として扱ってはいけない、という注意が明示されている。まずは「Legacy Actual」という観測事実として残し、人間が「正しい現行仕様／過去互換のために残す／バグ／不要／判断不能」に分類して初めて「Approved Expected」になる、という手順を踏む。

レガシーマイグレーションの最終確認は、**旧コードなしで再構築できるか**という問いに集約される。これは「古いコードだけが知っていることを無くす」という[[Approval_Engineeringと構造化された意図]]でのレガシー再定義と完全に一致する。

## Source of Truthの反転

```text
従来: Code = Source of Truth
反転後: Approved Structured Intent = Source of Truth
       Generated Program = Projection / View
```

コードを資産にするのではなく、**コードを何度でも生み出せる「承認済み意図」を資産にする**、という方向。品質の中心も Code Quality → Specification Quality → Intent Quality へ上がっていく、という見立て。

## Behavior/Workflow Definitionの必要性

Field Definitionだけでは状態遷移(未保存→保存→検証→反映→画面遷移等)を表現しきれないため、`Behavior Definition` / `Workflow Definition` / `State Transition Definition` のような、振る舞いそのものを表すデータも構造化された意図に含める必要がある、という補足。

## オープンクエスチョン

- 「同じソースコードを復元する必要はない」の判定基準となる「同じ外部振る舞い」を、実際にどこまで厳密にBehavior Diffとして機械観測できるか（[[Expected_Diff方式と検証世界の設計原則]]が具体的な観測方式を提供しうる）
- FRBStudio_Appの既存責務を対象に、この「元コードを見ずに再構築する」実験を実際に行ったことはまだない（この会話時点では仮説段階）
