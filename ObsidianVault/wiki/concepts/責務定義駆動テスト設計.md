# 責務定義駆動テスト設計 (Responsibility-Driven Test Design)

## 要旨

JSON Studioで確立した「項目定義(Field Definition) → Validation Type → 標準TestPattern → Expected自動生成」という構造を、画面の「責務(Responsibility)」を対象にしたテスト設計へ継承しようとする設計思想。項目の値には単一の型(integer/string/date等)がつくのに対し、責務は複数の振る舞いが合成されているため、「Behavior Type」という一段抽象化した概念を responsibility_type の代わりに導入し、責務ごとにBehavior Typeの集合(TestPattern Family)を合成する、という発展形にたどり着いている。

## 対応関係

| JSON Studio | Responsibility-Driven Test Design |
|---|---|
| Field Definition | Responsibility Definition |
| validation_type | Behavior Type(単一ではなく複数合成) |
| minimum / maximum / required | Guarantee / Behavior Rule |
| minimum_minus_1 等のTestPattern | EMP / ONE / MULTI / NONE / SCOPE 等のTestPattern略語 |
| Definition Test Runner | Responsibility Test Runner |

## Behavior Type / TestPattern Familyの例（会話内で挙げられた仮候補）

- `FILTER`: EMPTY_QUERY / ZERO_HIT / ONE_HIT / MULTI_HIT / CLEAR_QUERY
- `SCOPED`: HIT_IN_SCOPE / HIT_OUT_OF_SCOPE / HIT_MIXED
- `SELECTION_REQUIRED`: NO_SELECTION / VALID_SELECTION / CHANGE_SELECTION
- `STATE_TRANSITION`(→ `RESTORE_TO_BASELINE` など): 下記「RESETのState Transition化」参照
- ほか候補: `LOAD` / `SELECTION` / `STATUS_FILTER` / `PROJECTION` / `EXPAND_COLLAPSE` / `ENCODING` / `SAVE_AS`

1責務 = 1 Behavior Typeとは限らない。例えば「選択ファイル内を検索」は `FILTER + SCOPED + SELECTION_REQUIRED` の合成として定義する方が実態に合う、という指摘が会話の核心。

```json
{
  "responsibility_id": "search_selected_file",
  "test_types": ["FILTER", "SCOPED", "SELECTION_REQUIRED"]
}
```

JSON Studioとの違いは、値の型(`minimum` → `minimum_minus_1`)はTestPattern単体でほぼ自動的にExpectedまで出せるのに対し、責務側はTestPattern略語だけではExpectedが決まらず、`TestPattern略語 + Fixture + Guarantee` の3点セットが必要になる、という点。

## RESETのState Transition化

「初期状態へ戻す」責務をそのままRESET専用の型にすると画面ごとの専用語になってしまうため、より上位の `STATE_TRANSITION → RESTORE_TO_BASELINE`（target = `INITIAL_STATE`）として一般化する案。画面ごとの「初期状態」の中身をRESET自身に持たせず、`state_contract` として外出しする。

```json
{
  "state_contract": {
    "reset_scope": ["selected_file", "file_search", "detail_search", "status_filter"],
    "preserve": ["loaded_document", "encoding"]
  }
}
```

標準TestPattern候補: `BASE`(既に基準状態) / `ONE`(1状態変更してRESET) / `MULTI`(複数状態変更) / `KEEP`(対象外を保持) / `REPEAT`(繰り返しても同じ) / `SCOPE`(指定範囲だけRESET)。

汎用Runnerは `① Fixtureで事前状態を作る → ② Actionを実行 → ③ Target State Contractを取得 → ④ Actual Stateを取得 → ⑤ Expectedとの差分を見る` という5ステップに一般化できる、という着地点。

## 過去サンプルとの接続 (grid_column_build)

`01b_axis_commonize_priority` にあった `grid_column_build` 責務の5つのGuarantee(g001〜g005)は、抽象化するとそのまま標準Behaviorに見える、と会話内で再評価されている:

| Guarantee | 抽象化後のBehavior |
|---|---|
| g001 非表示を除外する | `FILTER` |
| g002 順序を維持する | `ORDER_PRESERVE` |
| g003 空入力でも安全 | `EMPTY_SAFE` |
| g004 呼出側方針を適用する | `POLICY_INJECTION` |
| g005 入力を破壊しない | `NO_MUTATION` |

つまり `grid_column_build` という具体的責務そのものを標準Patternにする必要はなく、その責務が「どのBehavior Patternを合成しているか」を見る方が汎用的、という結論に至っている。

## 実践: FRB責務棚卸し Phase1/2 Pilot (2026-08)

031の会話の後、実際にFRBStudio_Appの既存責務を対象に棚卸しを行った記録が残っている。

**Phase 1**（[[AI協働033_責務棚卸しPhase1]]）: JSON Object Studio / Markdown Studio / Diff JSON / MetaDiffの4画面から20責務を「今の粒度のまま」一覧化した。ここでの明示ルールが重要:

- 先に抽象化しない（`grid_column_build`をいきなり`FILTER`等へ置き換えない）
- 粒度が変でも直さない、違和感は別途メモに残す
- Guaranteeも原文優先（共通Behaviorへ先に変換しない）
- 「機械生成できそう」はまだ判定しない

**Phase 2 Pilot**（[[AI協働034_責務Behavior_Pilot_Phase2]]）: Guaranteeが揃っている4責務・25Guaranteeを対象に、Behavior Pattern名を先に付けずに横断比較した。ここで安全弁となる重要な発見があった:

> Guaranteeの文言一致だけでは共通化できない。「除外」「維持」「変更しない」のような動詞は複数責務に現れるが、対象・条件・保証・観測結果・Expected生成方法まで一緒に見なければ、安易な共通化は危険。

実際に「候補D: 除外」は、`grid.visible=false`の除外・検索条件不一致の除外・全文検索対象外・集計対象外、という4つのGuaranteeが表面上は同じ「除外」動詞を持ちながら、対象・判定タイミング・出力契約が全く違うため、**共通化しない方がよい候補**として明示的に保留されている。一方「候補A: 入力非破壊」「候補B: 順序維持」は比較的近く、次の人間レビュー対象として絞り込まれた。

この安全弁は、Behavior Type Catalogを「まず10個前後洗い出し、他画面でも使えると分かったものだけ標準へ昇格させる」という育て方（[[Approval_Engineeringと構造化された意図]]のType階層育成と同じ構造）を、具体的にどう慎重に進めるかの実例になっている。

Phase 2 Pilotの末尾からは、GitDiffの「変化だけを正解として持つ」思想をExpectedへ応用する着想が生まれ、[[Expected_Diff方式と検証世界の設計原則]]として独立に発展した。

## オープンクエスチョン

- Diff JSON Viewer / JSON Studio / Markdown Studio / 設定画面を横断して、実際にどのBehavior Typeが「本当に共通化できる」候補として昇格するか(会話内では「まず10個前後洗い出し、他画面でも使えると分かったものだけ標準Typeへ昇格させる」という進め方が提案されている)
- GuaranteeやFixtureの具体的な中身(「何を検索対象にするか」「何件返るべきか」)を、Behavior Type承認後にどう自動/半自動生成するか
- 候補A(入力非破壊)・候補B(順序維持)の人間レビューは、Phase 2 Pilotの時点ではまだ完了していない
