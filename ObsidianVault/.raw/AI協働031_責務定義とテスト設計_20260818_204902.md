# 責務定義とテスト設計

## 001 User

画像がアップロードされました

ふんわり質問。今は細かく詰めるつもりはなし。
Diff JSON Viewer の責務定義、テストパターンを　JSON STUDIOの考え方を継承しようとしたときにどうにかなる案ある？💦

## 002 Assistant

あぁーーー、そこね（笑）
今の補足で気にしてるポイント分かった。

JSON Studioでやったのは、雑に言うとこうやったよね。

項目定義
  minimum = 0
  maximum = 100
  required = true

  ↓

テストパターン略語
  minimum
  minimum_minus_1
  maximum
  maximum_plus_1
  null

つまり、

項目が持っている契約から、どのTestPatternを実行するかを項目定義側に紐づける

という構造。

Diff JSON Viewerの「責務定義」でこれをやろうとすると、確かにそのままではイメージしにくい。
でもたぶん、一段だけ概念を足すと綺麗にハマる。

項目定義の validation_type に相当するものを、責務側にも作る

例えばこの責務。

検索語を入力してファイルを抽出する

これをただの文章として持つんじゃなくて、

JSON
{
  "responsibility_id": "diff_file_filter",
  "caption": "検索語を入力してファイル抽出",
  "responsibility_type": "collection_filter"
}

みたいにする。

この

collection_filter

が、JSON Studioにおける

integer
string
date

みたいなテストパターン生成元になるイメージ。

すると collection_filter 用の標準TestPatternを用意できる。

EMP    空条件
ONE    1件ヒット
MULTI  複数件ヒット
NONE   0件ヒット
DUP    同一対象内で複数ヒット
SCOPE  対象範囲外にヒットあり
RESET  条件解除

責務定義には、

JSON
{
  "responsibility_id": "diff_file_filter",
  "responsibility_type": "collection_filter",
  "test_patterns": [
    "EMP",
    "ONE",
    "MULTI",
    "NONE",
    "DUP",
    "RESET"
  ]
}

みたいに書ける。

これならJSON Studioでやったことと、ほぼ同じ構造になる。

しかも右側の

選択ファイル内を検索

も同じ collection_filter を使えるけど、ちょっと性質が違う。

JSON
{
  "responsibility_id": "selected_file_diff_filter",
  "responsibility_type": "scoped_collection_filter",
  "test_patterns": [
    "EMP",
    "ONE",
    "MULTI",
    "NONE",
    "SCOPE",
    "RESET"
  ]
}

ここで SCOPE が効く。

例えば、

選択ファイル A
検索語 caption

A → 2件ヒット
B → 10件ヒット

なら、

SCOPE
Expected:
Aの2件だけ表示
Bは表示されない

となる。

これ、かなり気持ちいい（笑）

要するに対応関係を作るとこうやと思う。

JSON Studio	Diff Viewer
Field Definition	Responsibility Definition
validation_type	responsibility_type
minimum / maximum / required	Guarantee / Behavior Rule
minimum_minus_1 等	EMP / ONE / MULTI / NONE / SCOPE 等
Definition Test Runner	Responsibility Test Runner

で、俺が特に大事やと思うのは、

テストパターン略語を「Diff Viewer専用語」にしすぎないこと。

例えば、

DIFF_FILE_SEARCH_EMPTY
DIFF_FILE_SEARCH_ONE
DIFF_FILE_SEARCH_MULTI

と作ったら、また画面ごとのテスト定義になる。

そうじゃなくて、

Collection Filter
  EMP
  ONE
  MULTI
  NONE
  SCOPE
  RESET

としておけば、将来、

インシデント一覧検索

Markdownファイル検索

JSON一覧検索

Diff一覧検索

全部に同じパターンを使える。

これ、Validation Type Catalog とほぼ同じ思想なんよ。

だから俺なら今の段階では、

Responsibility Type Catalog

みたいなものが将来生える、と考えるかな。

collection_filter
selection
load
reset
status_filter
detail_projection

とか。

その型ごとに、

標準TestPattern略語

を持たせる。

ただし、ここで一個だけJSON Studioとの違いがある。

数値項目なら、

minimum
↓
minimum_minus_1

はほぼ自動でExpectedまで出せる。

一方、

collection_filter
↓
MULTI

だけでは、

何を検索対象にするのか
何件返るべきなのか

までは分からない。

なので責務テスト側では、

TestPattern略語
+
Fixture
+
Guarantee

の3つがセットになると思う。

つまり、

JSON Studio

FieldDef
    ↓
TestPattern
    ↓
Expectedをほぼ自動生成

に対して、

Responsibility

ResponsibilityDef
    ↓
TestPattern略語
    ↓
Fixtureを当てる
    ↓
GuaranteeからExpected生成

になる。

たぶんここが、今イメージしづらかった正体やと思う。

責務は値そのものじゃないから、TestPatternだけではExpectedが決まらない。
でも、

責務の「型」を定義して、その型に標準TestPattern略語をぶら下げる

ところまでは、JSON Studioの思想をかなり素直に継承できる。

これ、思ったより綺麗につながると思う（笑）
しかも「項目定義駆動テスト」から、ほんまに一段上の**「責務定義駆動テスト」**に進んでる感じがする。

## 004 Assistant

そうそうそう。そこが本丸やと思う。（笑）

JSON Studioでいう、

Validation Type
= その種類の値に対して
  実施すべき標準TestPatternの集合

やもんね。

だから Diff JSON Viewer 側で考えるべき問いは、

「画面の責務には、どんな“標準的な振る舞いの型”が存在するのか？」

になる。

で、ここ考えてみると結構出せそう。

たとえば最初の候補だけでも、

仮のType	対象責務	TestPatternの例
LOAD	ファイル読込	正常／空／不正形式／対象外形式
FILTER	一覧絞り込み	0件／1件／複数件／全件
SCOPED_FILTER	選択範囲内検索	範囲内Hit／範囲外Hit／混在／0件
SELECTION	ファイル選択	未選択／1件選択／選択変更
STATUS_FILTER	Status絞り込み	各Status／該当なし／全Status
PROJECTION	詳細表示	1件／複数情報／欠損項目
RESET	初期状態へ戻す	条件あり→解除／選択あり→解除
EXPAND_COLLAPSE	Raw JSON等	閉→開／開→閉
ENCODING	UTF-8等	標準／指定変更／不正文字
SAVE_AS	別名保存があるなら	正常／キャンセル／既存名等

みたいな感じ。

ただ、ここで一個JSON Studioとは違う面白い問題が出ると思う。

1責務 = 1 Type では足りないかもしれない

たとえば右側の、

選択ファイル内を検索

は、

FILTER
+
SCOPE
+
SELECTION_REQUIRED

という3つの性質を持ってる。

なので、

JSON
{
  "responsibility_id": "search_selected_file",
  "test_types": [
    "FILTER",
    "SCOPED",
    "SELECTION_REQUIRED"
  ]
}

みたいにした方が美しい可能性がある。

これ、かなり重要。

JSON Studioの場合は、

integer
date
string

みたいに値の型が比較的ひとつに決まりやすい。

でも責務は、

検索する
かつ
選択範囲に限定する
かつ
未選択時には実行できない

という複数の振る舞いを合成している。

だから責務側では、

Validation Type相当を一個巨大な型として作るのではなく、TestPattern Familyを合成する

方が伸びる気がする。

たとえば、

FILTER
  EMPTY_QUERY
  ZERO_HIT
  ONE_HIT
  MULTI_HIT
  CLEAR_QUERY

SCOPED
  HIT_IN_SCOPE
  HIT_OUT_OF_SCOPE
  HIT_MIXED

SELECTION_REQUIRED
  NO_SELECTION
  VALID_SELECTION
  CHANGE_SELECTION

右検索の責務なら、この3集合を参照する。

つまり、

Responsibility Definition
       ↓
TestPattern Families
       ↓
必要な標準TestPattern集合を合成
       ↓
具体的TestPattern生成

になる。

これ、俺はかなり好き（笑）

そしてこの考え方まで行くと、名称もひょっとすると Responsibility Type より、

Behavior Type
または
Test Pattern Family

の方が正確かもしれん。

なぜなら欲しいのは責務の分類そのものじゃなくて、

「この責務には、どんな標準テスト群を当てるべきか」を決める分類

だから。

JSON Studioで、

Validation Type
= テストパターン集合を選ぶキー

だったのと完全に同じで、

Behavior Type
= 責務テストパターン集合を選ぶキー

になる。

ここ、かなり掘る価値あると思う。

最初にDiff Viewerを教材にして Behavior Typeを10個前後洗い出す。
そのあとMarkdown Studioや設定画面を眺めて、

「これ他画面でも使えるやん」

となったものだけ標準Typeへ昇格させる。

このやり方なら、いきなり巨大な体系を設計せず、JSON Studioでやった Validation Type Catalog育成の再演 ができる（笑）

## 006 Assistant

あぁー、RESETを「初期状態へ戻すボタンのテスト」と考えた瞬間に専用化するんよね。
汎用化するなら、もっと上に上げて、

「現在状態を、定義済みの基準状態へ遷移させる責務」

として扱うのが綺麗やと思う。

つまり RESET そのものを最上位Typeにせず、

STATE_TRANSITION
  └─ RESTORE_TO_BASELINE
        └─ target = INITIAL_STATE

くらいに考える。

「初期状態」をコードに持たない

例えば Diff Viewer の初期状態が、

JSON
{
  "selected_file": null,
  "file_search": "",
  "detail_search": "",
  "status_filter": "all",
  "detail_line_filter": "all"
}

だったとする。

一方 JSON Studioなら、

JSON
{
  "selected_row": null,
  "search_text": "",
  "detail_mode": "view",
  "dialog_open": false
}

みたいになる。

値は全然違う。

でもRESETの責務はどちらも、

Current State
    ↓
RESET
    ↓
Defined Baseline State

で同じ。

ここで大事なのは、

RESETが何を初期化するかをRESET自身に知識として持たせない

ことやと思う。

RESETは、

「この画面に定義された baseline_state に戻せ」

しか知らない。

するとテストパターンも汎用化できる。

例えば RESTORE_TO_BASELINE の標準TestPattern集合として、

略語（仮）	意味
BASE	既に基準状態からRESET
ONE	1状態だけ変更してRESET
MULTI	複数状態を変更してRESET
KEEP	RESET対象外の状態を保持
REPEAT	RESETを繰り返しても同じ
SCOPE	指定された範囲だけRESET

みたいにできる。

例えば Diff Viewerなら、

Fixture:
file_search = "caption"
selected_file = "app.js"
status_filter = "modified"

Action:
RESET

Expected:
file_search = ""
selected_file = null
status_filter = "all"

JSON Studioなら同じ MULTI で、

Fixture:
search_text = "customer"
selected_row = 5
dialog_open = true

Action:
RESET

Expected:
search_text = ""
selected_row = null
dialog_open = false

になる。

TestPatternは完全に同じ。FixtureとBaseline定義だけが違う。

これやと思う。

さらに、ここでめちゃくちゃ重要なのが 「戻さないもの」 も定義すること。

たとえば、

Diff ViewerのRESET

戻す
- 検索語
- 選択ファイル
- Status filter

戻さない
- 読み込んだDiffToJson
- UTF-8指定

かもしれない。

あるいはJSON Studioで、

戻す
- 選択行
- 検索条件
- 編集ダイアログ状態

戻さない
- 読み込んだData JSON
- ViewDef
- Workspace

かもしれない。

なのでBaseline定義は、

JSON
{
  "state_contract": {
    "reset_scope": [
      "selected_file",
      "file_search",
      "detail_search",
      "status_filter"
    ],
    "preserve": [
      "loaded_document",
      "encoding"
    ]
  }
}

みたいになってもいい。

すると KEEP パターンが自動的に生える。

RESET後

reset_scope
→ baselineと一致すること

preserve
→ RESET前と一致すること

おお、これ結構強い（笑）

で、もっと抽象化すると、RESETだけの話じゃなくなってくる。

State Transition

Current State
      ↓
    Action
      ↓
Target State
      ↓
Expected State Contract

になる。

例えば、

RESET
→ INITIAL_STATEへ

CANCEL
→ BEFORE_EDIT_STATEへ

RELOAD
→ LOADED_STATEへ

CLEAR_SEARCH
→ SEARCH_EMPTY_STATEへ

全部同じ構造。

つまり、汎用Test Runner側は、

① Fixtureで事前状態を作る
② Actionを実行する
③ Target State Contractを取得
④ Actual Stateを取得
⑤ Expectedとの差分を見る

だけになる。

これ、JSON Studioの思想にかなり近い

JSON Studioでは、

Validation Type
↓
TestPattern集合
↓
値を作る
↓
Validator実行
↓
Expected比較

だった。

状態責務なら、

State Transition Type
↓
TestPattern集合
↓
事前Stateを作る
↓
Action実行
↓
Target State Contractと比較

になる。

なのでRESETに相当するTypeを考えるというより、

「状態遷移」というValidation Type相当を作って、その一種としてRestore-to-Baselineを置く

のが一番汎用的な気がする。

これならDiff Viewerだけじゃなく、JSON Studio、Markdown Studio、設定画面まで普通に食える。

そして個人的には、ここで Initial StateそのものがExpectedになる のがかなり面白いと思う。

Initial State Definition
= RESETテストのExpected生成元

になるから。

つまりまた、期待値をテストコードに書かず、定義側から引っ張れる。
たぶん狙ってる方向はこっちやと思う（笑）

```text
g002 順序を維持する
g003 空入力でも安全
g004 呼出側方針を適用する
g005 入力を破壊しない
```

と、**複数の期待される振る舞い**がぶら下がってる。

これ、今話してる構造そのもの。

---

ただ、今日の話を踏まえると、次の進化ポイントがものすごくはっきりする。

今のJSONでは、この5個を人間またはAIがかなり具体的に書いてる。

```json
"guarantee": "当該項目をGrid列へ含めない。",
"observable_result": "...",
"expected_def_type": "RuleExpectedDef",
"test_pattern_seed": "visible=false除外パターン"
```

未来は、ここをもっと**キーワードへ圧縮できないか？**なんよね。

例えばこの5保証、抽象化すると実はこう見える。

```text
g001 → FILTER
g002 → ORDER_PRESERVE
g003 → EMPTY_SAFE
g004 → POLICY_INJECTION
g005 → NO_MUTATION
```

うわ、かなり普通の標準Behaviorに見える（笑）

つまり将来的には責務定義が、

```json
{
  "responsibility_cd": "grid_column_build",

  "behaviors": [
    {
      "type": "FILTER",
      "condition": "grid.visible != false"
    },
    {
      "type": "ORDER_PRESERVE"
    },
    {
      "type": "EMPTY_SAFE",
      "empty_result": []
    },
    {
      "type": "POLICY_INJECTION",
      "policy": "includeField"
    },
    {
      "type": "NO_MUTATION",
      "target": "fields"
    }
  ]
}
```

くらいまで圧縮できる可能性がある。

そしてプログラムが、

```text
FILTER
↓
対象あり
対象なし
全対象除外
一部除外
...
↓
Expected生成
```

とか、

```text
ORDER_PRESERVE
↓
1件
複数件
途中除外あり
...
↓
Expected = 入力相対順序と一致
```

とか、

```text
NO_MUTATION
↓
実行前Snapshot
実行
実行後比較
↓
Expected = Diff 0
```

を勝手に作る。

---

なので、今のサンプルを評価すると、

**責務の粒度はかなりいい。**

なぜなら、

> `GridColumnBuilder.build` に入力を与えれば、
> 複数の振る舞いについて独立してTestPattern＋Expectedを作れる

から。

逆に今日見えてきた「まだ手作業な部分」は、

> **Guaranteeの内容そのもの。**

今は、

```text
人間/AI
↓
Guaranteeを5個具体的に考える
↓
TestPattern Seedを書く
```

だけど、目指してるのは、

```text
人間
↓
FILTER
ORDER_PRESERVE
EMPTY_SAFE
POLICY_INJECTION
NO_MUTATION
を承認
↓
プログラム
↓
Guarantee
TestPattern
Expected
を生成
```

なんやと思う。

これ、かなりデカい違い。

そしてもう一個大事なのは、

**`grid_column_build` 自体を標準責務Patternにする必要はないかもしれない。**

これはStudio固有の「具体的責務」。

その下に、

```text
FILTER
ORDER_PRESERVE
EMPTY_SAFE
POLICY_INJECTION
NO_MUTATION
```

という**汎用Behavior Patternを合成している**と見る方が綺麗。

つまり、

```text
Responsibility
grid_column_build
       ↓
Behavior Pattern集合
       ├ FILTER
       ├ ORDER_PRESERVE
       ├ EMPTY_SAFE
       ├ POLICY_INJECTION
       └ NO_MUTATION
       ↓
TestPattern集合
       ↓
Expected
```

これやね。

昨日話してた、

> Validation Type ＝ TestPattern集合を呼び出すキー

から、さらに一段進んで、

> **Responsibility ＝ Behavior Patternの合成**
>
> **Behavior Pattern ＝ TestPattern＋Expected生成規則**

という構造が見えてきた。

なのでこの昔のサンプル、かなり惜しいところまで既に来てるわ（笑）

**今まではGuaranteeを「書く」設計だった。
これからはGuaranteeを「生成する」設計へ行けるかもしれない。**

たぶん今日の議論の進歩はここやと思う。
