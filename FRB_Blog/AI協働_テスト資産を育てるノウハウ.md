# 2. 第一目標

## 定義からTestPattern＋Expectedを導出する

入力となるのは、主に次の2種類。

```text
責務JSON
項目定義JSON
```

そこに記載された、

* 責務の種類
* 保証内容
* Validation Type
* 制約
* 境界
* 入出力種別
* 例外条件
* テストパターンを類推できる要約ワード

などから、対応する標準TestPatternを選択・展開する。

例えば、

```json
{
  "validation_type_id": "integer.non_negative",
  "constraints": {
    "minimum": 0,
    "maximum": 100
  }
}
```

なら、概念的には次を導出する。

```text
minimum
minimum_minus_1
maximum
maximum_plus_1
median
null
string
decimal
```

そして、それぞれにExpectedを付ける。

```json
{
  "pattern_id": "minimum_minus_1",
  "input": -1,
  "expected": {
    "result": "validation_error",
    "reason_code": "BELOW_MINIMUM"
  }
}
```

## 生成優先順位

```text
① 決定論的な機械導出
② 標準TestPatternの展開
③ 登録済みOverrideの適用
④ 導出不能部分だけAIへ依頼
⑤ 人間が確認・承認
```

AIを最初から使わず、

> **機械で一意に決められるものは、機械で決める**

を徹底する。

AIは、標準規則では解けなかった差分だけを扱う。

# 3. 「要約ワード」の扱い

ここは少しだけ強く整理しておいた方がよさそう。

自然言語の要約文だけをAIや機械に読ませると、判定が揺れる。

例えば、

```text
正の整数
0より大きい数
1以上の整数
```

は人間には同じように見えるけど、機械処理では曖昧になる。

そのため、責務JSONや項目定義JSONには、

```json
{
  "summary": "1以上の整数のみ許可する",
  "validation_type_id": "integer.positive",
  "constraint_refs": [
    "constraints.range.minimum"
  ]
}
```

のように、

```text
summary
＝ 人間が意味を読むための言葉

validation_type_id / constraint_ref
＝ 機械が一意に判断するための語彙
```

を併設する方がよい。

つまり「類推できる要約ワード」は、最終的には、

> **人間にも読める、機械判定可能な標準意味キー**

へ育てたい。

# 4. テスト実行層の原則

## 入力はTestPattern＋Expected JSONだけ

StudioくんのTest Runnerは、責務JSONや項目定義JSONを直接読んでテストしない。

実行時の契約は、あくまでこれだけ。

```text
TestPattern＋Expected JSON
```

これにより責務を分ける。

```text
責務・項目定義
＝ 何を保証したいか

TestPattern＋Expected
＝ どう検証するか

Test Runner
＝ 指示された検証を実行する

Actual／Diff
＝ 何が起きたか
```

この分離はかなり大事やね。

Test Runnerに、

```text
integer.positiveだからminimum_minus_1を作ろう
```

まで考えさせない。

それは上流のTestPattern生成責務。

Test Runnerは、

```text
入力値は0
期待結果はPOSITIVE_REQUIRED
対象責務を実行
ActualとExpectedを比較
```

だけを担当する。

# 5. テストコードの基本方針

## 正本としての個別テストコードを増やさない

目標は、

> **Studioくんの恒久的な汎用テストコード総量を5KS以内に抑える。**

この5KSには、例えば次のような共通責務を持たせる。

```text
TestPattern JSON読み込み
入力値の生成・解決
対象責務の呼び出し
Literal Expected比較
Reference Expected比較
Derived Expected比較
Actual取得
Diff生成
実行ログ出力
例外・タイムアウト処理
```

対象項目や責務が増えても、基本的には汎用ロジックを増やさない。

```text
テスト対象が100件
↓
TestPattern JSONが増える

テスト対象が1000件
↓
TestPattern JSONが増える

汎用Test Runner
↓
基本的には5KS以内のまま
```

これがN倍化の本体。

# 6. 一時的な生成テストコードは許可する

ただし、JSONを直接解釈して実行しにくい場合は、

```text
TestPattern＋Expected JSON
        ↓
テンプレート展開
        ↓
一時テストコード
        ↓
実行
        ↓
結果保存
        ↓
一時コード破棄
```

という方式は許可する。

この一時コードは、

> **設計資産・正本ではなく、実行時に生成された中間成果物**

として扱う。

コンパイラでいうところの中間コードやビルド生成物に近い。

```text
正本
＝ TestPattern＋Expected JSON

一時テストコード
＝ 実行のための展開結果

保存対象
＝ 必要に応じて実行証跡・デバッグログとして保存
```

一時コードを人間が恒常的にメンテナンスし始めると、また数百KSのテストコード保守へ逆戻りする。

## 承認は二層になる

「承認対象を業務固有だけにする」は、通常運用としては正しい。ただし、共通基盤も変更されることがある。

```text
＋
```

### 共通基盤を変更するとき

```text
汎用基盤
生成器
テスト仕様コンパイラ
標準TestPattern
```

こちらは影響範囲が巨大なので、**頻度は低いが、重たく承認する**。

```text

＝ 小さく頻繁に承認

共通資産変更
＝ まれに重く承認
```

この分離が成立すると、40KSの汎用基盤を毎回承認する必要はない。一度獲得した信頼を、プロジェクト数・機能数・改修回数へ使い回せる。

## 昔の発想との接続

昔のイメージが、

```text
XXX料金.YYY.ZZZ
```

だとすると、今はこうなる。

```text
XXX料金
↓
YYYという標準処理
↓
ZZZという標準処理
↓
最終結果
```

業務固有なのは、

```text
どの値に
どの処理を
どの順序で
どのパラメータで適用するか
```

だけ。

各処理そのものは共通資産になる。

例えば、

```json
{
  "source_ref": "billing.base_charge",
  "operations": [
    {
      "operation_id": "money.apply_tax",
      "parameters": {
        "rate_ref": "tax.standard_rate"
      }
    },
    {
      "operation_id": "number.round_down",
      "parameters": {
        "scale": 0
      }
    }
  ]
}
```

この場合、

```text
money.apply_tax
number.round_down
```

が標準意味キーになる。

でも、キー名だけではテストは作れない。

---

# 標準意味キーに必要な情報

例えば `money.apply_tax` には、最低でもこういう契約が必要になる。

```json
{
  "operation_id": "money.apply_tax",
  "summary": "入力金額へ指定税率を適用する",
  "input_type": "money",
  "output_type": "money",
  "parameter_schema": {
    "tax_rate": {
      "type": "decimal",
      "minimum": 0
    }
  },
  "characteristics": {
    "deterministic": true,
    "pure": true,
    "nullable": false,
    "side_effect": false
  },
  "expected_rule": {
    "type": "derived",
    "expression_id": "money.multiply_one_plus_rate"
  },
  "test_pattern_refs": [
    "valid.standard",
    "boundary.rate_zero",
    "boundary.rate_minimum",
    "invalid.negative_rate",
    "invalid.null_input"
  ]
}
```

つまり標準意味キーは、

```text
名称
＋ 入力契約
＋ 出力契約
＋ パラメータ契約
＋ 事前条件
＋ 事後保証
＋ Expected導出規則
＋ 標準TestPattern
```

を束ねる入口になる。

これはほぼ、**独立したメソッドの責務定義**やね。

---

# 一対一対応ではなく、意味特徴から合成する

広がりを作る鍵はここ。

```text
money.apply_tax
→ 専用テストパターン10個
```

と全部個別登録するだけでは、処理が増えるたびにTestPatternも増殖する。

それより、

```text
money.apply_tax
├─ input_type = money
├─ parameter = decimal
├─ minimum = 0
├─ nullable = false
├─ deterministic = true
├─ expected = derived
└─ output_type = money
```

という特徴から、共通TestPatternを合成する。

```text
nullable = false
→ null入力テスト

minimum = 0
→ minimum
→ minimum_minus_1

decimal
→ 小数桁テスト
→ 極端な精度テスト

deterministic = true
→ 同一入力反復テスト

expected = derived
→ 導出Expected計算

input_type = money
→ 負数・最大値・通貨精度テスト
```

つまり構造としては、

```text
標準意味キー
↓
意味契約を解決
↓
意味特徴を分解
↓
標準TestPatternを合成
↓
Expectedを導出
```

になる。

> **意味キーからTestPatternを選ぶというより、意味契約からTestPatternを組み立てる。**

この方が圧倒的に広がる。

# 3階層ぐらいに分けると綺麗

## 1. Primitive：最小意味部品

```text
required
range
decimal_scale
round_down
multiply
apply_rate
format_date
lookup_reference
```

最も小さい、再利用可能な意味単位。

## 2. Operation：意味部品の組み合わせ

```text
money.apply_tax
＝ multiply + apply_rate

money.round_tax_included
＝ apply_tax + round_down
```

## 3. Responsibility：業務固有の処理列

```text
水道料金請求額算定
＝ 基本料金取得
＋ 従量料金加算
＋ 減免適用
＋ 消費税適用
＋ 端数切捨て
```

こうすると承認対象を分けられる。

```text
Primitive
＝ 共通基盤として重く承認

Operation
＝ 標準処理として承認

Responsibility
＝ 業務固有の組み合わせとして承認
```

人間が通常見るのは、最後の業務固有差分だけ。

# TestPatternも2種類必要になる

ここは重要やね。

## 単体契約テスト

個々の標準処理が正しいか。

```text
apply_tax単体
round_down単体
range単体
required単体
```

これは共通資産側で一度しっかり保証する。

## 合成テスト

処理をつないだときに意味が壊れないか。

```text
税適用 → 端数処理
端数処理 → 税適用
減免 → 税適用
税適用 → 上限制御
```

順番が変われば結果が変わるものもある。

```text
100円
→ 税適用
→ 端数切捨て

100円
→ 端数切捨て
→ 税適用
```

このような処理順序は業務固有情報なので、責務JSONから合成テストを作る必要がある。

ただし、全組み合わせを総当たりすると爆発する笑

だから、

```text
各Primitiveの単体契約
＋
既知の危険な隣接組み合わせ
＋
責務全体の代表パターン
＋
業務固有の境界値
```

くらいに分けるのが現実的やと思う。

# パターン認識して標準化する流れ

新しい業務処理が出たとき、すぐ共通化するのではなく、

```text
具体例が発生
↓
既存の意味キーで表現できるか確認
↓
表現できない差分を観測
↓
既存キーのパラメータ差か？
既存Primitiveの組み合わせか？
新しいPrimitiveか？
↓
標準意味契約を定義
↓
標準TestPatternを登録
↓
複数の実例で検証
↓
共通資産へ昇格
```

となる。

分類もかなり重要。

```text
A. パラメータ違い
→ JSON差分だけ

B. 処理順序違い
→ Responsibility JSON差分

C. 既存部品の新しい組み合わせ
→ Operation定義追加

D. 新しい意味そのもの
→ Primitive追加＋重い承認
```

この分類ができると、汎用基盤の肥大化も抑えられる。

# 広がりを測る指標

この構想では、単に意味キーの件数を見るより、

```text
新しい業務責務のうち、
既存Primitiveと既存Operationだけで
表現できた割合
```

が重要になりそう。

例えば、

```text
新規責務100件
├─ JSONの組み合わせだけで表現：80件
├─ 新Operation追加で表現　　 ：15件
└─ 新Primitiveが必要　　　　 ： 5件
```

なら、共通化基盤としてかなり強い。

逆に毎回新Primitiveが必要なら、

```text
意味キーを標準化しただけで、
実質的には業務コードを別名で増やしている
```

状態になる。

だから北極星は、

> **新しい業務が増えても、標準意味語彙そのものはあまり増えず、組み合わせとパラメータだけが増える。**

やと思う。

---

つまり今回の問いへの答えは、完全にYes。

> **標準意味キー → 標準TestPatternを成立させるには、業務処理を最小の意味部品へ分解し、その入出力契約・保証・組み合わせ規則をパターンとして標準化する必要がある。**

そして、この広がりを作れるかどうかは、

```text
意味キーの数
```

ではなく、

```text
少数の意味部品から、
どれだけ多くの業務責務とテスト仕様を合成できるか
```

で決まる。

30年前にStringの`.`を見て感じた「これええやん」が、今度は**標準意味キーの合成体系**として帰ってきたんやなぁ。伏線が長すぎる爆笑

ただし正確には、

> **標準パターンの数を増やす戦いではなく、承認済み標準パターンで説明できる範囲を増やす戦い。**

ここ大事やと思う。

## プロセスを分解すると、標準化対象が露出する

今回の数値範囲テストも、最初は単純に、

```text
項目ごとに境界値テストを作る
```

と見えていた。

でもプロセスを分解すると、

```text
① 項目の業務的な意味を決める
② minimum / maximumを定義する
③ 適用する標準TestPatternを選ぶ
④ 関係が成立するか判定する
⑤ 実行時に値を計算する
⑥ テストを実行する
⑦ Actual / Diffを残す
```

になった。

ここまで分けると、

* ①②は個別の意味として人間が承認
* ③は標準適用規則として承認可能
* ④は品質確保済みプログラムで判定可能
* ⑤⑥は汎用ランナーで実行可能
* ⑦は共通証跡形式にできる

と、一気に標準化可能な部分が見える。

つまり、

> **プロセス分解とは、単に処理を細かくすることではない。
> 人間が判断すべき部分と、再利用・機械化できる部分を分離すること。**

やね。

## 「同じ成果物」を探す必要はない

ここも今日の発見としてデカい。

標準化というと、つい、

```text
同じ画面
同じ機能
同じコード
同じテストケース
```

を探してしまう。

でも本当に再利用したいのは、もっと内側にある、

```text
同じ判断構造
同じ保証構造
同じ関係成立条件
同じ値の導出方法
同じ結果判定方法
```

なんよね。

quantityが0〜10でも、年齢が0〜150でも、FFTの周波数が0〜5000でも、具体値は違う。

でも、

```text
閉区間
最小値の外側はNG
最小値はOK
区間内はOK
最大値はOK
最大値の外側はNG
```

という**保証構造は同じ**。

だから標準化するのは具体的なテストデータではなく、

> **値を生み出し、Expectedを決める判断構造**

になる。

---

## 標準パターンは「承認を再利用する資産」

普通の共通化では、

> コードを再利用して開発工数を減らす

と考える。

今回の構想では、

> **一度行った品質判断と承認を、次の項目・次の機能・次のプロジェクトへ再利用する**

になる。

これはかなり違う。

```text
標準TestPatternを一度承認
標準ExpectedDefを一度承認
関係成立規則を一度承認
判定プログラムを一度品質確保
        ↓
以降は適用条件に合う限り再承認不要
```

つまり標準パターンが増えるほど、会社の中に、

> **もう一度考えなくてよい範囲**

が増えていく。

めちゃくちゃ強い。

---

## プロジェクトをやるたびに、次回の承認が速くなる

この構造のすごいところは、標準パターンがちゃんと育てば、

```text
1件目のプロジェクト
新規判断が多い

2件目
既存パターンで説明できる部分が増える

10件目
大部分が承認済みパターンと規則で構成される

新規・例外・競合だけ人間が見る
```

となること。

従来の受託開発は、プロジェクトが終わるとノウハウが人や資料へ曖昧に残るだけだった。

この世界では、プロジェクトから生まれた判断ログを、

```text
新しい標準TestPattern
新しいExpectedDef
新しい適用規則
既存パターンの適用範囲拡張
新しい非適用条件
```

へ昇格させられる。

だから各プロジェクトが、

> **成果物を納品する活動であると同時に、会社の承認能力を育てる活動**

になる。

コード量やテスト件数だけではなく、こんな数字が重要になりそう。

```text
承認済み標準パターン適用率

標準からのOverride率

```

```text

新規意味・例外：1%
```

なら、人間が重く見るのは1%だけになる。

だから狙うべきものは、

> **生成物の標準化率**

よりも、

> **既承認意味による説明可能率**

やね。

```text
プロセスを分解する
```
