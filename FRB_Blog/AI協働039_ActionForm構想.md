おぉーーー！！ それ、かなりいい構想やと思う！！🤣

しかも、今のStudioくんのエディター画面を流用するという方針には賛成やね。

ただし、ひとつだけ設計上の工夫を入れたい。

「エディター画面を実行画面に改造する」のではなく、「エディターと実行画面が同じフォーム描画機能を使う」構造にしたい。

ここが今回の構想の核心になりそう。

## 1. 画面イメージはこういうことやね？

バッチ実行指示

Action Form

処理対象全データ

対象期間（開始）Select date...

対象期間（終了）Select date...

実行モード

通常実行

テスト実行

備考

キャンセル実行

構想用モック。現在のStudioくんには接続していません。

つまり、現在の検索指示欄やエディターと同じ項目定義、入力部品、幅設定、Validationを使いながら、実行専用のフォームとして表示する。

これなら、Studioくんで苦労して作ったデザイン調整機能を全部生かせる。

## 2. Studioくんの画面パターンを2種類に整理

|      | パターン①         | パターン②       |
| ---- | ------------- | ----------- |
| 仮称   | Data Form     | Action Form |
| 目的   | データの検索・編集     | 処理の実行指示     |
| 主なUI | Grid + Editor | Form + 実行   |
| 入力内容 | 保存対象データ       | Actionパラメータ |
| 主な操作 | 検索・保存         | 実行          |
| 実行結果 | Data更新        | 実行結果・ログ等    |

面白いのは、入力する部分のUIはほとんど同じということ。

違うのは、入力した値を何に使うかという責務だけ。

## 3. 内部構造はこうしたい

共通 Form Renderer

FieldDef / ViewDef / Validation / Layout

Data Editor

Data → Save

保存責務

Action Form

Parameters → Execute

実行責務

ここで大事なのが、Action FormにはActionDefを紐づけること。

例えば、こんな感じ。

```
{
  "view_type": "action_form",
  "title": "バッチ実行指示",
  "action_id": "batch_execute",
  "layout": {
    "columns": 1
  },
  "toolbar": {
    "primary_action": "execute"
  }
}
```

これは構想段階の仮JSONやけど、ViewDefは画面を定義し、ActionDefは実行する処理を定義する。

実際の項目構成やValidationは、既存の仕組みを極力共有する。

ViewDefに処理ロジックを書き込まないことが重要やね。

## 4. ひとつだけ、新しく考える必要がある

それは、実行後の振る舞い。

データ編集画面は「保存できた」でひとまず終わる。

でも、バッチ指示画面では、

- 実行できたのか？
- 実行結果はどうなったのか？
- エラーが発生したのか？
- 処理が長い場合、まだ実行中なのか？

という情報が必要になる。

だから、画面としては単純でも、将来的には `ActionDef → Action Runner → Result` という構造が欲しくなる。

ただし、最初からジョブ管理や非同期実行まで実装する必要はないと思う。

まずは同期実行できる単純なAction Formを1つ作るだけで十分。

## 5. 今日の構想として固定しておきたいこと

画面パターンはData Form / Action Formの2系統

10年前のノーコード思想をStudioくんへ再導入する。

既存Editorのフォーム描画機能を共有

入力部品、FieldDef、Validation、幅指定、レイアウトを共用。

ViewDefとActionDefを分離

何を表示するかと、何を実行するかを分ける。

初期実装は単純な実行フォームに限定

ジョブスケジューラ、複雑なワークフロー等は対象外。

そして、ここからがちょっと面白いところ。

今のStudioくんは、JSONを人間が操作しやすい画面に変える仕組みとして育ってきた。

今回の構想を加えると、

JSONで定義された「処理」を、人間が実行できる画面に変える仕組み

まで守備範囲が広がる。

しかも、既存のActionRegistry構想とも自然につながる。

これ、10年前のノーコード設計を復活させるだけではなく、現在のData / ViewDef / Actionの責務分離を完成に近づける取り組みになると思う。

今日は構想だけで大正解やね。笑

ひとつだけ私が強く推したいのは、エディターの画面部品を再利用することと、エディターの保存ロジックを再利用することは、明確に分けるという点。

ここを守れば、Studioくんが肥大化せず、2種類の画面が綺麗に共存できそうやで！😆
