## 01. FRB ワープ差し棒！

**通称：ぐりぐりスピナー**

緑の円マークを起点に、限られた操作エリア内でマウスを少し動かすだけで、長い差し棒の向きが大きく変わり、離れたファイルを素早く指し示す操作方式。差し棒の先端で対象ファイルをカレントにして捉える。ホイールによる先端の上下移動や、実マウスポインターの追従も組み合わせている。

## 02. FRB ぐりぐり追従スクロールハイブリッド方式

**通称：ハイブリッド方式**  
**コードネーム：Wheel Adaptive Navigation（WAN）**

マウスホイールを回したとき、**一覧をスクロールできる間は一覧そのものを動かし、スクロールできない端ではカレント行を移動**させる操作方式。対応する設定でマウスポインターの自動追従を有効にすれば、選んだ行へポインターも移動し、そのままクリックできる。

**ひと言：** 相手が来られる間は相手に来てもらい、来られなくなったらこちらが迎えに行く（笑）。

[【動画】ぐりぐり追従スクロールぅ～・・・。まぁ見ててもまったく面白くない動画です💦](https://youtu.be/SyadxvHePII)

## 03. FRB ぐりぐり追従スクロールハイブリッド方式 With 手裏剣スクロール

**通称：ハイブリッド方式**  
**コードネーム：Wheel Adaptive Navigation（WAN）**  
**位置づけ：02の拡張版**

02のハイブリッド方式に、手裏剣スクロールの**慣性滑走**を組み合わせた方式。ホイールを素早く連続回転させると、専用の手裏剣スクロールボタンを押さずに自動滑走を開始する。滑走中は同方向の入力で加速し、逆方向の入力で減速する。

**ひと言：** 普通にぐりぐり、勢いよくぐりぐりすると「走れぇーーー！」（※音声認識ではありません）。

[【動画】妖艶に踊るさまをご覧ください！！手裏剣スクロール！！Go！！](https://youtu.be/hiOgvz-5Lg0)

## 04. FRB ぐりぐりクリックRunner

ファイルなどの右クリックメニューを開いたあと、**マウスを移動せずにホイールでメニュー項目を選び、そのままクリックして実行**する操作方式。対応するコンテキストメニューやサブメニューで、ポインターを選択先まで運ぶ手間を減らす。

**ひと言：** 右クリックした場所から、動かずに仕事を片付ける。

## 05. FRB ぐりぐりボタンセレクター

複数の選択可能なボタンに対し、**マウスホイールの回転で選択対象を切り替え、ポインターを手動移動することなく、クリックで選択したボタンを実行**できる操作方式。OK／Cancelの確認応答から生まれたが、ダイアログに限定しない。

**ひと言：** ボタンを探してマウスを運ぶくらいなら、ぐりぐりで選ぼう！

## 1. まずは検索の基本 — 空白、OR、項目指定

普通のキーワード検索はもちろんできます。ただし、空白や `or` を入れると意味が変わります。

| 検索式 | 意味 |
| --- | --- |
| `ルアー 振動` | **AND**：両方を含む |
| `ルアー or 振動` | **OR**：どちらかを含む。`OR` も可 |
| `タイトル=Studio` | **項目指定**：タイトルに `Studio` を含む |
| `タイトル==Studio` | **完全一致**：タイトルが `Studio` と一致 |
| `種別!=bug` | **不一致**：種別が `bug` 以外 |
| `"重要 案件"` | 空白を含む言葉を、ひとつの検索語として扱う |

例えば `ルアー 振動` は、両方を含むデータを探します。

一方、`ルアー or 振動` は、どちらかが含まれていれば対象です。

そして、Studioくんらしいのが **`タイトル=Studio`**。

単に「Studioという言葉がどこかにあるか」を調べるのではなく、「タイトルという項目で探してくれ」と指定できます。

なお、項目を指定しないキーワード検索は、JSON行に含まれる文字列を横断的に探す方式です。子オブジェクトや子配列内の文字列も対象になります。

**ひと言：** 何を探すかだけでなく、どこを探すかまで、わがままを聞いてくれます（笑）。

## 2. 比較演算子 — `=` ひとつで終わらない

ここから少しSQLのWHERE句みたいな雰囲気になってきます。

| 入力① | 入力② | 意味 |
| --- | --- | --- |
| `A=2` | — | 標準検索。数値・選択肢は一致、文字列は部分一致 |
| `A==2` | — | 完全一致 |
| `A!=2` | `A=!2` | 不一致 |
| `A>=2` | `A=>2` | 2以上 |
| `A<=2` | `A=<2` | 2以下 |
| `A>2` | — | 2より大きい |
| `A<2` | — | 2より小さい |
| `A=2..5` | — | 2以上5以下（両端を含む） |
| `A=2..` | `A=..5` | 開始値だけ、または終了値だけを指定 |

`A` は説明用の項目名です。実際には `件数=2..5` のように入力します。

例えば、

- `件数>=2`：件数が2以上
- `件数=2..5`：件数が2〜5
- `件数=..5`：件数が5以下

という具合です。

**ポイントは、`=` の意味が項目の型によって変わること。** 文字列は部分一致、数値や選択肢は一致を基本としています。

また、`>=` と `=>`、`<=` と `=<` のように、書く順序が異なる表記も受け付けます。

※大小比較・範囲指定は数値や日付・日時などの対応項目で利用します。存在しない項目や、対応していない型の演算子はエラーになります。また、不一致検索でも、項目が存在しない・空のレコードを「不一致」として拾うわけではありません。

**ひと言：** 演算子の書く順番にまで寛容。わがままなのは人間のほうでした（笑）。

## 3. 日付・日時検索 — 入力の長さが、そのまま検索期間になる

個人的に紹介しておきたいのが、日付・日時の検索です。

日付の検索に、毎回「開始日」「終了日」を入力するのはちょっと面倒。

Studioくんでは、**入力した日付の細かさに合わせて、検索期間を解釈**します。

| 検索式 | 検索対象 |
| --- | --- |
| `日付=2026` | 2026年度、または2026年（設定による） |
| `日付=202610` | 2026年10月の全日 |
| `日付=20261023` | 2026年10月23日 |
| `日時=20261023_15` | 10月23日の15時台 |
| `日時=20261023_1530` | 同日15時30分台 |
| `日時=20261023_153045` | 同日15時30分45秒台 |
| `日時=202610..202611` | 2026年10月1日〜11月30日の全時刻 |
| `日時=20261023_09..20261023_17` | 9時台〜17時台（18時より前） |

例えば、

```text
日時=20261023_15
```

と書けば、15:00:00から15:59:59までの時間帯が対象です。

```text
日時=20261023_09..20261023_17
```

なら、9時台から17時台まで。**終了側の「17時台」も含む** のがポイントです。

年だけ指定した場合は、暦年か年度かを設定で選べます。現在の同梱設定は **4月始まりの年度モード** なので、`日付=2026` は2026年4月1日〜2027年3月31日の期間に相当します。

設定箇所は `app_settings.json` の `smart_search.date_search`。

`YYYY-MM-DD`、`YYYY/MM/DD` といった従来の日付表記も使えます。ただし、検索欄の `/` キーには入力補完を開く役割があるので、スラッシュ入りの日付は貼り付けで入力します。

**ひと言：** 「202610」で10月全部。もう開始日と終了日を手で打ちたくありません（笑）。

## 4. AND・OR・括弧 — ここからが超わがまま

単純なAND・ORだけではありません。**括弧を使って、条件を好きな単位にまとめられます。**

| 検索式 | 意味 |
| --- | --- |
| `aaa or bbb` | `aaa` または `bbb` |
| `(aaa or bbb) ccc` | `(aaa or bbb)` と `ccc` のAND |
| `((aaa or bbb) or (ccc or ddd))` | ORグループ同士のOR |
| `(aaa or bbb) (ccc or ddd)` | ORグループ同士のAND |
| `((aaa or bbb) ccc) or (ddd eee)` | AND・ORを括弧で組み合わせる |

演算の優先順位は、

**括弧 → AND → OR**

です。括弧は入れ子にできます。

例えば、項目が定義されているデータなら、こんな検索もできます。

```text
(タイトル=Studio or タイトル=Launch) 種別!=bug
```

「タイトルにStudioまたはLaunchを含み、種別はbug以外」という意味です。

さらに数値や日付も組み合わせられます。

```text
(タイトル=Studio or タイトル=Launch) 件数=2..5
```

これは、**論理条件と範囲条件を、検索欄の1行で組み合わせる** 例です。

**ひと言：** SQLを書いているようで、SQLを書いていない。検索したいだけなんですけどねぇ〜！（笑）

## 5. 項目名の入力補完 — 全部覚えなくていい

「でも、JSONの項目名なんて覚えられません！」

……その通りです。私も覚えられません。（爆笑）

そこで、検索欄から項目候補を呼び出せます。

■検索対象**項目**の選択画面

■検索対象**値**の選択画面
![image.png](https://qiita-image-store.s3.ap-northeast-1.amazonaws.com/0/3069714/549e82e0-02e6-4af0-9cc3-aae6697ee766.png)


| 操作 | 動作 |
| --- | --- |
| `/` または検索欄を右クリック | 項目候補を表示（`/` は入力文字に残らない） |
| `↑` / `↓` | 候補を移動 |
| `Tab` / `Enter` / `→` | 候補を確定。選択肢がある項目では値候補へ進む |
| `Esc` | 候補を閉じる |

項目名は、**画面上の表示名でも、項目IDでも指定できます**。

空白が入る項目名も大丈夫です。

```text
"Flux A">=0.1
```

このように引用符で囲めば、「Flux A」という項目名として扱えます。

選択肢のある項目では、項目を決定したあとに値候補へ進めます。候補を見ながら検索式を作れるので、すべての項目名や選択値を暗記する必要はありません。

**ひと言：** 項目名を忘れても検索できる。開発者本人に一番必要な機能かもしれません（笑）。

## 6. そもそも、この検索は何が「超」なのか

FRB Launchの **「わがままサーチ」** は、AND・OR・括弧を組み合わせる検索。

FRB Studioの **「超わがままサーチ」** は、さらにJSONの項目定義に基づく検索条件まで扱えます。

| できること | FRB Launch | FRB Studio |
| --- | :---: | :---: |
| キーワード検索 | ○ | ○ |
| AND・OR・括弧 | ○ | ○ |
| 項目を指定して検索 | — | ○ |
| 完全一致・不一致 | — | ○ |
| 数値・日付の範囲指定 | — | ○ |
| 日付・日時の省略入力 | — | ○ |
| 項目名・選択値の入力補完 | — | ○ |

※この表は、今回命名した検索式機能の比較です。両アプリ全体の機能比較ではありません。

どちらも、目指すことは同じです。

**人間が探したいと思った条件を、できるだけそのまま入力できるようにする。**

それだけの話です。

でも、それを一つずつ実装していたら、いつの間にか「超」が必要になってしまいました。💦

## 1. FRB Launchは、思考拡張実験として始まったわけではない

始まりは、実にしょうもない不満でした。

**「昨日の日付を、毎回手で入力したくない！」**

会社のCopilotくんに、文字列を選んで入力する小さなランチャーを作ってもらいました。当初はキーボード主体。左右の矢印キーでメニューが出たり引っ込んだりする。

**なんか、脳が喜んでいる！（笑）**

ここが転機でした。

私は以前から、釣り竿の振動を測定するFRB（Fishing Rod Benchmark）という個人研究を通じて、「自分の思考を拡張する条件は、意図的に作れないか？」と考えていました。

だから、この妙な高揚感を感じたとき、思ったんです。

**「今だっ！ ここから意図的に発想を広げてみよう！」**

つまり、最初から「思考拡張を説明するためにランチャーを作ろう」と計画していたのではありません。

小さな不満からランチャーが生まれ、操作中の高揚感を捕まえたところで、**意図的な思考拡張の実践へ切り替えた**のです。

## 2. 仮説：思考拡張は「現象」なら、条件を設計できるのでは？

以前、ChatGPTくんとの対話で整理した考え方があります。

**「思考拡張は現象である」**

現象であるなら、どんな条件のときに起こりやすいのか、考えて試すことができるはずです。

もちろん、条件さえ整えれば必ず同じアイデアが生まれる、という意味ではありません。

**設計できるのは、発想が生まれるための条件。何を思いつくかまでは設計できない。**

そこで今回は、自分なりの条件を設計し、AIとの試作・体験を繰り返してみました。

その結果として形になったものが、FRB Launchの独自UI機能14選です。

## 3. FRB式・思考拡張の4つの技術（Draft）

今回、私が意識したことを4つに整理しました。

| 技術 | 意図してやること |
| --- | --- |
| **① 違和感サーチ** | 不満、課題、感動、成功体験、過去のアイデアなど、発想の材料を逃さない --- **日々常時発動** |
| **② 高揚感キャッチ** | 「脳が喜んだ！ 今だっ！」という探索の加速タイミングを捕まえる |
| **③ 制約と目的関数の意図的設計** | あえて自分に「不自由」を与え、普段なら考えない問題を深く考える |
| **④ 高い要求** | 自分の知識・技術力を発想の天井にせず、未知の領域にも要求を出す |

これは4工程を順番に一回ずつ実行する手順書ではありません。行ったり来たりしながら、何度も使う技術です。

### ① 違和感サーチ：アイデアの材料を逃さない

少なくとも私は、何もないところから突然新しいアイデアを生み出せません（笑）。

「面倒くさい」「なんか変だ」「これ面白い！」「前にも似たことを考えたぞ？」

そんな小さな反応が、次のアイデアの材料になります。30年前の違和感だって、使えるなら捨てません。

ここで大事なのは、**その時点で役に立つか分からない材料も、すぐに捨てないこと**。

### ② 高揚感キャッチ：「今だっ！」を逃さない

FRB研究では、2025年11月、釣り竿で床を擦ったときの鳥肌が立つような体感が強烈なきっかけでした。

FRB Launchでは、左右の矢印キーでメニューを操作したときの、妙にうれしい感覚です。

一方、AI承認駆動開発の背景にあるのは、約30年前の「テストコード入庫拒否」から続く、なかなか回収できなかった違和感（笑）。瞬間的な喜びだけでなく、**長く残った違和感が探索のエネルギーになる**場合もあります。

共通するのは、発想の材料に強く反応したとき、それを「気のせい」で終わらせず、探索を加速させること。

ここで次の③を**意識して設定しにいく**のが、私なりの工夫です。

### ③ 制約と目的関数の意図的設計：自分を不自由にする

FRB Launchは最初からマウス専用だったわけではありません。キーボード主体のランチャーを育てる途中で、マウス主体の操作へ関心が移っていきました。

その段階で、あえて自分に不自由な条件を与えました。

- **制約：左手は操作に参加させない。**
- **制約：マウスを動かせる範囲を極力狭くする。**
- **目的関数：必要なマウス移動の「範囲」を最小化する。**

ここで最小化したいのは、単純な移動距離の合計というより、**マウスを動かす必要がある領域の広さ**です。

「遠くのファイルを選びたい？ だったら、マウスをそこまで動かせばいいやん」

……それは禁止！（笑）

「キーボードのショートカットを使えば？」

……今回は左手参加不可！（笑）

**この不自由な条件の中で、じゃあ、どんな手段がある？**

考えてよい解決方法をあえて狭めると、普段なら選ばない操作方法を真剣に考え始めます。

ただし、誤解してほしくないことがあります。

**ここでの制約は、発想を閉じ込める法律ではありません。思考を深掘りするための道具です。**

途中で制約の外へ面白いアイデアが枝分かれしてもいい。必要なら制約自体を設計し直してもいい。実装時に守るべき安全・品質上の制約とは、役割が違います。

### ④ 高い要求：自分の技術力を発想の天井にしない

③で自分を不自由にすると、当然、要求は難しくなります。

「マウスをちょっとしか動かさず、画面の遠くを選べないか？」

「ぐりぐりだけで操作できないか？」

「フリックで日本語入力できないか？」

ここで「自分には実装できないから、やめよう」とは考えない。

**自分の技術力を、発想の天井にはしない。**

自分の知らない世界を見たいなら、自分がすでに実現方法を知っていることだけを探していても、なかなかその世界には行けません。

実現したい体験を先に考え、難しい実装はAIと一緒に試す。自分が実装できるかどうかと、アイデアを思いついてよいかどうかは別問題です。

そして④の中でも、**過去のアイデアから紐づけて連想する → 試作する → 体験する → また連想する**を繰り返します。

## 4. 種明かし：一つのフリックから、どうして手裏剣や差し棒が生まれた？

ここからが今回の主役、具体例です。

※以下は**発想のつながりを分かりやすくするための整理**です。実際の開発順序は、もっと複雑に前後・分岐・合流しています。

### 起点：「第1列と第2列の移動を簡単にしたい」

FRB Launchの一覧を操作するとき、右の列へ、また左の列へ……とマウスを往復させたくない。

すると、以前から知っているスマートフォンの操作と紐づいた。

**「これ、日本語のかなフリック入力にも使えるんちゃう？」**

そこで、AIと試作してみました。

## 5. 実験の核心：試作すると、次の「材料」が生まれる

今回のFRB Launchで意図して繰り返したのは、次の循環です。

1. **人間がアイデアを思いつく。**
2. **AIと小さく試作する。**
3. **実際に見て、触って、結果を体験する。**
4. **予想外の見た目・操作感・成功・失敗・違和感を拾う。**
5. **過去のアイデア（上記 項番.4の結果含む）と紐づけて、新しいアイデアを考える。**
6. **また試作する。**

重要なのは、**この循環が偶然起きるのを待っていたわけではなく、次の発想材料を手に入れるために意図して回していた**ということです。

アイデアを試作すると、必ず何らかの結果が生まれます。

その結果が、そのまま新しいアイデアになるとは限りません。でも、今まで存在しなかった**新しい観察対象**にはなる。

「かな選択プレビューがメニューに見えた」のは、かなフリックを作って動かしたからこそ得られた材料でした。

つまり、試作は単なる**答え合わせ**ではありません。

**次のアイデアを思いつくための材料を、意図的に増やす行為**でもあるんです。

過去のアイデアから紐づけて連想し、その結果をまた試す。点と点がつながり、さらに枝分かれする。

私は、これを **「目的に向かう道路を太くしていく」** 感覚で捉えています。

AIが目的地を決めてくれるのではない。人間が行きたい方向を決め、AIとの試作によって、そこへ向かう道や選択肢を増やしていく。

## 6. このやり方の原点は、ランチャーではなくFRB研究

振り返ると、似た姿勢で取り組んできたテーマがほかにもあります。

## 7. この設計パターンを、皆さんにも紹介したかった

釣り竿の振動は、体験したことのない人には伝わりにくい。

AI承認駆動開発の話は、従来の開発プロセスや品質保証を経験した人でないと、背景が分かりにくい。

でもUIなら、実際に動くものを見れば、少なくとも **「この操作が、あの操作の発想につながった」** という過程を追いやすい。

だから今回、FRB Launchでは思いついたことを次々に試し、発想のつながりを、目に見えるUIとして残すことにも力を入れました。

**「自分で新しいアイデアを思いつくために、意図してできることがあるかもしれない」**。

## 技術の種明かし：60pxの円形リモコンは、どう作ったのか？

ここからは、ちょっとだけ真面目に。実装は**Python + PySide6（Qt）**。ただし、Windows全体の入力を横取りする新しいデバイスドライバーを作ったわけではない。操作対象は、FRB Launch自身が持つFiles Exp／Files Listだ。

### 1. 入力装置と操作対象を分離する

もともとのFRB Remoteには、ホイール・クリックなどを受け付ける`WheelPad`があった。今回の実装では、この部品を土台に、`RoundRailWheelPad(WheelPad)`という円形の操作部を作った。

実装の役割分担は、ざっくりこうなる。

```text
マウス（60pxの丸ボタン上）
  ├─ 左半分 → Files Expを操作対象にする
  └─ 右半分 → Files Listを操作対象にする
             ↓
       WheelPadの意味コマンド
       UP / DOWN / CLICK / DOUBLE_CLICK / CONTEXT_MENU ...
             ↓
       FRB Launchの既存操作処理
             ↓
       選択移動・フォルダー開閉・ファイル実行・メニュー表示
```

つまり、**入力の受付・操作対象の決定・実際の処理**を分けている。画面の別々の場所に同じ操作を作り直すのではなく、既存の処理へ橋を架けた。

### 2. 左右判定は、驚くほど単純

操作対象の判定は、実際に次のような小さな関数で行っている。

```python
# src/rail_wheel_model.py（抜粋）
def rail_target_from_x(x, width):
    return 'files_exp' if x < width / 2 else 'directory'
```

丸ボタンの**ローカル座標**で、中心より左なら`files_exp`、右なら`directory`（Files Listの内部名）。左右に移ったら、親画面へ操作対象の変更を通知する。

大事なのは、**「クリックしてから切り替え」ではない**こと。ポインターの位置だけで、次のホイールやクリックがどちらの列に届くかが決まる。左右に移るときには、ホイールの端数もリセットして、片側で回した途中の入力が反対側に持ち越されないようにした。

### 3. 丸ボタンは「浮遊する別Window」ではなく、Launchの子Widget

円形ボタンはFiles画面の子Widgetとして配置した。Files ExpとFiles Listを分ける`QSplitter`のハンドル位置を基準にして、表示位置を更新する。

```python
# 配置の考え方を示す抜粋（細部は省略）
handle = self.files_splitter.handle(1)
center = handle.mapTo(
    self, QPoint(handle.width() // 2, handle.height() // 2)
)
pad.move(center.x() - pad.width() // 2 - 6,
         center.y() - pad.height() // 2)
```

この構成なら、Launchのウィンドウを移動させたときは親子関係で追従でき、Expの幅をドラッグで変更したときも`splitterMoved`をきっかけに位置を調整できる。**リモコンを画面の一部にする**という要求を、座標の小細工より素直に実現できた。

### 4. マウス自動移動は「次に操作すべき場所」へ。ただし円の外へ飛ばさない

試作初期には、メニューから「List列へ進む」を選ぶと**Listのカレント行までポインターが飛んでいた**。

……いやいや！　それでは、わざわざ小さなリモコンに集めた意味がない！（笑）

そこで現在は、**単独リモコン表示中＋マウス自動移動ON**の場合に限り、移動先を円の中へ限定した。

```python
# 移動先を決める考え方（要点のみ）
x = pad.width() // 4 if target == 'files_exp' else pad.width() * 3 // 4
destination = pad.mapToGlobal(QPoint(x, pad.height() // 2))
QCursor.setPos(destination)
```

リモコン非表示や従来のリモコンウィンドウを使う場合は、従来どおりカレント行への自動移動方式を残している。自動移動OFFなら、ポインターを勝手に動かさない。

なお、**丸ボタンのExp側ダブルクリックでListへ進む**動作は、自動移動ON時だけにしている。OFFなのに列だけ変えると、ポインターがExp側に残り、次の操作でExpに戻ってしまうからだ。

### 5. いちばん苦労したのは、左右判定よりイベントの順番だった（笑）

ここはQiita読者にも共有したい。実装が一発でうまくいかなかった原因は、単なる座標判定の難しさではなかった。

| 実機で起きたこと | 対応した考え方 |
| --- | --- |
| 丸ボタンの中身が表示されない | `QPointF`のインポート漏れを修正し、`QPainter`は`finally`で終了 |
| 右クリックメニューが2個開く | マウスのリリースイベントとQtの`contextMenuEvent`で二重起動しないよう入口を一本化 |
| メニューを閉じても残る | 開いているメニューを正しく保持・終了させる |
| ダブルクリックで列切替直後に元へ戻る | 2回目のリリースで古い操作対象を再通知しない |
| ポインター自動移動がドラッグ扱いと競合する | 2回目のマウスボタンを離した後のタイミングで移動 |
| 列を切り替えたのに遠くへワープする | 丸ボタン表示モードだけ、移動先を円の半分に限定 |

たとえば、Qtではダブルクリックが**押す→離す→押す→離す**という複数のイベントを伴う。途中でポインターを動かしてしまうと、ボタンの押下状態や最後のリリースイベントと競合する。

そのため実装では、**「操作対象の変更」と「ポインターの物理移動」を、タイミングまで含めて分けた**。ただ処理を書くのではなく、イベントのライフサイクルを扱うことが必要だった。

もう一つ、丸ボタンは中央の「🔘」やExp/Listラベル、現在の操作対象を示す半透明の●を重ね描きしている。**表示するものと、入力を受けるものを分ける**ため、中央の絵文字ラベルにはマウスイベントを透過させている。

### 6. 設定は既存機能と共存させる

今回の単独リモコンは強制表示ではない。設定の「リモコン表示」は、次の4択になった。

| 設定 | 内容 |
| --- | --- |
| 使用しない | 初期値。リモコンを表示しない |
| リモコンウィンドウ 1.5列へ表示 | 従来の埋め込み表示 |
| リモコンウィンドウ 別Window | 従来の独立リモコン |
| **ぐりぐりボタンのみ** | **今回の60px円形ボタン** |

丸ボタンが必要ない人はOFFにできるし、従来の操作を好む人はそのまま使える。新UIを追加するときほど、**既存ユーザーの操作習慣を壊さない**ことも大切だと思っている。

### 7. この方式の限界と、これから検証したいこと

まだ、一般的なマウス操作より速い・疲れにくいと測定で証明したわけではない。現時点で分かっているのは、**FRB Launch内で操作を集約する一つの方法が実装できた**ことまでだ。

今後は、操作完了までのマウス移動距離、ポインターの往復回数、操作時間、誤操作率あたりを比べてみたい。60pxという数字は**ボタンの直径**であり、すべての作業でマウス移動距離が60px以内になるという保証ではない。

また、自動ポインター移動は環境や好みによって相性がある。自動移動をOFFにできること、標準的なキーボード操作も残すことは、実験を続けるうえでも重要だ。

## 会見を少しだけ真面目に振り返る

今回の発想の転換は、**マウスの移動をゼロにすることを諦めた**ところにあった。

本当に減らしたかったのは、異なる操作対象へ向けて、何度もポインターを長距離移動させる負担である。

操作対象がExpなのかListなのか。それを小さな範囲のポインター位置で示し、ぐりぐり・クリック・ダブルクリック・右クリックという既存の操作をそのまま使う。

**操作対象は広く、操作する場所は狭く。**

だから、特別な「仮想横回転」を作り込むのではなく、すでに存在したリモコンの操作部を、Filesの境界へ埋め込むという答えにたどり着いた。

そしてもう一つ。今回の開発では、AIが「できました」と返してきた実装が、実機では失敗した。描画エラーも、メニューの二重表示も起きた。何度も修正した。

それでも、失敗は無駄ではなかった。

**完成した答えよりも、答えからこぼれ落ちた違和感を大切にする。**

失敗した実験を触りながら、自分が本当に欲しかった操作体験を発見できた。これこそ、私がAI協働で続けている「思考拡張」の面白さなのかもしれない。
