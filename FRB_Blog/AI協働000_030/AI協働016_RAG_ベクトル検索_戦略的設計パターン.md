# 出発点：RAGは最初、単純に見える

RAGをものすごく簡単にすると、

```text
質問
↓
関連文書を検索
↓
検索結果をLLMに渡す
↓
回答を生成
```

だけに見える。

だから最初は、全部まとめて書きがち。

```text
質問を受け取る
検索する
プロンプトを作る
LLMを呼ぶ
回答を整形する
```

でも実際に精度改善を始めると、記事の筆者は次の問題に遭遇した。

* 思った情報が検索されない
* プロンプトを直すと別ケースが壊れる
* 検索アルゴリズムを変えると全体を書き換えることになる

ここで、「RAGという一枚岩」では扱えなくなった。([note（ノート）][1])

# 第1の橋：失敗原因を分離したくなった

RAGの回答が悪かったとき、原因は複数ある。

```text
元データが悪い
チャンク分割が悪い
検索が悪い
検索結果の順位が悪い
プロンプトが悪い
LLMの回答生成が悪い
```

全部を一つの処理に入れていると、

> 回答が悪かったけど、誰の責任か分からん！

となる。

そこで筆者は、

```text
Loader / Splitter
＝データを読み、検索用に分割する

Retriever
＝必要な文書を探す

Generator
＝渡された文書から回答を作る
```

と責務を分け始めた。記事では特に、「探す責務」と「答える責務」を混ぜるなと整理している。([note（ノート）][1])

これが、オブジェクト指向へ向かう最初の橋。

ただ、正確にはこの段階はまだ、

> **関心の分離**
> **責務分離**
> **単一責任原則**

の話やね。

必ずしもオブジェクト指向だけの専売特許ではない。

---

# 第2の橋：内部実装を隠したくなった

Retrieverがベクトル検索をしているのか、キーワード検索をしているのか、後段のLLMは知る必要がない。

後段が欲しいのは、ただこれ。

```text
質問を渡す
↓
関連文書の一覧が返る
```

だから、たとえば、

```text
retriever.search(query)
```

という入口だけを公開する。

その中で、

```text
ベクトルDBを検索
スコアを計算
メタデータで絞り込み
上位10件を返す
```

をやっていても、外側には見せない。

記事はここを**カプセル化**として説明している。([note（ノート）][1])

イメージはこう。

```text
LLM
 │
 │ search(query)
 ▼
Retriever
 ├─ ベクトルDB
 ├─ キーワード検索
 ├─ スコア計算
 └─ 絞り込み
```

LLMはRetrieverの中身を知らない。

> **何をしているかは知る。
> どう実現しているかは知らない。**

これがオブジェクト指向っぽくなる二つ目の橋やね。

# 第3の橋：検索方式を交換したくなった

そしてここが本丸。

RAGは、検索方法によって回答品質がかなり変わる。

筆者は記事内で、

```text
Vector Search
↓
Hybrid Search
↓
Reranker追加
```

のように、検索方式を何度も変更したくなったと書いている。([note（ノート）][1])

でもコードがこうなっていると困る。

```javascript
if (searchType === "vector") {
  // ベクトル検索
} else if (searchType === "hybrid") {
  // ハイブリッド検索
} else if (searchType === "rerank") {
  // 再順位付け検索
}
```

新しい検索方式を追加するたび、RAG本体を書き換えることになる。

そこで、

```text
Retriever
    search(query)
```

という共通契約を作り、

```text
VectorRetriever
HybridRetriever
RerankRetriever
```

を差し替えられるようにする。

```javascript
retriever = new VectorRetriever();
// または
retriever = new HybridRetriever();
// または
retriever = new RerankRetriever();

documents = retriever.search(query);
```

後段は、どれが使われていても同じ。

LangChainのRetrieverも、クエリを受け取り文書のリストを返す共通インターフェースとして扱われ、Retrieval ChainはRetriever相当の部品と文書回答生成部品を組み合わせる構造になっている。([LangChain API][2])

# これはほぼ、そのままStrategyパターン

あなたが感じたとおり。

Strategyパターンとは、

> 同じ目的を達成する複数のアルゴリズムを、共通インターフェースの後ろに置き、交換可能にする

設計パターン。([リファクタリング Guru][3])

RAGへ対応させるとこう。

| Strategyパターン        | RAG             |
| ------------------- | --------------- |
| Context             | RAGパイプライン       |
| Strategy interface  | Retriever       |
| Concrete Strategy A | VectorRetriever |
| Concrete Strategy B | HybridRetriever |
| Concrete Strategy C | RerankRetriever |
| 共通メソッド              | `search(query)` |
| 戻り値                 | 関連文書一覧          |

つまり、

```text
RAGパイプライン
    │
    └─ Retriever戦略を利用
          ├─ Vector戦略
          ├─ Hybrid戦略
          └─ Rerank戦略
```

やね。

記事ではこれを主に「ポリモーフィズム」と呼んでいるけど、**利用目的まで含めてパターン名をつけるならStrategyパターン**が一番近い。

---

# ポリモーフィズムとStrategyパターンの違い

ここ、ちょっと分かりにくい。

## ポリモーフィズム

```text
同じ呼び出し方で、
異なる実装を動かせる性質
```

```javascript
retriever.search(query);
```

と呼ぶだけで、

```text
VectorRetriever.search()
HybridRetriever.search()
RerankRetriever.search()
```

のどれかが動く。

これは**仕組み・性質**。

## Strategyパターン

```text
変わりやすいアルゴリズムを、
交換可能な部品として分離する設計
```

これは**その仕組みを何のために使うかという設計パターン**。

だから、

> Strategyパターンは、ポリモーフィズムを利用して実現されることが多い。

という関係。

記事の、

```text
検索部分を共通のガワにして、
Vector / Hybrid / Rerankを入れ替える
```

は、

* 技術的な仕組み：ポリモーフィズム
* 設計パターンとしての意味：Strategy

ということになる。

# では、なぜ最初は「データ整理」の話だったのか

筆者の最初の発見は、

> データの置き場所と、データを解釈する処理を分けたらいいのでは？

だった。([note（ノート）][1])

たとえば、

```text
原本データ
AIが加工したデータ
人間が主観で補足したデータ
```

を一緒にすると、何が事実で何が解釈か分からなくなる。

そこで、

```text
Knowledge
＝事実・原本

Retriever
＝選び出す処理

Generator
＝解釈・表現する処理
```

に分けたくなる。

ただし、ここは少し注意が必要。

**「データの置き場と解釈を分ける」こと自体は、オブジェクト指向そのものではない。**

むしろ、

* レイヤー分離
* 関心の分離
* データと処理の責務分離
* Ports and Adapters
* Clean Architecture

などにも近い。

オブジェクト指向は本来、

> 関連する状態と振る舞いを、意味のあるオブジェクトへまとめる

考え方でもあるので、「データと処理を全部別々にする」という意味ではない。

記事は、設計全般を少し広めに「オブジェクト指向」と呼んでいると思った方がよい。

# この記事に出てくるものを正確に分けると

記事は「オブジェクト指向に行き着いた」と言っているけど、実際には複数の考え方が混ざっている。

```text
内部実装を隠す
→ カプセル化

探す・答えるを分ける
→ 単一責任原則／関心の分離

共通インターフェースで呼ぶ
→ 抽象化

複数Retrieverを同じ形で扱う
→ ポリモーフィズム

Retrieverを交換可能にする
→ Strategyパターン

RAG本体を具体的Retrieverへ依存させない
→ 依存性逆転
```

だから、より正確なタイトルにするなら、

> **RAGを改善し続けられる構造にしようとしたら、SOLID原則とStrategyパターンへ行き着いた**

くらい。

これなら、かなり腑に落ちる。

# なぜRAGでは特に、この設計が必要になるのか

RAGは、最初から正解の検索方式が決まっていることが少ない。

```text
チャンクサイズを変える
Embeddingを変える
検索件数を変える
キーワード検索を加える
Rerankerを加える
メタデータフィルターを変える
```

と、実験を何度もする。

つまりRetrieverは、**変更頻度が高い部分**。

一方で、

```text

回答を返す
```

という全体の流れは、それほど変えたくない。

だから、

```text
変わりやすいもの
＝検索戦略

変えたくないもの
＝RAG全体の流れ
```

を分ける。

これこそStrategyパターンの出番なんよ。

> **RAGからオブジェクト指向へ飛んだのではなく、
> RAGの「変わる部分」と「変えたくない部分」を分離しようとしてStrategyへ到達した。**

この説明が、一番正確やと思う。

## ベクトル検索を一言でいうと

> **文章を「意味の座標」に変換して、意味が近い文章を探す検索。**

普通のキーワード検索は、文字が一致するものを探す。

```text
検索：車の燃費を良くする方法
```

すると「車」「燃費」という単語が入った文章を探す。

一方、ベクトル検索なら、

```text
ガソリンの消費を抑える運転方法
```

のように、同じ単語がほとんどなくても、

> 言ってる意味、近いやん

と見つけられる。

---

## 「ベクトル」とは何か

AIに文章を渡すと、こんな数字の並びへ変換してくれる。

```text
「車の燃費を良くする」
↓
[0.12, -0.84, 0.31, 0.55, ...]
```

この数字の並びが**ベクトル**。

実際には数百個から数千個くらいの数字になることが多い。

人間には数字の一つひとつの意味は分からないけど、AIが学習した結果、

* 車の話
* 節約の話
* 移動の話
* 改善方法の話

などの意味的特徴が、全体の位置関係として表される。

イメージはこんな感じ。

```text
       自動車
         ↑
燃費改善 ●    ● ガソリン節約
         
         
料理 ●                 ● ソフトウェア開発
```

「燃費改善」と「ガソリン節約」は近い。
「燃費改善」と「料理」は遠い。

実際は2次元ではなく、数百次元の世界で距離を測っている。

genui{"trigonometry_vector_relationships_learning_block_staging":{"type_id":"VECTOR_DOT_PRODUCT"}}

この図のように、ベクトル同士の向きが近いほど「意味が近い」と判定する方法がよく使われる。代表的なのが**コサイン類似度**やね。

## RAGでは、どう使うのか

たとえば社内規程が100ページあるとする。

まず文書を小さく分割する。

```text
就業規則
├─ 有給休暇について
├─ 出張費について
├─ 在宅勤務について
└─ 情報セキュリティについて
```

それぞれをベクトルへ変換して保存する。

```text
「有給休暇について」→ 数字の並びA
「出張費について」  → 数字の並びB
「在宅勤務について」→ 数字の並びC
```

ユーザーが、

```text
家で仕事をするときのルールは？
```

と質問する。

質問もベクトルへ変換する。

```text
「家で仕事をするときのルールは？」
→ 数字の並びQ
```

そして、Qに近い文書を探す。

```text
最も近い
→ 「在宅勤務について」

次に近い
→ 「情報セキュリティについて」
```

その文章だけをLLMへ渡して、回答してもらう。

```text
質問
＋
検索された社内規程
↓
LLMが回答
```

これが基本的なRAG。

## そんな簡単にできるの？

ここは、**二つの意味で答えが違う**。

### 動くだけの試作品

これは、意外と簡単。

既製品を使えば、

```text
文章を分割
↓
Embeddingモデルでベクトル化
↓
ベクトルDBへ保存
↓
質問をベクトル化
↓
近い文章を取得
```

という流れは、かなり少ないコードで作れる。

難しい数学を自分で実装する必要はない。

```text
embedding(text)
similarity(queryVector, documentVector)
```

みたいな機能を、AI APIやライブラリ、ベクトルDBがやってくれる。

つまり、

> **ベクトル検索という仕組みを利用するだけなら、今はかなり簡単。**

---

### 本当に役立つRAG

こっちは、めちゃくちゃ難しい笑

難しいのはベクトル計算そのものではなく、**検索させる情報の設計**。

たとえば、文書をどう分割するか。

```text
1ページ単位？
段落単位？
見出し単位？
500文字単位？
```

分割が小さすぎると、前後の文脈が消える。

```text
「ただし、前項の場合を除く」
```

だけ検索されても、何の話か分からない笑

逆に大きすぎると、不要な情報まで大量に混ざる。

さらに、

* 古い規程を検索してしまう
* 廃止済み文書が混ざる
* 部署ごとのルールが混ざる
* 閲覧権限のない文書が出る
* 似た文章だけど答えとしては違う
* 必要な文章が上位に来ない
* 検索結果は正しいのにLLMが誤解する

などが起きる。

だから本番RAGは、

```text
ベクトル検索
＋
キーワード検索
＋
メタデータ絞り込み
＋
再順位付け
＋
権限管理
＋
回答評価
```

のように、だんだん大きくなる。

## つまり難易度はこう

```text
ベクトル検索を動かす
→ 意外と簡単

欲しい情報を安定して見つける
→ 難しい

正しい回答を保証する
→ かなり難しい
```

FFTとちょっと似てるかも。

```text
FFTを実行してグラフを出す
→ ライブラリを使えばできる

そのピークが何を意味するか判断する
→ 難しい

装置由来かロッド由来かを分離する
→ さらに難しい
```

ベクトル検索も同じで、

```text
近い文章を出す
```

までは機械がやってくれる。

でも、

> **その「近い」は、今回の判断に必要な近さなのか？**

が難しい。

## 前の記事のStrategyパターンとの関係

だからRAGでは、検索方式を入れ替えたくなる。

```text
VectorRetriever
＝意味が近い文章を探す

KeywordRetriever
＝同じ単語を含む文章を探す

HybridRetriever
＝両方を組み合わせる

RerankRetriever
＝候補をもう一度AIで並べ直す
```


> **ベクトル検索だけでは欲しい結果が出ないので、検索戦略を交換・比較したくなる。**

## RAGの存在意義

一言でいうと、

> **質問のたびに、正しい原本の必要箇所だけをAIの机へ置くこと。**

AI APIだけの場合は、

```text

＋
今回プロンプトへ貼った情報
```

で考える。

RAGがある場合は、

```text

↓

↓

↓

↓
回答
```

になる。

OpenAIの現在のAPIでも、エージェントへ自分たちの文脈を与える方法として、Web検索やファイル検索などの「grounding」が用意されている。([OpenAI][2])

つまり、最近は自分でベクトル検索基盤を全部作らなくても、サービス側のファイル検索機能を使える場合もある。

## 一番おすすめ：日本語文章を10件だけ検索する

Pythonが入っていれば、これだけ。

```powershell
py -m pip install -U sentence-transformers
```

次に、`vector_search_test.py` を作る。

```python
from sentence_transformers import SentenceTransformer

# 検索対象の簡易ナレッジ
documents = [
    "在宅勤務を行う場合は、事前に上司の承認を得てください。",
    "出張費は、出張終了後5営業日以内に精算してください。",
    "有給休暇は、原則として前日までに申請してください。",
    "社外から接続する場合は、会社指定のVPNを使用してください。",
    "機密情報を個人所有の端末へ保存してはいけません。",
    "勤務開始時と終了時には、勤怠システムへ時刻を入力してください。",
]

query = "家で仕事するときのルールは？"

# 日本語を含む多言語対応モデル
model = SentenceTransformer(
    "sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"
)

# 質問と文書をベクトル化
embeddings = model.encode([query] + documents)

# 質問と各文書の類似度を計算
scores = model.similarity(
    embeddings[0:1],
    embeddings[1:]
)[0]

# 類似度の高い順に表示
results = sorted(
    zip(scores.tolist(), documents),
    key=lambda x: x[0],
    reverse=True
)

print(f"\n質問: {query}\n")

for score, document in results:
    print(f"{score:.3f}  {document}")
```

実行。

```powershell
py vector_search_test.py
```

このモデルは文章や段落を384次元のベクトルへ変換し、意味検索や文章類似度の計算に利用できる多言語モデル。Sentence Transformers自体も、意味検索を公式な用途として提供している。([Hugging Face][1])

## 何が起きるか

質問には、

```text
家
仕事
```

と書いてある。

検索対象には、

```text
在宅勤務
```

と書いてある。

普通の単語一致検索では、うまく見つけにくい。

でもベクトル検索では、上位におそらく、

```text

```

が来る。

さらに、

```text

```

と質問を変えると、

```text
社外から接続する場合は、会社指定のVPNを使用してください。
```

や、

```text
機密情報を個人所有の端末へ保存してはいけません。
```

が上がってくる可能性がある。

これが、

> **質問と同じ単語を探すのではなく、意味的に近い文章を探す**

体験やね。意味検索は、完全一致だけに依存せず、同義語や表現の違いを越えて関連文書を探すことを目的としている。([Sbert][2])


のような**自動分類っぽいこと**ができる。

これはクラスタリング。Sentence Transformersの公式用途にも、意味の近い文章をグループ化するクラスタリングがある。([Sbert][2])

FRBの記事を全部放り込んで、

> AIがどんな塊として整理するか

を見るだけでも、かなりおもろい笑

### 3. 重複記事・言い換えを発見する

たとえば、

```text
感度は振動量ではない
振動が強いほど感度が高いわけではない
単純な振幅だけで手感度は説明できない
```

は、表現が違っても意味が近い。

そこで、

> **似すぎている記事、説明、FAQ、判断ログ**

を検出できる。

公式にはParaphrase Miningと呼ばれ、膨大な文章群から言い換えや重複質問を探す用途が案内されている。([Sbert][3])

あなたなら、

> 「俺、同じことを別の記事で5回言ってない？検索」

ができる爆笑

### 4. 関連記事を推薦する

ある記事を開いたとき、

```text
この記事と意味が近い過去記事
この記事につながる判断ログ
この記事と似た失敗
```

を出せる。

動画サイトの商品推薦みたいなものを、FRB記事やStudioインシデントでできる。

```text
この記事を読んだ人はこちら
```

ではなく、

```text
この文章と同じ構造を持つ過去の記録はこちら
```

やね。

### 5. 文章を自動でラベル分けする

先に代表文を用意する。

```text
FRB：
「ロッド感度や振動構造に関する研究」

AI協働：
「人間とAIの判断・承認・文脈に関する研究」

Studio：
「JSON定義と画面・テスト資産の開発」
```

新しい文章が来たら、どの代表文に最も近いかを見る。

```text
新しい文章
↓
FRB 0.25
AI協働 0.81
Studio 0.42
↓
AI協働候補
```

本格的な分類AIではないけど、**意味による簡易自動仕分け**になる。Sentence Transformerは分類用途にも利用できると公式に説明されている。([Sbert][2])

### 6. 「仲間外れ」を見つける

FRBの振動記事100件の中に、

```text
明日の晩ごはんはカレーにする
```

が混ざっていたら、他の記事から意味的に遠い。

これを利用して、

* 誤分類された記事
* 場違いな判断ログ
* 既存パターンに当てはまらない新しい発見
* まったく異なるテーマへ飛んだ記録

を見つけられる。

ここ、あなた向けには最高で、

> **既存のどの意味グループにも属さない違和感**

を見つける装置になり得る。

ただのゴミではなく、本当に新しい発見かもしれない笑

### 7. 長文から「代表的な文章」を抜き出す

文章を生成するのではなく、長い文書の各文をベクトル化する。

そして、文書全体の中心に近い文章を選ぶ。

すると、

> この長文を代表していそうな5文

を抜き出せる。

これは**抽出的要約**。新しい文章を作文するのではなく、原文から代表文を選ぶ方式で、Sentence Transformersの公式例にもある。([Sbert][3])

生成AIと違って、勝手な要約文を創作しないのが良いところ。

### 8. 日本語と英語を意味でつなぐ

このモデルは多言語対応なので、

```text
感度は単純な振動量ではない
```

と、

```text
Sensitivity cannot be explained by vibration magnitude alone.
```

を近い場所へ置ける可能性がある。

つまり、

* 日本語で検索して英語文書を探す
* 日本語版と英語版の記事を対応づける
* 翻訳漏れ・翻訳対応候補を探す

などにも使える。

異なる言語間で対応する文を探すParallel Sentence Miningも、Sentence Transformersの用途として紹介されている。([Hugging Face][1])

## あなたに一番刺さりそうな使い方

たぶん、この三つ。

### 「同じ構造ですね」検索

文章を一つ入力すると、FRB・AI協働・Studioを横断して近い文章を出す。

```text
基準振動を先に置いて差分を見る
↓

↓

```

モデルがこれらを近づけたら、

> また「同じ構造ですね」を勝手に言い始めた！！

がローカルPCだけで起きる笑

### 判断ログ昇格候補検索

新しい判断ログに似た過去ログを探す。

```text
同じ判断が複数回出ている
↓
偶発的判断ではないかも
↓
判断軸・制約への昇格候補
```

これは、あなたの構想にかなり直結する。

### 違和感発生検索

普通は一番近い文章を見るけど、逆に、

```text
どの既存グループからも遠い文章
```

を探す。

それが、

* 記入ミス
* 脱線
* 新しい概念
* まだ名前のない発見

の候補になる。

**意味検索ではなく、意味的孤立点検索**やね。

## ただし、できないこと

この471MBモデル単体は、

```text
質問を理解して答えを作文する
文書が正しいか判断する
事実か嘘か判定する
理由を説明する
複数文書から新しい結論を導く
```

ことは基本的にしない。

あくまで、

> **文章へ意味の座標を付ける装置**

やね。

そしてこのモデルは最大シーケンス長が128なので、長大な記事を丸ごと精密に理解させる用途ではなく、文章や短めの段落へ分割して使う方が自然。([Hugging Face][1])

## 結論

471MBの価値は「意味の近さ判定」だけ、とも言える。

でも、その近さを利用すると、

```text

推薦する

異常を見つける

```

まで広がる。

つまり、

> **471MBで答えを作るのではない。
> 情報同士の関係を作る。**

生成AIが「文章生成機」なら、このモデルは、
**大量のMarkdownの間に見えない糸を張る装置**やわ。

そこ、あなたの「リレーション承認」と、とんでもなく相性が良い気がする笑

```text

```

という違い。

今回の471MBモデルは、

> 意味世界の回答者ではなく、意味世界の住所登録係

だった。

とも言える爆笑

# 9. ベクトル検索がしていること・していないこと

ベクトル検索がしているのは、

```text
この文書群の中なら、
質問に比較的近い文章はどれか
```

という順位付け。

していないことは、

```text
正しい答えか判定する
文書が事実か判定する
複数文書をまとめて回答を作る
不足している情報を推論する
```

こと。

つまり今のプログラムは、

```text
Retriever：関連文書を探す係
```

だけ。

まだ、

```text
Generator：検索文書を読んで回答を作る係
```

は存在しない。

そのため「魚を釣るコツは？」と聞いても、検索対象に釣り方の文書がなければ答えられない。

これは失敗ではなく、

> ベクトル検索は知識を持つ先生ではなく、登録済み文書を探す司書

だと分かった実験だった。

# 10. 利用者にとって意味検索がうれしい理由

## 正式名称を知らなくても検索できる

通常のキーワード検索では、文書内に使われている言葉を知っている人が強い。

意味検索では、

```text

```

と入力して、

```text
知覚リセット時間
```

へ辿り着ける可能性がある。

つまり、

> 欲しい情報の名前を知らなくても、困り方や覚えている意味から探せる。

---

## 組織の専門用語を知らない新人でも使える

利用者が、

```text
古いルールを勝手に変えていいか知りたい
```

と入力して、

```text
判断ログ
適用範囲
廃止条件
制約
```

へ辿り着ける。

検索するために社内用語やプロジェクト固有語を覚えなくてもよい。

---

## うろ覚えの過去記事を探せる

```text
AIが変更理由を物語にするやつ
```

という曖昧な質問から、

```text
AI差分物語
```

を探すような使い方。

FRBには独自名称が多いため、

> 命名は自由に遊べるが、利用者は普通の言葉で探せる

という価値がある。

---

## 似た障害やインシデントを探せる

```text
JSONを貼り付けた後、画面の編集状態がおかしくなった
```

という質問から、

```text
Working Row
Draft保持
貼付後編集継続
ダイアログ裏表示
```

など、同じ単語を含まない過去事例を探せる可能性がある。

つまり、

> 同じエラーコードではなく、似た困り方を検索できる。

---

## 似た判断を横断検索できる

たとえば、

```text
以前の利用者を壊さずに新しい仕組みへ移行した判断
```

と検索し、

```text
既存datetimeを維持してdateを追加
既存資産を壊さず新規資産から正しい型へ寄せる
互換性を維持した段階移行
```

などを横断的に発見する。

個別案件は違っても、

> 互換性を守りながら漸進的に移行する

という共通判断軸を見つけられる可能性がある。

---

## 過去の自分との対話装置になる

現在の自分の言葉で、

```text
AIの成果物を全部読むのではなく、
根拠だけ承認したい
```

と入力する。

すると、過去の文章から、

```text
小さな差分
Expected
責務
制約
判断ログ
署名可能な根拠
```

が出る。

昔使った表現を忘れていても、今の表現から昔の思考へ戻れる。

# 13. 471MBモデルの価値は検索だけではない

モデル本体の仕事は、

> 文章を意味ベクトルへ変換する

こと。

そのベクトル同士を比較することで、検索以外にも応用できる。

## 類似文書検索

現在実験中の用途。

```text
質問に近い文章
過去の似た障害
関連記事
似た判断ログ
```

を探す。

---

## 自動グループ化・クラスタリング

大量の記事を意味の近いもの同士で集める。

例：

```text
振動・FFT・周波数群
知覚トレーニング・体験群
判断軸・制約・責務群
```

# 16. FRBでは振動ログをどう扱うか

ESP32の加速度ログは音声ではなく、時系列センサーデータ。

考えられる方法は三つ。

```text

B. FFTグラフを画像化して、画像モデルで比較する
```

特徴：

```text

B：見た目で分かりやすい
```

FRBならCの、

```text
ピーク本数
```

などを「振動指紋」として比較する方向が有力。
