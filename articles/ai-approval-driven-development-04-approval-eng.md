# 前回は「同じ判断を、二度させるな」だった

前回の **AI承認駆動開発 #3** では、

> **同じ判断を、二度させるな。**

という考え方について書いた。

AIが生成したものを、人間が毎回一件ずつ確認する。
答えがすでに決まっていることまで、AIに何度も考え直させる。

それでは、AIの生成速度が上がるほど、人間の承認負荷も増えていく。

そこで、

```text
承認済みDefinition
＋
承認済みGeneration Rule
↓
Program Derived
```

という方向を考えた。

人間が一度意味を持って判断したことを、

- 判断軸
- 制約
- 責務
- Generation Rule

として再利用可能な構造へ変える。

一意に導出できるものはプログラムへ倒す。

そして、

> **人間には、まだ答えのない判断へ集中してもらう。**

という考え方である。

その記事の中で、一つの小さな実装上の話を書いた。

```text
minimum
minimum_minus_1
maximum
maximum_plus_1
```

というテストパターンである。

今回の話は、そこから始まる。

---

# 始まりは、minimum_minus_1だった

StudioくんのField Definitionでは、例えば次のような定義を持っている。

```json
{
  "validation_type": "integer",
  "minimum": 1,
  "maximum": 100,
  "nullable": false
}
```

この定義を見ながら、

> どんなテストをすればよいのか。

を考えていた。

そこで、

```text
minimum_minus_1
minimum
maximum
maximum_plus_1
invalid_format
```

のような、テストパターンを表す略語を作り始めた。

しかし途中で、

> **おん？？**

となった。

`minimum = 1` が分かっていて、`minimum_minus_1` という意味も分かっている。

なら、

```text
0
1
100
101
```

という具体値を、AIや人間が毎回考える必要はない。

プログラムで導出できる。

さらに、

```text
0   → REJECT
1   → ACCEPT
100 → ACCEPT
101 → REJECT
```

というExpectedまで導出できる。

そして、複数の検証パターンをひとまとめにするために使っていた言葉が、

> **Validation Type**

だった。

```text
Validation Type
        ↓
そのTypeで確認すべき複数のPattern
        ↓
具体値
        ↓
Expected
```

この構造は、実際にかなり便利だった。

Typeを指定すれば、

> **そこにぶら下がる複数の検証パターンを容易に展開できる。**

# Validation Typeのインパクトを、少しだけ想像してみる

ここで、この方式のインパクトを少しだけ具体的に想像してみたい。

例えば、

```json
{
  "validation_type": "integer"
}
```

という、一つの型を決めたとする。

そして、この`integer`という型に、

```text
minimum_minus_1
minimum
maximum
maximum_plus_1
invalid_format
```

という5つの基本的な検証パターンがぶら下がっているとする。

では、同じような数値項目が20項目あったらどうなるだろう。

```text
20項目
×
5チェック
=
100チェック
```

さらに、同じような画面が50画面あったら。

```text
20項目
×
50画面
×
5チェック
=
5,000チェック
```

5,000である。

もし従来型の仕事で、

- テスト仕様書へチェック項目を書く
- テストデータを書く
- Expectedを書く
- 実行結果を確認する
- エビデンスを残す
- 別の人がレビューする
- さらに承認者が確認する

という流れを取っていたら、

> **この5,000個のチェック項目を、いったい何回、人間は書き、読み、確認するのだろう。**

と考えたくなる。

例えば、5,000個のチェック項目を、

```text
テスト担当者
＋
レビュー担当者
```

の2人が一度ずつ見るだけでも、

```text
5,000
×
2人
=
10,000回
```

の確認機会になる。

さらに承認者が加われば、もっと増える。

もちろん、実際の開発では全画面・全項目が完全に同一条件ではないし、
すべてのチェックが人間による一件単位の確認になるわけでもない。

それでも、この数字を見れば、

> **Typeを決めることで、同じ意味の検証を何度も人間が記述・確認する構造を減らせる。**

という、この方式のインパクトは想像しやすいと思う。

重要なのは、

> **5,000個のチェックを省略すること**

そのものではない。

本当に減らしたいのは、

> **すでに意味が確定している同じ判断を、何度も人間へ返すこと**

である。

`validation_type = integer`

と一度決めれば、

```text
minimum_minus_1
minimum
maximum
maximum_plus_1
invalid_format
```

という検証パターンを毎回ゼロから考えなくてよい。

Field Definitionから具体値を導出できる。

Expectedも導出できる。

共通Test Runnerへ渡せる。

つまり、

```text
1つのType
↓
複数の検証パターン
↓
多数の項目
↓
多数の画面
```

へ、一つの判断を再利用できる。

私は、この経験から、

> **「Typeを作る」という行為そのものに、大きな意味があるのではないか。**

と考えるようになった。

そして今回考えたいのは、

> **この構造は、本当にプログラム開発だけのものなのか？**

という話である。

---

# 「チェック観点」という言葉が、私の中で曖昧だった

私はこれまで、

> チェック観点

という言葉を普通に使ってきた。

でも最近、少し引っかかるようになった。

例えば、

> 操作性をチェックする。

と言ったとする。

これはチェック観点なのだろうか。

かなり大きい。

では、

```text
文字が切れていないか
ボタンが他の要素へ重なっていないか
主要操作へ常に到達できるか
余白が不自然ではないか
```

はどうだろう。

これらもチェック観点と呼べる。

つまり、

> **「チェック観点」という一つの言葉の中に、抽象度の違うものが混ざっている。**

ように見えてきた。

そこで、少し分けて考えることにした。

---

# 判断軸・制約は「大きな意味」

例えば、UIを設計するときに、

```text
利用者が迷わず操作できることを重視する
```

という考え方があったとする。

これは **判断軸** である。

複数の成立する案があるとき、

> どちらを優先して選ぶのか。

その方向を示す。

一方、

```text
主要操作を利用不能な状態にしてはならない
```

なら、**制約** として扱える。

越えてはいけない境界である。

```text
判断軸
= 何を大切にするのか

制約
= 何を越えてはいけないのか
```

成果物を作るとき、AIや人間へ方向を与える言葉である。

---

# Validation Typeは「小さな見る型」

では、その成果物をレビューするときはどうするか。

例えば、先ほどのUIなら、

```text
CLIPPING
OVERLAP
ACTION_REACHABILITY
STATE_FEEDBACK
VISUAL_HIERARCHY
```

のような、**もっと小さな「見る型」**へ分解できる。

```text
CLIPPING
→ 文字やボタンが領域外へ欠けていないか

OVERLAP
→ 要素同士が意図せず重なっていないか

ACTION_REACHABILITY
→ 主要操作へ常に到達できるか

STATE_FEEDBACK
→ 現在状態が利用者へ伝わっているか
```

私は、このくらいの粒度を、

> **Validation Type**

として扱えないかと考えている。

つまり、

```text
判断軸・制約
= 大きな意味

Validation Type
= 小さな見る型
```

である。

さらにValidation Typeの下には、具体的な確認パターンがぶら下がる。

```text
判断軸・制約
「なぜ見る？」

        ↓

Validation Type
「何を見る？」

        ↓

Check Pattern / Test Pattern
「具体的にどう見る？」

        ↓

Expected
「どうなっているはず？」
```

この整理をすると、私の中で曖昧だった「チェック観点」という言葉が、少しだけ解像した。

---

# 作るときは判断軸・制約、見るときはValidation Type

一旦、かなり乱暴に分けるなら、

```text
成果物を作るとき
→ 判断軸・制約

成果物を見るとき
→ Validation Type
```

と考えることができる。

例えば、AIへ資料を作ってもらう。

そのとき、

```text
判断軸：
簡潔さより説明可能性を優先する

制約：
根拠のない断定をしない
```

を渡す。

成果物ができた。

今度はレビューする。

```text
Validation Type:
EVIDENCE
CONSISTENCY
TRACEABILITY
DIFF_EXPLANATION
```

のような型で確認する。

もちろん、完全に別物ではない。

制約に、

```text
根拠のない断定をしない
```

があれば、その制約自体が守られているかを見る必要がある。

しかし、その場合でも、判断軸・制約一つひとつを別々のValidation Typeへ変換する必要はないと思っている。

例えば、

```text
AXIS_CONSTRAINT_COMPLIANCE
```

のような一つのTypeで、

> **適用される判断軸・制約が守られているか。**

を確認すればよい。

判断軸・制約そのものは、大きな意味として残しておく。

Validation Typeは、もっと小さな「見る型」を中心にする。

---

# ドキュメントにもValidation Typeを置けるのではないか

この考え方を、プログラムの外へ持ち出してみる。

例えば、設計書。

```text
EVIDENCE
TRACEABILITY
CONSISTENCY
UNRESOLVED_ITEM
DIFF_EXPLANATION
```

のようなValidation Typeを持てるかもしれない。

提案書なら、

```text
CUSTOMER_VALUE
EVIDENCE
RISK
ALTERNATIVE
COST_BENEFIT
```

かもしれない。

ここで重要なのは、

> **プログラムと同じように「保証できる」と言っているわけではない。**

ということである。

プログラムなら、`minimum_minus_1` を機械的に生成し、ExpectedとActualを比較して、PASS / FAILをかなり確定的に出せる。

しかし、

> この提案書は顧客価値を十分に説明できているか。

は、同じようには扱えない。

AIに評価してもらうことはできる。
人間がレビューすることもできる。

でも、機械的な真偽判定とは違う。

だから、Validation Typeを一般化するときには、

```text
Machine
AI
Human
```

のどこで確認するのかも考える必要がある。

それでも、

> **Typeを指定すると、そこに紐づく複数のチェック観点を展開できる。**

という構造自体は変わらない。

---

# デザインのValidation Typeを作りたい

個人的に、今かなり興味があるのが、

> **デザインのValidation Type**

である。

私はAIと一緒にUIを修正しているとき、何度も、

> そこじゃない。

となる。

例えば、

```text
区切り線を左へ寄せたい。
ただし右端のテキストボックス位置は変えたくない。
```

という話。

人間には、

> 「この部分だけを動かしたい」

と比較的自然に伝わる。

しかしAI側では、余白全体を調整したり、別の要素まで動かしたりすることがある。

ここで、

```text
OVERLAP
ALIGNMENT
INVARIANT_POSITION
```

のような共通語彙があれば、

> 今回確認してほしいのはOVERLAP。  
> INVARIANT_POSITIONは守る。

と話せるかもしれない。

これは、AIのデザイン能力そのものを高める話ではない。

> **人間とAIが「何を見ているのか」を合わせるための共通語彙を作る。**

という話である。

---

# Validation Typeを作ることは、暗黙知を炙り出すことかもしれない

ここで、さらに面白いことに気づいた。

Validation Typeを作ろうとすると、

> **なぜ私は、ここをチェックしているのか？**

を考える必要がある。

例えば、

```text
ACTION_REACHABILITY
```

というValidation Typeが何度も必要になる。

すると、

> どうして私は、毎回これを見ているのだろう。

と考える。

そこで、

```text
重要な操作へ常に到達できることを重視する
```

という判断軸が見つかるかもしれない。

さらに、

```text
主要操作を利用不能な状態にしてはならない
```

という制約へ昇格するかもしれない。

つまり、

```text
違和感
↓
チェック観点
↓
Validation Type
↓
蒸留
↓
判断軸・制約
```

という方向がある。

ところが、判断軸・制約が育つと、今度は逆方向が始まる。

```text
判断軸・制約
↓
それを確認するには、
何を見ればよい？
↓
新しいValidation Type
```

である。

---

# 判断軸・制約とValidation Typeは、同期しながら育つ

ここまで考えると、判断軸・制約とValidation Typeは、完全に別の資産ではないように見えてきた。

```text
判断軸・制約
        ↓ 具体化
Validation Type
        ↓ 適用
差分・違和感
        ↓
人間の判断
        ↓
判断ログ
        ↓ 蒸留
判断軸・制約
```

という循環で育っていく。

判断軸・制約は、

> **なぜ見るのか。**

Validation Typeは、

> **何を見るのか。**

そしてCheck Patternは、

> **どう見るのか。**

を持つ。

```text
なぜ見る？
判断軸・制約

何を見る？
Validation Type

どう見る？
Check Pattern / Test Pattern
```

私は今、この三つを分けて考えることで、「チェック観点」という言葉を以前よりかなり扱いやすく感じている。

---

# 優れた人は、頭の中に大量の「見る型」を持っているのではないか

例えば、会社の経営者や経験豊富な管理者へ何かを報告すると、いろいろな質問が返ってくる。

```text
前年対比は？

顧客への影響は？

リスクは？

誰が責任を持つ？

それは再現できる？

そもそも、何のためにやる？
```

これは単に、

> 偉い人だから色々言っている。

という話ではない。

経験の中で、**大量の「見る型」を持っている**と考えることもできる。

```text
報告内容
    ↓
頭の中の複数の型と比較
    ↓
ギャップを発見
    ↓
質問・助言
```

もし、その型の一部をValidation Typeとして外へ出せたらどうなるだろう。

```text
CUSTOMER_IMPACT
RISK
ACCOUNTABILITY
REPRODUCIBILITY
STRATEGIC_ALIGNMENT
```

報告前に、

> このValidation Typeで一度レビューして。

とAIへ頼める。

もちろん、経営者本人の判断を代替できるとは思っていない。

しかし、

> **熟練者が普段見ている観点を、組織で共有する。**

ことはできるかもしれない。

---

# AI協働では、Validation Typeを判断軸・制約の近くに置いておきたい

AI協働を始めるとき、

```text
目的は？
判断軸は？
制約は？
```

と聞く。

その近くに、

> **Validation Typeは？**

という言葉も置いておく。

そして、

> **新しいTypeを作ったら、何か再利用できないか？**

と考える。

最初から完璧なValidation Type Catalogを作る必要はない。

現場で、

```text
また同じことを指摘した。

また同じ観点でレビューした。

またAIへ同じ説明をした。
```

となったときに、

> **これ、Typeにできない？**

と考える。

それを積み重ねる。

Validation Typeが溜まる。
似たTypeから、判断軸・制約が見えてくる。
判断軸・制約が育つ。
そこからまた、新しいValidation Typeが生まれる。

---

# プロンプトではなく「見る型」を組織資産にする

企業でAIを使い始めると、良いプロンプトを集めたくなる。

もちろん、それにも価値はある。

でも今回の話を考えていると、別の資産も重要に思えてくる。

```text
Prompt
= AIへどう伝えるか

Validation Type
= 組織として何を見るか
```

モデルが変われば、プロンプトの書き方は変わるかもしれない。

しかし、

```text
根拠を見る
要求との接続を見る
リスクを見る
差分理由を見る
主要操作への到達性を見る
```

という観点は、比較的長く残る。

だから、

> **プロンプトだけでなく、組織の「見る型」を育てる。**

という考え方があってもよいと思う。

これは、組織の暗黙知を外へ出す行為でもある。

---

# 少ない良いルールが、チーム全体の行動を変えるかもしれない

ここで少しだけ、自己組織化という言葉を思い出した。

大げさな意味ではない。

AIが自律的に勝手に成長する、という話でもない。

チームの一人ひとりが、

```text
判断軸・制約を確認する
適用するValidation Typeを選ぶ
違和感があれば残す
同じ観点が繰り返されたらType化を考える
```

という、少数の簡単なルールを守り続ける。

すると外から見れば、

```text
このチームは、
いつも似た観点で確認している。

新しい問題が起きると、
新しい観点が蓄積される。

熟練者の判断が、
少しずつ共有されている。
```

ように見えるかもしれない。

誰か一人が、組織全体の判断体系を最初から設計したわけではない。

小さな判断の積み重ねから、結果として **組織の判断構造が育っていく。**

そのくらいの意味で、一種の自己組織化と呼べる可能性はあるのかもしれない。

---

# そして、この考え方に名前を付けたくなった

ここまで考えてきたことを振り返る。

始まりは、

```text
minimum_minus_1
```

だった。

そこから、

```text
minimum
maximum
maximum_plus_1
```

という複数のテストパターンが生まれた。

それらを、

```text
Validation Type
```

としてまとめた。

すると、

> **Typeを指定すれば、複数の検証パターンを容易に展開できる。**

ことが分かった。

そして、

> この構造を、プログラム開発の外へ持ち出せないか。

と考えた。

ドキュメント。
デザイン。
報告。
意思決定。
組織のレビュー。

そこでも、

```text
判断軸・制約
        ↓
Validation Type
        ↓
Check Pattern
        ↓
Machine / AI / Human
        ↓
差分
        ↓
人間の判断
```

という構造を作れる可能性がある。

大切なのは、**すべてをAIに自動判定させることではない。**

何を大切にするのか。
何を越えてはいけないのか。
何を見るのか。
どう見るのか。
誰が確認するのか。
そして、人間が何を見れば承認できるのか。

それらを設計する。

私は、AI承認駆動開発から派生してきたこの考え方を、

> **Approval Engineering**

と呼んでみることにした。

日本語にするなら、

> **承認工学**

である。

まだ構想段階である。

定義も、構造も、Validation Typeの分類も、これから変わると思う。

ただ、一つだけオリジンは明確に残しておきたい。

> **Approval Engineeringは、Validation Typeを指定することで、そこにぶら下がる複数の検証パターンを容易に導出できた、ソフトウェアテスト上の実体験から始まった。**

最初から、

「人間の承認を工学化しよう」

と考えていたわけではない。

ただ、

```text
minimum_minus_1
```

を見ながら、

> **これ、毎回考えなくていいやん。**

と思った。

そこから始まった。

---

:::message
**判断軸・制約は「大きな意味」。**

**Validation Typeは「小さな見る型」。**

**その型を育て、人間・AI・プログラムが何を見るべきかを整理し、人間が承認しやすい構造を設計する。**

**この試みを、Approval Engineering（承認工学）と呼んでみることにする。**
