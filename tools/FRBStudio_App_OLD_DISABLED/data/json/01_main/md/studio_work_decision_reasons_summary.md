# 判断理由の要約一覧

- 初回の構造変更では、新技術の導入よりも既存動作と読み込み順の安全を優先する。
- 責務分割、Registry化、UI接続など性質の異なる変更を一度に混ぜると、原因切り分けと回帰確認が難しくなる。
- 大きな構想でも、最初は価値を確認できる最小単位に絞り、重い機能は次段階へ分離する。
- 実績のある既存契約を壊さず、新しい仕掛けを互換レイヤーとして段階導入する。
- 既存関数やUIに依存する外部拡張を考慮し、呼び出し口を急に変更しない。
- 実装詳細ではなく、責務・契約・設定・戦略の境界を明確にする。
- 同じ意味の処理はRegistry・Strategy・共通フォーマットへ寄せ、追加や変更で触る場所を明確にする。
- 共通化によって意味が薄まる場合は無理に統合せず、ドメイン固有の判断軸を残す。
- Coreに個別データ名、会社固有語彙、特定機能名を埋め込むと、汎用性と更新可能性が失われる。
- RuntimeはViewDefやDataから宣言値を受け取り、固定文字列による分岐を増やさない。
- 表示、編集、保存、検索、比較、実行の責務を分け、一つの変更が全体へ波及するのを防ぐ。
- 原本Data、画面定義ViewDef、表示用Markdown・HTML、実行時状態を混在させない。
- 表示用文字列、HTML、検索キャッシュ、集計値、一時レイアウトを原本JSONへ混入させない。
- 保存値はMarkdown原文や構造化JSONのまま保持し、読みやすい表示はView側で変換する。
- ルール、期待値、語彙、メッセージ、設定は複数箇所へ複製せず、一つの正本から参照する。
- 正本ファイル名や参照IDを安定させ、URL、ViewDef、AI依頼、テスト証跡の連鎖切れを防ぐ。
- 現行参照は更新しても、過去ログや差分に残る旧名は当時の証跡として保存する。
- 旧パスや空フォルダーを残すと正本に見えるため、互換が不要なものは明確に退避・削除する。
- 名前やフォルダーは表示順よりも、意味と責務が伝わる構造を優先する。
- ファイル選択はbasenameではなく相対パスを使い、同名ファイルとサブフォルダーを安全に扱う。
- 手動管理リストを増やさず、実体ファイルやmanifestから自動列挙する。
- アプリ固有ルートより上位のPC固有絶対パスに依存せず、持ち運べる相対パス契約にする。
- GitHub PagesなどAPIのない環境では、静的ファイルだけで読込が完結する必要がある。
- 外部URL、親ディレクトリ、任意ファイル、任意コマンドの実行口を開けず、許可済み契約へ限定する。
- 破壊的操作や保存先変更は人間の明示操作と確認を必要とし、通知だけで自動実行しない。
- 判断が不要な成功通知や途中経過は操作を止めず、警告・失敗・対処が必要な状態だけを目立たせる。
- テスト失敗は観測された結果であり、Runnerや起動機構の故障とは区別する。
- 対話型プロセスの起動成功と、終了するテストの成否を同じ結果種別で扱わない。
- ログ出力は診断補助であり、ログ作成失敗が本処理を止めないようにする。
- ログ形式と保存先を共通化し、バッチごとの独自実装で原因調査を難しくしない。
- 一時生成物や再生成可能な出力を成果物ZIPやGitへ混ぜず、ノイズ・肥大化・解凍事故を防ぐ。
- 返却成果物は、ユーザー環境で実際に開けることを内容の正しさと同じくらい重視する。
- Data JSONは人間も読む原本なので、日本語、日時、パス、差分を直感的に読める形式にする。
- 正確でも人間に読みにくいUTC表記やUnicode escapeを、作業画面や証跡の標準にしない。
- 画面上の現在地は一時トーストではなく、現在Data名・タイトル・パスとして常時確認できるようにする。
- タイトルの取得を特定フィールド名へ固定せず、ViewDef契約を正式な入口にする。
- 読む操作と編集操作が衝突しないよう、閲覧時は読み物、編集時は原文というモードを使い分ける。
- 長文は表セルへ押し込まずカードやMarkdownプレビューで読み、短文・数値・選択値は高密度な表で扱う。
- 編集コントロールは対象の近くに置き、hoverや画面幅の変化で逃げたり重なったりしないようにする。
- 画面上部や検索UIは縦に肥大化させず、一覧と本文へ早く到達できる密度を守る。
- 全画面に標準UIを露出する前に、責務境界、保存先、共有方法、操作品質が十分かを確認する。
- 高頻度の小改善は目的が同じならまとめ、管理作業そのものが開発速度を落とさないようにする。
- 現在の困りごとに直接効く情報を優先し、完了通知など代替可能なUIは減らす。
- 読者が記事から同じDataとViewDefへ直接到達できることで、説明ではなく体験を共有できる。
- ブランド名や画面上の名札は、実際に扱う価値と思想が伝わる名称へ統一する。
- アプリの名札、動作設定、履歴、業務データを一つの設定ファイルへ詰め込まない。
- Markdown本文へレビューコメントを埋め込むと公開本文とDiffが汚れるため、Sidecarへ分離する。
- Sidecarと本文は同じ名前と場所で対応関係を分かりやすくし、持ち運びと再読込を容易にする。
- 直接文字列を切り貼りするとMarkdown構造が壊れやすいため、BlockやCellの意味単位で編集する。
- 保存前検査、バックアップ、RoundTrip確認を行い、再生成による意図しない構造差分に備える。
- 大容量データを無理に描画してブラウザを固めるより、概要を示して安全に停止する。
- APIは巨大本文の運搬より、成果物の場所・サイズ・概要・警告を案内する責務へ寄せる。
- 人間が読むべき差分はテキスト差分だけでなく、同一性キーとViewDefによる意味差分で示す。
- Gitは履歴と変更ファイルの検出、Object Compareは内部の意味差分という役割分担にする。
- CSVは画面で見えている行・順序・列を反映し、元JSONへ戻れる安定キーを含める。
- 全文検索はJSON構造を知らない人にも使える共通能力にしつつ、キー名や単純値による大量ノイズを避ける。
- 検索用集約文字列や表示行合計はRuntime状態として再計算し、Dataの正本にはしない。
- 一時的な列幅やレイアウト変更を自動で共有ViewDefへ保存せず、明示的な設計変更として確定する。
- Expected、Actual、Diffを分け、期待値・観測値・比較結果の責務を曖昧にしない。
- 期待値をテストコードへ直書きせず、Expected JSONを人間とAIがレビューできる正本として育てる。
- fail時こそ差分証跡を残し、失敗の理由を人間が追体験できる状態にする。
- テストごとに専用コードを増やさず、言語ごとの汎用RunnerとJSON定義・Adapterで差分を吸収する。
- CompareStrategyを分離し、期待値の型が増えてもRunner本体のif分岐を肥大化させない。
- 比較対象が実際に評価されていないのにpassへ見える状態を、最も危険な設計ミスとして扱う。
- UTは細かな実装手順ではなく、外部から観測できる意味ある責務境界を検証する。
- CTは責務間の接続を確認し、UTの細かな分岐を重複させて組み合わせ爆発を起こさない。
- 責務入口で入力の安全を確立し、内部の小関数すべてへ同じ完全防御を重複要求しない。
- 本番DataやViewDefの変更でテストが壊れないよう、テスト専用fixtureと安定した保証IDを使う。
- 人間が承認できないほど巨大な表や構造は、性能だけでなく品質説明性の問題として扱う。
- メッセージ文言は変更されても、message_idを意味の安定キーとしてログ・Expected・差分を接続する。
- 表示用名称と保存用コードを分け、Value Vocabularyを一つのRegistryから解決する。
- risk、priority、confidenceなど似た値でも判断軸が異なるものは、同じEnumへ安易に統合しない。
- Pluginへ業務マスタを内蔵せず、Core・Overlay・Pluginの所有責務を分ける。
- Coreと会社固有Overlayを物理的に分離し、Core更新で会社資産が消えず、会社変更でCore正本が汚れないようにする。
- OverlayはCore標準IDを上書きせず、manifestに宣言された追加定義だけを読み込む。
- Plugin基盤は会社固有機能をCoreへ持ち込まない最小接続口から始める。
- 文脈の全体前提と対象固有の追加前提を分け、必要な作業だけに適切な情報量を渡す。
- ViewDefは文脈の表示・参照契約を持っても、文脈本文そのものの正本にはしない。
- AIがルール未読や古いソースの記憶だけで作業しないよう、作業前に読む正本と最新ファイルを明示する。
- 前のチャットで扱ったファイルは現在の作業環境に存在するとは限らないため、実物確認なしで修正しない。
- 確認済みという言葉だけでなく、静的確認・parse・実機・ユーザー確認待ちなど確認の種類を記録する。
- AIの完了報告、更新ファイル、対象ルール、影響範囲をインシデントへ残し、会話外でも追跡できるようにする。
- バージョン、リビジョン、作業テーマ、発見時点、修正時点を分け、履歴と責任範囲を追えるようにする。
- AIが更新した内容を人間未確認のまま承認済みにせず、AI確認と人間承認を分離する。
- AI提案は即実行せず、必要性・危険性・重複・優先度を人間が判断できる状態にする。
- AI分析結果は仮説として保持し、Relation Approvalを通るまで正本関係へ昇格させない。
- 反復回数やAI評価だけで判断軸・制約・関係を自動昇格させない。
- 繰り返された失敗や悪習を、頻度だけで正しい基準として舗装しない。
- 思考クラスの定義は実行中に自己変更せず、元版・根拠・反例・承認履歴を持つ次版として更新する。
- 何を実行した結果どの定義が変わったかを追跡し、人間承認を維持する。
- 既知の共通構造を大量表示して差分を埋没させず、非対称・欠落・矛盾など新しい問いを生む差分を優先する。
- グラフの意味データ、表示定義、座標・Viewport、承認状態を分け、見た目の操作で意味の正本を変えない。
- Runtimeへ特定ドメイン語彙を埋め込まず、GraphやDataの差替えでFRB・品質・思考進化へ再利用できるようにする。
- 外部公開よりも、出所・ライセンス・安全な公開範囲の確認と、手元でのAI協働体験を優先する。
- 公開保留時もプロジェクト停止と誤解されない最小限の案内を残す。
- 後続作業を別管理表へ分散せず、インシデント内の明細と代表Statusで検索可能にする。
- 未評価の過去項目を推測で対応不要へ変えず、未評価のまま明示する。
- 管理対象が増えても、人間が全体を眺め、検索し、判断できる構造を優先する。
