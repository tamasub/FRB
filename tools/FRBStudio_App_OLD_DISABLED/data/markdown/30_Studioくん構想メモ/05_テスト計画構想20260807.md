# FRB Studio Test Architecture v0.1 Draft

更新日: 2026-08-07  
ステータス: Draft / 議論用

## 0. 目的

FRB Studioにおけるテストの全体構造を仮定義する。

本資料の目的は、個々のテスト仕様を確定することではない。

今後、新しいDefinition、責務、機能、インシデントが発生した際に、

- 何をテスト対象とするのか
- どの粒度でテストするのか
- TestPatternが必要なのか
- Expectedをどこから導出するのか
- UT / CTをどう区別するのか

を議論するための共通の地図を作る。

---

# 1. 基本思想

FRB Studioのテストは、

「テストコードを書くこと」

を中心には置かない。

中心に置くのは、

- Definition
- Responsibility
- Guarantee
- TestPattern
- Expected
- Actual
- Diff

である。

基本形は以下とする。

```text
Definition / Responsibility / Scenario
              ↓
          Expected
              ↓
            Runner
              ↓
           Actual
              ↓
            Diff
              ↓
        Human Approval
````

テストコードは、言語・実行環境ごとの汎用Runner側へ寄せる。

人間が承認する対象は、
できるだけDefinition、責務、Expected、Diffへ寄せる。

---

# 2. テストの大分類

現時点では、テストを次の3系統に分類する。

```text
TEST
│
├─ 1. Definition Driven Test
│
├─ 2. Responsibility Test
│      ≒ UT
│
└─ 3. Scenario Test
       ≒ CT
```

---

# 3. Definition Driven Test

## 3.1 定義

Definitionを入力として、
検証方法またはExpectedを機械的に導出できるテスト。

原則として、
人間が個別TestPatternを定義しない。

```text
Definition
    ↓
Test / Expected 自動導出
    ↓
Runner
    ↓
Actual
    ↓
Diff
```

---

## 3.2 Definition Validation Test

Definitionそのものが成立していることを確認する。

対象例:

* ViewDef
* FieldDef
* ValidationDef
* ContextDef
* TestDef
* その他Definition JSON

確認例:

* 必須項目
* JSON型
* enum
* minimum / maximum
* Schema適合

```text
Definition
    ↓
Schema Validation
    ↓
PASS / Diff
```

TestPattern:

```text
原則不要
```

---

## 3.3 Definition Contract Test

複数のDefinition間の関係・整合性を確認する。

例:

```text
ViewDef.field_path
    ↓
FieldDefに存在するか

validation_type_id
    ↓
Validation Type Registryに存在するか

view_type = number
    ↓
Validation定義と矛盾していないか
```

Schema単体では検出できない、
Definition間の契約を検証する。

TestPattern:

```text
原則不要
```

---

## 3.4 Definition Realization Test

Definitionで宣言された内容が、
実際の成果物・画面状態へ正しく反映されたことを確認する。

代表例:

```text
ViewDef
    ↓
Expected ScreenState
    ↓
画面表示
    ↓
Actual ScreenState
    ↓
Diff
```

確認例:

* Caption
* visible
* readonly
* control type
* option一覧
* Grid列順
* 初期列幅
* 初期選択状態

重要:

このテストは、

「人間が選んだViewDefが適切か」

を判定するテストではない。

確認するのは、

「承認されたViewDefどおりに実現されたか」

である。

TestPattern:

```text
原則不要
```

実行手順はRunner側の固定処理として扱う。

---

## 3.5 Derived Behavior Test

Definitionから複数のテスト条件を機械的に展開できる場合。

代表例:

```json
{
  "minimum": 0,
  "maximum": 100
}
```

から、

```text
minimum
minimum - 1
maximum
maximum + 1
null
invalid_format
```

などを自動導出する。

```text
Definition
    ↓
Derived TestPattern
    ↓
Derived Expected
    ↓
Runner
    ↓
Actual
    ↓
Diff
```

TestPattern自体は存在するが、

```text
人間がTestPatternを書く必要はない
```

という位置づけとする。

---

# 4. Responsibility Test

## 4.1 定義

1つの責務、またはその責務が持つGuaranteeを
単独で検証するテスト。

FRB StudioにおけるUTは、

```text
コード量が小さいテスト
```

ではなく、

```text
1つの責務が持つ保証を単独で確認するテスト
```

として扱う。

---

## 4.2 基本構造

```text
Responsibility
    ↓
Guarantee
    ↓
Responsibility Test
    ↓
Expected
    ↓
Actual
    ↓
Diff
```

現在の責務マスターでも、
責務を「検証可能な保証の集合」として管理し、
各Guaranteeへ `guarantee_id` を付与し、
TestPatternをそのGuaranteeへ接続する構想となっている。


---

## 4.3 例：列幅変更

```text
責務A
列幅を変更できる

責務B
変更した列幅を保存できる

責務C
保存済み列幅を読み込める

責務D
読み込んだ列幅を画面表示できる
```

UTでは、それぞれを独立して検証する。

```text
Resize責務 UT

Input:
  width = 200

Action:
  resize(300)

Expected:
  width = 300
```

---

# 5. Scenario Test

## 5.1 定義

複数の責務を接続した状態で、
一連の振る舞い・状態遷移が成立することを確認する。

FRB StudioにおけるCTは、

```text
複数の承認済み責務を接続したときの保証確認
```

として扱う。

---

## 5.2 基本構造

```text
Responsibility A
      +
Responsibility B
      +
Responsibility C
      ↓
   Scenario
      ↓
 TestPattern
      ↓
  Expected
      ↓
   Actual
      ↓
    Diff
```

---

## 5.3 例：Grid列幅変更

```text
初期幅 200
    ↓
ユーザーが300へ変更
    ↓
保存
    ↓
画面を閉じる
    ↓
再表示
    ↓
300で復元
```

これは、

```text
Resize
+
Save
+
Load
+
Screen表示
```

という複数責務の接続確認である。

したがってScenario Test / CTとして扱う。

---

# 6. TestPattern要否の判断軸

TestPatternを人間が定義する必要があるかどうかは、
次の判断軸で考える。

## 判断軸

```text
Definitionや責務から、
実行経路とExpectedを
機械的かつ一意に導出できるか？
```

### YES

```text
TestPatternを人間は定義しない
```

例:

* Schema Validation
* Definition Contract
* ViewDef → ScreenState
* Validation境界値自動生成

---

### NO

```text
TestPatternを明示的に定義する
```

主な条件:

* ユーザー操作がある
* 状態遷移がある
* 操作順序に意味がある
* 複数責務を接続する
* 複数の実行経路がある
* 条件分岐がある

---

## 簡易ルール

```text
実行経路が一意
    ↓
TestPattern省略 / 自動導出

実行経路を選択する必要がある
    ↓
TestPattern必要
```

TestPatternとは、

```text
どの経路を通って保証を確認するか
```

を明示する資産と考える。

---

# 7. Expected / Actual / Diff

全テスト系統で、
可能な限り共通の結果構造を使用する。

```text
Expected
    ↓ compare
Actual
    ↓
Diff
```

Expectedは単なる値だけではない。

対象例:

* Value
* State
* Rule
* Relation
* ScreenState
* Count
* Absence
* CSV
* Interface

など。

DefinitionからExpectedを導出可能な場合は、
Expectedも人間が二重入力しない。

---

# 8. ScreenState

画面に関する静的な確認には
ScreenStateを利用する。

```text
ViewDef
    ↓
Expected ScreenState

実画面
    ↓
Actual ScreenState

Expected
    ↓
   Diff
    ↑
Actual
```

ScreenStateは、

「画面を操作するテスト」

ではなく、

```text
定義された画面状態が
実際に成立していることを確認するための観測値
```

として扱う。

---

# 9. UTとCTの境界

## UT

```text
1責務
    ↓
1つ以上のGuarantee
    ↓
単独検証
```

定義:

> UT = 責務単位の保証確認

---

## CT

```text
責務A
 +
責務B
 +
責務C
 ↓
Scenario
 ↓
接続結果確認
```

定義:

> CT = 品質保証済みの責務を接続した際の保証確認

CTでは、
UTで確認済みの内部保証をすべて再確認するのではなく、

```text
責務同士を接続したことによって発生する差分
```

を中心に確認する。

---

# 10. Incidentとの関係

テストをIncident配下の一時成果物にはしない。

```text
Incident
    ↓
責務 / Guaranteeの変更
    ↓
Test資産の追加・更新
```

Incidentは、

```text
なぜこのテストが生まれたのか
```

を示す履歴・理由として扱う。

Testは、

```text
現在の品質を保証し続ける恒久資産
```

として扱う。

したがって、

```text
Incident = Test変更の起点・理由

Test = 現在のResponsibility / Guaranteeに所属する品質資産
```

とする。

Test側から必要に応じて、

```text
origin_incident_id
```

等で起点Incidentへ戻れるようにする。

---

# 11. ResponsibilityとTestの関係

責務JSONの配下へ、
FieldDef等のDefinitionを物理的にネストしない。

各資産は独立して管理し、
Relationによって接続する。

```text
FieldDef
ViewDef
ValidationDef

Responsibility
Guarantee

TestPattern
Expected
Result

        ↓

Relationで接続
```

例:

```text
Responsibility
    ── uses ──> FieldDef

Guarantee
    ── verified_by ──> TestPattern
```

これにより、

```text
Field変更
    ↓
関連Responsibility
    ↓
関連Guarantee
    ↓
関連Test
```

という影響追跡を可能にする。

---

# 12. ResponsibilityのL1とTest

責務は、実装ファイルや画面部品ではなく、

```text
何を保証する責務か
```

で切る。

現時点のL1候補例:

```text
リソース探索・取得
Definition解決
画面表示
検索・抽出
派生情報生成
編集・状態変更
Validation
永続化・RoundTrip
出力・Projection
比較・観測
拡張・Overlay
デスクトップHost連携
```

L1は責務領域を示す。

実際のResponsibility Test対象は、
その下の品質保証上意味のあるResponsibility単位とする。

例:

```text
L1: 画面表示

  Grid列生成
  詳細フォーム表示
  子Grid表示
  検索フォーム表示
  ...
```

物理JSONを親子構造にする必要はなく、

```json
{
  "responsibility_cd": "grid_column_build",
  "responsibility_domain": "screen_display"
}
```

のようなRelationでよい。

---

# 13. 実行基盤について

Windows Forms / WebView2 / AP Server等は、
原則としてTest分類そのものにはしない。

これらは、

```text
責務をどこで、どの技術方式で実装するか
```

という実行基盤・配置の問題として扱う。

例:

```text
デスクトップHost連携責務
    ↓
現在の実装方式候補
Windows Forms + WebView2
```

責務名には可能な限り技術方式を埋め込まない。

# 15. 現時点の重要原則

1. Definitionから導出できるテストは、人間に書かせない。

2. DefinitionからExpectedを導出できる場合、
   Expectedを人間に二重入力させない。

3. TestPatternは必須資産ではない。

4. TestPatternは、
   「検証する実行経路を明示する必要がある場合」に使用する。

5. UTはコード量ではなく責務単位で切る。

6. CTは、品質保証済み責務の接続を確認する。

7. IncidentはTestの所有者ではない。
   Incidentを起点としてTest資産が進化する。

8. Responsibility / Definition / Testは独立資産として管理し、
   Relationで接続する。

9. 実装技術と責務を混ぜない。

10. 人間が判断する対象を可能な限り小さくする。

# 17. 現時点の要約

FRB Studioのテスト体系は、

```text
Definitionを検証する
責務を検証する
責務の接続を検証する
```

という3層を基本とする。

そして、

```text
Definitionから導出できるもの
    → 機械へ渡す

責務単独の保証
    → UT

人間が経路を選ぶ必要があるもの
    → TestPattern

複数責務を接続したもの
    → CT

結果
    → Expected / Actual / Diff

最後
    → Human Approval
```

という構造を目指す。

目的はテストケースを増やすことではない。

**人間が判断しなければならないテスト定義と、
人間が確認しなければならない差分を最小化することである。**

```

これ、今の段階の**議論用v0.1としてはかなり良い外枠**になったと思う。

特に今回の整理で核になったのは、たぶんこの3本やね。

> **Definition Driven = 定義から機械が検証を導出する**  
> **Responsibility Test = 1責務の保証をUTする**  
> **Scenario Test = 保証済み責務を接続してCTする**

そして横串として、

> **実行経路を人間が選ばなければならないときだけTestPatternを持つ。**

ここは今後のテスト設計をかなり左右する判断軸になりそう。 
```
