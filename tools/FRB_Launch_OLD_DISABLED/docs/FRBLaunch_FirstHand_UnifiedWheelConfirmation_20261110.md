# FRB Launch｜一の手 1〜4件共通化＋同一ボタンぐりぐり確認

**起点**：ユーザー添付 `launch_app_20261110_200820.zip`（20:08版）

## 今回の承認対象

誤ったQt Releaseで即実行される症状に対し、10:38版の正常神話を廃棄。
一の手の選択モデルを1〜4件で統一し、**候補選択と実行の間に独立した確認ゲート**を設けた。

### 操作手順（手裏剣 一の手ボタンからマウスを移動しなくてよい）

1. **一の手ボタンを押す** → ポケモンボール風UIの中心に目玉。
2. 押したまま上下左右等へ動かす → 登録件数に応じた対象へ目玉が移動。
3. **中央へ戻して離す** → 候補なし、実行なし。
4. 対象を選択した状態で離す、または異常なReleaseが紛れ込む → **実行はしない**。
   ポケモンボール風UIは表示したまま、同じプレビュー内に「実行候補：○○／キャンセル・OK」を表示。
   目玉の対象IDと確認候補IDは同一（不一致ならエラー）。
5. **一の手ボタンの上でホイールを回す**：下で `OK（実行）`、上で `キャンセル`。
6. **同じ一の手ボタンを新しくクリックして確定**：OKのときだけ当該機能を実行。
   ホイールを一度も操作していない場合と、キャンセル選択中の場合は常にキャンセル。

### 共通配置

- 1件＝上
- 2件＝左・右
- 3件＝左上・右上・下
- 4件＝上・右・下・左
- 5件目以降＝一の手では表示しない（設定は残す）

優先順 `shuriken_order` の昇順で割当。旧 `shuriken_direction` は一の手で無視。
Studioへ方向選択を追加しない。Remoteの別のExp/List selectorの既存仕様は維持。

## 安全性

- 最初のフリックReleaseでは `SHURIKEN_ITEM:` シグナルを発行しない。
- 確認候補の目玉は選択中の同一 `ShurikenEntry` オブジェクトを保持し、Release時の再判定はしない。
- 確認中のマウス移動・単独Releaseでは候補と目玉を変えない。
- 確認ホイールは **一の手ボタン側で消費**し、通常のFilesナビゲーションへ流さない。
- OK判定条件：`wheel_selected=True` かつ `choice=ok` かつ別のPress→Release（ボタン内）。
- Cancel時／確認中のボタン非表示時／別のLaunchダイアログ登場時は誤実行しない。
- 間違ったReleaseの発生自体やプレビューのちらつきは今回は根絶していない。**誤実行をゲートで止める**修正。

## 変更ファイル

- `src/first_hand_variable.py`：1〜4件の共通方向カタログと選択ルール。
- `src/shuriken_model.py`：4件だけの10:38互換分岐を廃止し、全件数で共通化。
- `src/first_hand_confirmation.py`：キャンセル初期値の純粋な確認状態モデル（新規）。
- `src/remote_shuriken.py`：プレビューを消さずに確認表示／一の手ボタン内のホイール＋クリック確定。
- `tests/`：新規確認テストと旧即時実行前提の既存テストの更新。

**設定JSONとViewDefは一切変更しない。** 添付20:08版では一の手の有効登録は2件。テストは設定を上書きせず、1〜4件の模擬データを組み立てて実施。

## テスト・残課題

- 重視する確認：初回Releaseは無実行／ホイールでCancel・OK／再クリックで1回だけ実行／候補と目玉ID一致／1〜4件選択／押下中のゴーストRelease。
- 実機Windows/PySide6のマウス捕捉や描画はこの環境では検証していない。
- プレビューのちらつき、異常なQt Releaseイベントが生じる根本原因は別課題。
