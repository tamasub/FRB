# FRB Launch 一の手｜確認ダイアログを応答完了まで保持（2026-11-10）

## 変更起点

ユーザー提供の `launch_app_20261110_204431.zip`（20:44版）。ユーザー設定JSON・Studio定義は変更しない。

## 実機で観測された問題

手裏剣一の手で候補を選ぶと、ポケモンボール風UI上にキャンセル／OK確認が出る。ぐりぐりは動くようになったが、**応答前に確認画面がときどき消える**。誤Releaseを避けるための二段階確認が途中で失われ、ユーザーはOK/Cancelを選べない。

## コードから確認された消失経路

- `ShurikenButton.hideEvent` が、一時的な非表示でも確認状態を無条件破棄していた。
- Launch の非アクティブ化／Windowsネイティブの外側クリック監視が Remote / Launch を閉じ得る。別の `Qt.Tool` に表示された確認ボタンのクリックは、元のRemoteの外側として扱われる可能性がある。
- `LaunchRemote.sync_window_mode` の `setWindowFlags()` はウィンドウを一度隠して再表示することがある。
- ホイール選択のたびに確認ボタン用ウィンドウの `.move()` / `.raise_()` が走っていた。
- `BACK` / `DOUBLE_CLICK` や別のLaunchダイアログが現れた場合にも、確認を終了する処理があった。

これらはコード上の消失経路・原因候補であり、Windows実機でどれが実際に起きたかは未確定。

## 修正した契約

1. 一の手で候補を確定して確認UIが出た時点から、**明示的なOKまたはCancel（ESC含む）応答まで**、候補の状態を保持する。
2. ボタン／プレビューの一時的な `Hide` で、確認待ち状態を消さない。
3. 確認中の自動外側クリック／非アクティブ化による Launch/Remote の非表示を抑止する。確認中のウィンドウフラグ再設定は延期する。
4. OS側でプレビューやボタンだけが非表示になった場合、100ms間隔で確認して、**同じ候補・同じ目玉・同じOK/Cancel選択**で表示を復旧する（入力イベントや実行は生成しない）。
5. ホイールでの候補変更はすでに表示されている確認ウィンドウを再移動・再浮上させず、色だけ更新する。
6. 未知のRemoteコマンド、重複Release、ボタン外でのRelease、他のダイアログ表示で確認を消さない。
7. 目玉の候補IDと実行IDが一致しない場合、**実行も終了もしない**。確認状態を保持し診断ログへ記録する。
8. ユーザーが明示的にOKを選んだときだけ実行。Cancelでは実行せず閉じる。アプリそのものの終了操作だけは例外で閉じられる。

## 非変更箇所とテスト

- 1〜4件の共通方向判定・目玉座標・形状・ガイドサイズ・設定JSONは変更なし。
- 通常のぐりぐりExp/List操作は、確認状態がないときは変更なし。
- 新規テスト9件を追加し、古い「別ダイアログなら確認を破棄する」というテスト1件を新契約に更新。
- 重点＋周辺テスト：**203 PASS / 10 FAIL**。同じテスト範囲の元の20:44版：**194 PASS / 同じ10 FAIL**。新規失敗なし。旧レイアウトや不完全なスタブなど元からの10件は未修正。
- Windows 11/PySide6によるネイティブ表示試験はこの環境では未実施。特に、Qt.Toolの実際のウィンドウ非表示イベントとWindowsの前面制御は実機で確認する必要がある。

## 実機での確認順序

1. 4件メニューで上に移動して離し、確認UIを表示する。
2. ぐりぐりでキャンセル／OKを何度も往復させても、UIが消えずExpに入力が漏れない。
3. 背景・確認UI・一の手ボタンをクリックするなど、OK/Cancel以外の操作でも確認が勝手に閉じない。
4. 明示的なCancelでは実行せず閉じる。明示的なOKでは目玉の候補を1回だけ実行する。
5. もし表示がちらついたら、上記診断ログから `*_hidden` → `*_restore` の発生時刻を照合する。
