更新日: 2026-07-11

ステータス: Draft / 検証前提

## 0. まず大前提

これは売買推奨ルールではない。

```text
過去チャート上で
自分が何を見ていたのかを再現し、
Entry / Hold / Close / Reset / NoTrade を
自動シミュレーション可能な形に分解する
```

ための仮説仕様である。

今回の整理で、HSIルールは単なるEntry条件ではなく、

```text
今どの状態かを分類し、
Expansionとして扱ってよい波かを格付けし、
Entryしてよい局面かを段階的に判断する
```

状態遷移ルールとして扱う。

---

v0.4では、Entry条件だけでなく、Entry後のポジション管理を明示的に分離した。

```text
Entry時に管理時間足を固定する。
上位足の波へ接続した場合だけ管理時間足を昇格できる。
利益確定を検討する時間足と、実際に降りるトリガー時間足を分ける。
```

v0.5では、さらに **Entry Rule と Close / Position Management Ruleを分離**する。

```text
どこで入るか
≠
入った建玉をどう閉じるか
```

現時点のSimulationでは、通常M5 Entryと将来のExpansion Entryの両方に対して、
共通のScale-out仮説を適用して検証する。

```text
1 Entry
= 1 Trade Lifecycle

1 Trade Lifecycle
= 1回以上のClose Executionを持ちうる
```

つまり、1回のEntryに対して、

```text
Partial Close
Partial Close
Full Close
```

のように複数回のCloseが発生しても、別Tradeではなく同一Tradeの建玉管理として扱う。

ただし、これは確定ルールではない。

```text
Single Close
vs
Scale-out
```

のどちらが通常M5 Entryに適しているかを、今後Simulation結果で比較するための仮説である。

v0.6では、通常M5 Entryの入口条件をExpansion Entryから明確に分離する。

```text
通常M5 Entry
= H4 T3方向
+ H1 / M5 Dow一致
+ H4 / H1 Cycle Late除外
+ 確定済みHSI起点からR2到達
```

H4 Dow、WEEK、DAY、Expansion Confirmedは、通常M5 Entryの必須条件にしない。

今回の目的は、完成された勝ちルールを先に作ることではない。

```text
まずEntry候補を出す
↓
チャート上で違和感を見つける
↓
「なぜここでEntryするのか」を検証する
↓
Entry条件を育てる
```

つまり、Entry回数そのものを品質とはみなさないが、
検証体験を成立させるための観測目安として、
**1営業日あたり約1回**を暫定的なEntry頻度目標に置く。

## 1. 時間足の役割

### WEEK = Expansion Season / Macro Context / 高値づかみ防止ガード

WEEKは通常M5 Entryの必須条件には使わない。

WEEKの役割は、Expansion Entryを探してよい季節かを判断すること。

```text
WEEK = Expansion Entryを探してよい季節かを見る足
WEEK = 大きな方向とサイクル位置を見る足
WEEK = 高値づかみ回避のためのSeason Filter
```

```text
WEEK Cycle Early / Middle
→ Expansion Entry候補を検討してよい

WEEK Cycle Late
→ 新規Expansion Entry禁止
→ Expansion ReEntry禁止
→ Expansion Add-on禁止
→ 既存ポジションのH1早期Closeトリガーを許可
```

WEEK自体を直接のClose判定足にはしない。

---

### DAY = UpperMap / Expansion格付け / 管理時間足の上限

DAYも通常M5 Entryの必須条件には使わない。

DAYの役割は、H4で見えているExpansion候補が、
日足スケールでも意味のある波なのかを確認すること。

```text
DAY = 上位地図
DAY = Expansion誤判定防止フィルター
DAY = 大きな山谷・調整タイミングを見る足
DAY = Position Management Timeframeの昇格上限
```

DAYの赤丸・緑丸は、通常M5 Entry材料ではなく、
H4 Expansion候補を日足スケールで格付けするための大局材料点である。

---

### H4 = Normal方向許可 / Expansion判断 / 利益確定判断

通常M5 Entryでは、H4 Dowを使わない。

H4はT3だけを使って、大きな方向を許可する。

```text
Long方向許可:
  最新確定H4 T3 > 1本前の確定H4 T3
  AND 最新確定H4 Close > 最新確定H4 T3

Short方向許可:
  最新確定H4 T3 < 1本前の確定H4 T3
  AND 最新確定H4 Close < 最新確定H4 T3

それ以外:
  H4方向未確定
  → 通常M5 Entry不可
```

H4 Dowは画面上の観測情報として残してよいが、
通常M5 Entryの許可・禁止には使用しない。

```text
H4 Dow confirmed
≠ 通常M5 Entry条件
```

一方、Expansion Entryでは引き続き、
H4構造・BB・Cycle・HSIを使って大波を判断する。

また、H4 Cycle Lateの場合は、
通常Entry / ReEntry / Add-onを含む新規建玉を禁止する。

Expansion保有中の利益確定は、H4で大きく判断する。

```text
H4 Cycle Late
+ H4 BB ContractingToMA
+ HSI Confluence
→ Profit Take Armed / 利益確定準備
```

---

### H1 = Dow方向確認 / Cycle Guard / Exit Trigger

通常M5 Entryでは、H1 Dowを中間トレンド確認に使う。

```text
Long候補:
  H1 Dow Trend = UP

Short候補:
  H1 Dow Trend = DOWN
```

H1 DowとM5 Dowが同じ方向になった場合だけEntry候補とする。

```text
H1 UP   + M5 UP   → Long候補
H1 DOWN + M5 DOWN → Short候補

不一致 / REVERSAL_WATCH / NO_TREND / UNDETERMINED
→ 通常M5 Entryなし
```

H1 Cycle Lateの場合は、新規Entry / ReEntry / Add-onを禁止する。

Expansionの利益確定準備がONになった後は、
H1を実際に降りるClose Triggerとして使う。

```text
Profit Take Armed
AND H1 Structure Break / Rebound Failure
→ Close候補
```

---

### M5 = Dow実行トリガー / Entry・Close実行

M5はEntry / ReEntry / Add-on / Partial Close / Full Closeの実行足。

通常M5 Entryでは、M5 DowがH1 Dowと一致していることを必須とする。

```text
H4 T3で方向許可
↓
H4 / H1 Cycle Lateではない
↓
H1 Dow方向確認
↓
M5 DowがH1と同方向
↓
確定済みHSI起点からR2到達
↓
Entry
```

M5単独ではEntryしない。

---

### 時間足の役割まとめ

```text
WEEK = Expansionの季節 / 通常Entryには使わない
DAY  = Expansion格付け / 通常Entryには使わない
H4   = T3による通常Entry方向許可 / Cycle Guard / Expansion判断
H1   = Dow方向確認 / Cycle Guard / Close Trigger
M5   = Dow実行トリガー / Entry・Close実行
```

### 通常EntryとExpansion Entryの責務分離

```text
通常M5 Entry:
  H4 T3
  + H1 Dow
  + M5 Dow
  + H4/H1 Cycle Guard
  + HSI R2

Expansion Entry:
  WEEK Season
  + DAY Grade
  + H4 Structure / BB / Cycle
  + H1 Permission
  + M5 Trigger
```

## 2. DataSource / 画面構成

M5だけからH1/H4/DAY/WEEKをすべて内部生成すると、表示期間と大局判断に限界がある。
そのため、最小構成として以下を採用する。

```text
Primary DataSource = M5
UpperMap DataSource = DAY / D1
WEEK Context        = 外部DAYデータを週足へ集約
```

現時点の画面構成。

```text
Expansion検討モード:
左     H4 main review       = M5から内部生成
右上   DAY UpperMap          = 外部D1 JSONを直接参照
右下   WEEK expansion context = 外部D1 JSONから週足集約

M5実行モード:
左     M5 entry observation
右上   H1 context
右下   H4 macro context
```

重要な責務分離。

```text
D1 Data JSON
= 差し替え可能な相場データ

plugin.json
= DAY/WEEK Confirm bars、marker policy、表示期間などUI設定の正本

chart_comments.json
= HSI / コメント / 保存縦線 / サイクル線など、注釈系データの正本

URL
= 画面を開くためのView状態
```

WEEK Confirm barsはDAY Confirm barsと独立してplugin.jsonで手動調整する。
WEEK窓では大局確認を優先し、保存済み通常縦線・サイクル縦線は表示しない。

HSI系URLパラメータはLegacy扱い。  
保存済みHSIはchart_comments.jsonを正本とし、URLコピーでは基本的にHSIを正本化しない。

## 3. HSI起点の絶対ルール

Entryに使うR判定は、必ず確定済みHSI起点から計算する。

```text
Entryに使うR2 / R3.5 / R4 は、
必ず「確定済みHSI起点」から計算する
```

未確定の赤丸候補からR2を引いてEntryすると、後からその起点が否定された瞬間にEntry根拠が消える。

起点は3段階に分ける。

```text
Candidate basis
= 候補。まだEntry計算には使わない。

Confirmed basis
= 確定済み。HSI起点候補として使える。

Adopted HSI basis
= 今回の波の基準点として採用済み。
```

Entry判定に使えるのはConfirmed以降。

## 4. Position Management Timeframe

すべてのEntryは、Entry時点で「どの時間足の構造が壊れたら処分を検討するか」を固定する。

```text
Entry Timeframe
= 実際にEntryを実行した時間足

Management Timeframe
= ポジションの保有根拠と処分判断を管理する時間足

Exit Trigger Timeframe
= Management Timeframeが処分準備に入った後、実際に降りる契機を見る時間足

Direction Context Timeframe
= 売買方向や季節を参照する上位足
```

同じ価格・同じ方向のEntryでも、管理時間足が違えば別のポジションとして扱う。

```text
Entry A = H1管理
Entry B = H4管理
Entry C = DAY管理
```

### 管理時間足昇格

Entry後に上位足の波へ接続した場合だけ、Management Timeframeを昇格できる。

```text
M5 → H1 → H4 → DAY
```

昇格上限はDAY。
WEEKはDirection Context / Season Filterであり、Management Timeframeにはしない。

昇格条件候補。

```text
- 上位足の方向が一致している
- 上位足の構造が確定している
- ポジションが含み益である
- 昇格後の新しい無効化条件を定義できる
- 損失回避を理由とした昇格ではない
```

禁止事項。

```text
含み損になった
→ M5では切らずH1で見る
→ H1でも切らずH4で見る
```

という損切り先延ばしは禁止。

### Exit Triggerの下位足化

Management TimeframeはH4/DAYのままでも、利益確定準備後のExit TriggerはH1へ下げてよい。
これは管理時間足の降格ではなく、逃げ遅れを防ぐための実行トリガー分離である。

```text
Management Timeframe = H4 or DAY
Profit Take Decision  = H4
Exit Trigger Timeframe = H1
Execution Timeframe    = M5
```

## 5. NoTrade / Watch を先に判定する

Entry判定では、通常M5 EntryとExpansion EntryのNoTrade条件を分ける。

### 5.1 通常M5 EntryのNoTrade

```text
1. H4 T3方向が未確定
2. H4 T3方向とH1 Dow方向が不一致
3. H1 DowとM5 Dowが不一致
4. H1 DowがREVERSAL_WATCH / NO_TREND / UNDETERMINED
5. M5 DowがREVERSAL_WATCH / NO_TREND / UNDETERMINED
6. H4 Cycle = LATE
7. H1 Cycle = LATE
8. 確定済みHSI起点がない
9. 確定済みHSI起点からR2未到達
10. すでにTrade中
11. future data insufficient / 検証不能
```

通常M5 Entryでは、以下をNoTrade条件にしない。

```text
- H4 Dow Trend
- WEEK Cycle
- DAY Cycle
- Expansion Confirmed
- H4 BB Opening
- DAY Expansion Grade
```

### 5.2 Expansion EntryのNoTrade

Expansion Entryでは、従来どおり上位足を厳しく扱う。

```text
1. WEEK Expansion Season = CLOSED
2. DAY Expansion Age = 60本超
3. H4 Trend / Structureが未確定
4. H4 Cycle = LATE
5. H1 Cycle = LATE
6. PostExpansion PullbackWindow中
7. Expansion Confirmed未成立
8. すでにTrade中
9. future data insufficient / 検証不能
```

### 5.3 Entry判定順序

```text
第0関門: Entry Modeを選ぶ
第1関門: Cycle Lateではないか
第2関門: 方向条件が一致しているか
第3関門: 確定済みHSI起点があるか
第4関門: R2へ到達しているか
第5関門: 建玉状態がEntry可能か
第6関門: Stop / Targetが表示・記録可能か
```

## 6. Entryモード整理

現時点では、Entryモードはこの5種類に分ける。

```text
A. Normal Trend Entry
B. ReEntry / Add-on Entry
C. Expansion Pullback Entry
D. Pre-Expansion R3.5 Breakout Entry
E. Post-Expansion Reverse Entry
```

---

---

## A. Normal Trend Entry

v0.6の通常M5 Entryは、H4 Dowを使わず、
H4 T3・H1 Dow・M5 Dowを中心に判定する。

### Long Entry

```text
H4 Direction Permission:
  最新確定H4 T3 > 1本前の確定H4 T3
  AND 最新確定H4 Close > 最新確定H4 T3

H1 Direction:
  H1 Dow Trend = UP

M5 Trigger:
  M5 Dow Trend = UP

Cycle Guard:
  H4 Cycle != LATE
  AND H1 Cycle != LATE

HSI:
  確定済みUP方向HSI起点あり
  AND 起点からR2以上

Position:
  新規Entry可能な建玉状態
```

### Short Entry

```text
H4 Direction Permission:
  最新確定H4 T3 < 1本前の確定H4 T3
  AND 最新確定H4 Close < 最新確定H4 T3

H1 Direction:
  H1 Dow Trend = DOWN

M5 Trigger:
  M5 Dow Trend = DOWN

Cycle Guard:
  H4 Cycle != LATE
  AND H1 Cycle != LATE

HSI:
  確定済みDOWN方向HSI起点あり
  AND 起点からR2以上

Position:
  新規Entry可能な建玉状態
```

### 明示的に使わない条件

通常M5 Entryでは、以下を必須条件にしない。

```text
H4 Dow Trend
WEEK Expansion Season
DAY Expansion Grade
Expansion Confirmed
H4構造ブレイク
H4 BB Opening
```

H4 Dowは観測対象として残してよいが、
通常Entry判定ロジックには接続しない。

### Cycle Guard

```text
H4 Cycle EARLY / MIDDLE → Entry可
H4 Cycle LATE           → Entry不可

H1 Cycle EARLY / MIDDLE → Entry可
H1 Cycle LATE           → Entry不可
```

CycleがUNDETERMINEDの場合は、初期版ではEntry不可として扱う。
Entry頻度が少なすぎる場合は、UNDETERMINEDの扱いを次の緩和候補とする。

### HSI First Target / Close Policy

Entry位置が属するHSIエリアの次境界を、
First Profit Targetとして扱う。

```text
R2〜R2.5   → First Target = R2.5
R2.5〜R3   → First Target = R3
R3〜R3.5   → First Target = R3.5
R3.5〜R4   → First Target = R4
R4〜R4.5   → First Target = R4.5
```

Close PolicyはEntry条件から分離する。

```text
COMMON_SCALE_OUT:
  First Target到達でCoreを一部決済
  残りは次のHSI境界へTarget更新

SINGLE_CLOSE:
  First Target到達で全決済
```

現時点では `COMMON_SCALE_OUT` を暫定defaultとする。

### 検証上のEntry頻度目安

```text
0.5回未満 / 営業日
→ 条件が厳しすぎる可能性

0.5〜1.5回 / 営業日
→ 違和感を回収しやすい観測帯

1.5回超 / 営業日
→ 条件が緩すぎる可能性
```

これは利益性能の評価値ではない。
人間がEntry地点を見てルールを育てられるか、という検証体験の目安である。

## B. ReEntry / Add-on Entry

通常ReEntry / 通常Add-onにも、v0.6の共通Entry Gateを適用する。

```text
H4 T3方向許可
AND H1 DowとM5 Dowが一致
AND H4 Cycle != LATE
AND H1 Cycle != LATE
AND 確定済みHSI起点からR2以上
```

Expansion ReEntry / Expansion Add-onは、これに加えてExpansion固有条件を要求する。

CloseOK後もH1/H4文脈が継続しているなら、HSI起点は消さない。  
HSIは1回のTradeではなく、上位足トレンド単位で維持する。

```text
ReEntry条件

前TradeがCloseOK
AND HSI起点は維持中
AND H4 T3方向許可が継続
AND H1 DowとM5 Dowが同方向
AND H4/H1 CycleがLATEではない
AND Entry位置が次のHSIエリア内
```

Add-onは通常M5理論でよい。  
ただし、Expansion方向と同じ方向だけ。

```text
Add-on Allowed =
  Core position が含み益
  AND H4 Expansion方向と同じ
  AND H4 Cycle Phase が Early or Middle
  AND 新しい確定済み押し目/戻り目 basis がある
  AND そのbasisからR2到達
  AND M5 Dow confirmed
```

Add-on禁止条件。

```text
H4 Cycle Late
OR WEEK Cycle Late
OR BBが閉じ始め
OR H1高値更新失敗
OR 価格がMA/T3へ戻り始め
OR Coreが含み損
```

合言葉。

```text
買い増しはナンピンではない。
勝っている波にだけ追加する。
```

---

WEEK Cycle Lateでは、Expansion方向が継続して見えていても、新規ReEntry / Add-onを禁止する。
目的は取り逃し回避ではなく、高値づかみ回避を優先するため。

## C. Expansion Pullback Entry

H4でR4級のExpansionが出ても、そこで即Entryしない。

```text
R4到達 = Entryではない
R4到達 = Expansion Watch / 例外アラート
```

R4到達後に押しを待つ。

```text
Expansion Detection Anchor
= Expansion判定用の大起点

Expansion Entry Anchor
= R4到達後の直近押し安値/戻り高値

Entry Trigger Anchor
= 実際にR2判定する確定済み押し目起点
```

④→⑤→⑯パターンなら、

```text
④ = Expansion Detection Anchor
⑤ = Pullback / Entry Trigger Anchor
⑯ = ⑤起点R2 + M5 Dow Up confirmed
```

ただし、勝負している波は⑤ではなく④。

```text
Entry判定  = ⑤起点R2
Hold判定   = ④起点Expansion文脈
Target判定 = ④起点R5以上
```

Stopも2層に分ける。

```text
構造Stop:
  ⑤ Pullback Anchor 割れ

大波Stop / Thesis Stop:
  ④ Expansion Anchor 文脈崩壊
```

Expansion Entryでは、通常CloseOKをそのまま使わない。  
リスクが広がるため、CloseOK候補がRiskに見合わないならEntryしない。

```text
minimum target  = ④起点R5
extended target = ④起点R5.5 / R6 / R6.5
```

## 7. Expansion候補の再定義

今回の整理で、Expansionは距離だけでは判定しないことが明確になった。

```text
Expansionは値幅だけでは判定しない。
DAYサイクル年齢で格付けする。
```

また、R4到達だけでExpansion候補にするのは弱い。

```text
R4到達はアラート
構造ブレイクで候補
押し戻り成功でEntry検討
DAY足で格付け
```

### Expansion Watch

```text
Expansion Watch
= 確定済み起点からR4以上に到達した状態
```

これはまだ候補ではなく、観察対象入り。

### Expansion Candidate

```text
Expansion Candidate
= R4到達
  AND H4構造ブレイク
  AND H4 BB Opening / ボラ拡大
```

H4構造ブレイク例。

```text
直近H4高値/安値を明確に抜いた
下降/上昇トレンドラインを明確に抜いた
レンジ上限/下限を抜いた
MA20/T3をまたいで反対側に定着した
BB外側に沿って走り始めた
```

### Expansion Grade

DAYで格付けする。

```text
これはH4だけの小爆発か？
それとも日足構造を変えに来ている爆発か？
```

を見る。

### Expansion Confirmed

```text
Expansion Confirmed
= Expansion Candidate
  AND 押し/戻りを作った
  AND 押し戻り後に再度継続方向へ動いた
  AND H1/H4文脈が崩れていない
```

### Expansion Invalid

```text
Expansion Invalid
= R4到達後、構造ブレイクできずレンジ回帰
  OR MA20/T3下へ戻る
  OR BB Openingが続かない
  OR DAY格付けでLate Cycle扱い
```

## 8. DAY Expansion Age Rule

今回の最重要追加ルール。

DAY Confirm=45で見ると、1サイクルがおおむね90日級に見える。
つまり、日足安値から45本を超えた場所は、上昇波の前半ではなく後半・成熟期として扱う必要がある。

Long Expansionの場合。

```text
DAY basis = 直近の日足Active Low
day_cycle_age = 現在足 - DAY basis足
```

Short Expansionの場合。

```text
DAY basis = 直近の日足Active High
day_cycle_age = 現在足 - DAY basis足
```

判定。

```text
45本以内:
  Expansion候補として見てよい

45本超え:
  だいぶ怪しい
  Expansion Grade Down / 要警戒

60本超え:
  Expansion扱いしない
  Late Cycle / 調整待ち扱い
```

これはEntry禁止ルールではなく、Expansion判定の格付けルール。

```text
45本超えだから絶対NoTrade
```

ではなく、

```text
45本超えだから、それをExpansionとして扱うのは怪しい
```

という整理。

60本超えたら、もうExpansionではない。

```text
R4到達 / H4で勢いあり
  ↓
でもDAY安値から何本経っている？
  ↓
45本以内ならExpansion候補
45本超えならLate寄り
60本超えならExpansion却下
```

### 22×2意識

```text
22営業日 ≒ 1か月
45営業日 ≒ 約2か月
```

日足で大きな山谷を見るなら、1か月単位より少し長め、つまり2か月級の確認幅が自然。

```text
DAY Confirm 45
= 日足の短期ノイズを捨てて、
  約2か月級の大きな山谷だけを材料点として見る設定
```

### DAYの右端解釈

DAY右端で、緑丸が立ったあとに価格がT3/MA20から浮き、BB上限側に寄っている場合、

```text
上昇は継続している
でも、もうすぐ調整下げが来そう
```

という絵に見える。

この感覚を可視化するために、DAY Confirm=45を暫定defaultとする。

## 9. WEEK Expansion Season / Late-Cycle Entry Guard

WEEKの季節判定は難しいため、初期版では「大波を最大限取る」より「Expansion Entry可能期間を短くする」方向へ倒す。

目的。

```text

```

初期状態は、まず2状態で扱う。

```text

= Expansion Entry候補を検討してよい

= 新規Expansion Entry禁止
= Expansion ReEntry禁止
= Expansion Add-on禁止
= 既存ポジションのH1早期Close Trigger許可
```

将来的にはTransitionを追加してもよい。

```text

TRANSITION
EXIT_PERMISSION
```

### WEEK Cycle Lateの効果

```text
WEEK Cycle Late = true

Expansion Entry Allowed  = false
Expansion ReEntry Allowed = false
Expansion Add-on Allowed  = false
WEEK Direct Close         = false
H1 Early Exit Trigger     = true
```

重要。

```text
WEEK Cycle Late
≠ 即Close
```

WEEKは「もう新しく乗る季節ではない」「H1で崩れたら早めに降りてよい」という許可を出す。
実際のCloseはH1以下で判断する。

### Late判定の初期候補

最初から完全なCycle判定を目指さない。
次のような終盤要素が増えたら、保守的にCLOSEDへ倒す。

```text
- WEEK起点からの経過バー数が上限を超えた
- WEEKの高値更新 / 安値更新が鈍化した
- WEEK BBの拡大が止まり、収縮へ向かった
- WEEK MA20 / T3の傾きが鈍化した
- WEEKでミニサイクルを複数消化した
- 長期トレンドライン突破後でも、次の週足押し目時期が接近している
```

初期実装では、経過バー数など単純な条件から始め、後からOPEN期間を延長する方向で調整する。

## 15. Close / Profit-Take Architecture

Closeは、Entry Modeと分離して管理する。

```text
Entry Mode
= Normal / ReEntry / Add-on / Expansion / Reverse

Close Policy
= Single Close / Scale-out / Structure Exit / Stop
```

現時点では、通常M5 Entryと将来のExpansion Entryの両方に、
共通Scale-out仮説を適用してSimulationする。

これは、

```text
Expansionだから分割利確する
```

という意味ではない。

```text
M5で細かくEntryした建玉でも、
最初のHSI Targetで一部利益を確保し、
残りを上位足の波へ接続できるか検証する
```

ための共通建玉管理仮説である。

### 15.1 共通Scale-out仮説

現時点の暫定default。

```text
initial_units       = 10
core_units          = 9
runner_units        = 1
partial_close_units = 2
```

基本Lifecycle。

```text
Entry
↓
First HSI Target到達
→ Coreを2単位Partial Close
↓
次のHSI Target到達
→ Coreをさらに2単位Partial Close
↓
構造離脱 / Full Close Trigger
→ 残りCore + RunnerをFull Close
```

最初のCloseで全部閉じない理由は、
その時点の相場から毎回動的に導出しているわけではない。

現時点では、次の仮説を検証するために固定している。

```text
- 最初のTargetで利益を確保する
- 残り建玉で次のHSI境界を狙う
- 全決済後のReEntry乱発を減らす
- M5 Entryを上位足の波へ接続できる可能性を残す
```

したがって、現在のPartial Closeは、

```text
強い相場だから残した
```

という判断ではなく、

```text
COMMON_SCALE_OUTポリシーを選択しているため残した
```

という意味。

この仮説が効率的かどうかは未確定であり、Single Closeとの比較対象とする。

### 15.2 Single Close比較候補

比較用の対照ルール。

```text
Entry
↓
First HSI Target到達
↓
全建玉をCloseOK
```

用途。

```text
- 1 Entry / 1 Closeの素直な基準
- Scale-outによる利益増減の比較
- 保有時間、再Entry回数、最大逆行の比較
```

将来的には同一期間を、

```text
Close Policy A = SINGLE_CLOSE
Close Policy B = COMMON_SCALE_OUT
```

で再実行し、結果を比較する。

### 15.3 通常EntryとExpansion Entryの違い

通常EntryとExpansion Entryで共通化するのは、
現時点では **Scale-outという建玉管理方式**。

異なるのは、主に以下。

```text
- Entry成立条件
- Management Timeframe
- Hold根拠
- Target Anchor
- Stop / Thesis崩壊条件
- Exit Armed条件
```

つまり、

```text
Closeの分け方は共通化できる
しかし、どこまでHoldするかはEntry Modeごとに異なる
```

と整理する。

### 15.4 Expansionの利益確定準備

Expansionの処分は、「利益確定を検討する時間足」と「実際に降りる時間足」を分離する。

利益確定すべき大きな季節に入ったかはH4で判断する。

```text
H4 Cycle Late
AND H4 BB ContractingToMA
AND HSI Confluence Rank A
→ Profit Take Armed
```

H4で見る理由。

```text
- H1の小さな押しをExpansion終了と誤認しない
- BB収縮を大きな波の視点で判断する
- HSI到達度とサイクル成熟を同じ時間軸で見る
```

### 15.5 実際のClose Trigger

Profit Take Armed後は、H4足確定まで待って利益を削らないため、H1で実際の離脱契機を確認する。

H1 Close Trigger候補。

```text
- H1高値更新失敗 / 安値更新失敗
- H1確定押し安値 / 戻り高値のブレイク
- H1 Dow反転確定
- H1 MA20 / T3を割り、反発しても戻せない
- H1 Rebound Failure
```

```text
H4で「そろそろ刈り取る」と決める
↓
H1で「今、降りる」を決める
↓
M5でCloseを実行する
```

### 15.6 WEEK Lateによる処分前倒し

WEEK Cycle Lateでは、H4の完全な成熟シグナルを待つより、高値づかみ回避を優先する。

```text
WEEK Cycle Late
→ Expansion Entry Season CLOSED
→ Profit Protection Mode
→ H1 Early Exit Trigger Enabled
```

WEEKは直接Closeしない。
H1の崩れが出たときに、H4/DAYの確定を待たずClose可能とする。

### 15.7 Expansion中のHold原則

```text
WEEK Early / Middle
AND H4 BB Opening / Expansion
AND H4 Cycle Early / Middle
→ M5/H1の小崩れではCoreを降ろさない
```

### 15.8 Stop / Thesis崩壊

利益確定とは別に、Expansion Entryの無効化Stopは2層で管理する。

```text
構造Stop
= Pullback / Entry Trigger Anchor割れ
= Add-on / Tactical Positionの主な処分候補

大波Stop / Thesis Stop
= Expansion Detection Anchorの文脈崩壊
= Core Positionの主な処分候補
```

どの建玉をどちらのStopで処分するかは、Entry単位のManagement TimeframeとPosition Roleで管理する。

### 15.9 役割まとめ

```text
WEEK = Expansion Entry Season / Exit Permission
H4   = Profit Take Decision / Exit Armed
H1   = Actual Close Trigger
M5   = Partial Close / Full Close / Stop Close Execution
```

## 16. 建玉管理

### 16.1 共通Position Role

建玉は3種類に分ける。

```text
Core Position
= 主たる保有玉

Add-on Position
= ミニサイクルで追加する追撃玉

Runner
= 最後に残す夢玉
```

通常M5 EntryでもScale-outを使用する場合、
Core / Runner構造を持つ。

```text
通常Entry
≠
必ず1 Entry / 1 Close

通常Entry + COMMON_SCALE_OUT
= Coreを段階決済し、Runnerを残す
```

### 16.2 通常M5 EntryのScale-out例

Entry位置がR2〜R2.5にある場合。

```text
R2.5到達:
  Core 2単位 Partial Close
  次Target = R3

R3到達:
  Core 2単位 Partial Close
  次Target = R3.5

構造離脱:
  残りCore + Runner Full Close
```

HSI境界はEntry位置から順に進める。
固定でR4.5から始めるわけではない。

### 16.3 Expansion EntryのScale-out例

Expansion Entryでは、大起点のRレベルやConfluenceを使って、
通常Entryより大きなTargetを持つ。

たとえば10単位なら、

```text
R4.5到達:
  2単位利確
  目的 = リスク軽減 / 建値化準備

R5到達:
  2単位利確
  目的 = 最低目標回収

R5.5到達:
  2単位利確
  目的 = 中間ターゲット回収

R6 / R6.5 Confluence:
  3単位利確
  目的 = 本命利確

残り1単位:
  Runner
```

Add-on玉は小波で回収。  
Core玉は大波で回収。

```text
本玉は大波を見る。
追撃玉は小波で回収する。
```

### 16.4 Trade Lifecycle識別

1回のEntryから複数Closeが発生しても、
同じTrade IDに属する同一Tradeとして扱う。

```text
trade_0001
  ENTRY
  PARTIAL_CLOSE
  PARTIAL_CLOSE
  FULL_CLOSE
```

表示上も、今後は可能な限り以下を区別する。

```text
Entry
PartialClose
FullClose / CloseOK
StopClose / CloseMiss
```

### 16.5 Simulation記録契約

Run Profile JSONは、実行設定の正本。

```text
fx_simulation_run_profile_v0_1.json
```

ここに持つもの。

```text
- Entry / Close Policy設定
- Position sizing
- HSI level
- Management Timeframe policy
- Simulation engine有効設定
```

実行結果そのものは、Simulation Trace Sidecarへ記録する。

```text
fx_usdjpy_m5_t3_data_v0_1.simulation_trace.json
```

ここに持つもの。

```text
- Run Snapshot
- Trade ID / Position ID
- ENTRY / PARTIAL_CLOSE / FULL_CLOSE / STOP_CLOSE
- 実行時刻 / 価格 / 単位数
- 実行前後の建玉状態
- 判定理由 / Rule ID
- 次Target
```

つまり、

```text
Run Profile
= どうSimulationするか

Simulation Trace
= 実際に何が起きたか
```

を分離する。

### 16.6 建玉が持つ情報

各建玉には、少なくとも以下を持たせる。

```text

Trade ID
Entry Mode
Close Policy
Entry Timeframe
Direction Context Timeframe
Management Timeframe
Management Timeframe Promotion Cap
Exit Trigger Timeframe
Invalidation Rule
Position Role
Exit Policy
Promotion History
```

標準候補。

```text
Direction Context Timeframe = WEEK / DAY
Management Timeframe Promotion Cap = DAY
WEEKはManagement Timeframeに設定しない
```

## 20. 今日の結論

v0.6の最大変更は、通常M5 Entryの入口を
Expansion Entryの厳しい上位足条件から切り離したこと。

通常M5 Entryの暫定条件。

```text
H4 T3方向許可
+ H1 DowとM5 Dowの一致
+ H4 Cycle Lateではない
+ H1 Cycle Lateではない
+ 確定済みHSI起点からR2以上
```

明示的に使わないもの。

```text
H4 Dow
WEEK Expansion Season
DAY Expansion Grade
Expansion Confirmed
```

H4 Dowを外した理由は、
通常Entryの確定を待ちすぎてEntry候補がほとんど消えることを避けるため。

ただし、H4を無視するわけではない。

```text
H4 T3
= 大きな方向の許可証

H1 Dow
= 中間トレンド確認

M5 Dow
= Entry実行トリガー

H4 / H1 Cycle
= 後半Entry防止ガード
```

今回のルールは、まだ厳しい可能性がある。

それでもまずは、

```text
Entryが出る
↓
チャートを見る
↓
「えぇーー、なんでここでEntryするのぉーー？」
という違和感を回収する
↓
次のルールへ反映する
```

というSimulation本来の楽しさを成立させる。

暫定的な観測目安。

```text
約1 Entry / 営業日
```

これは勝率目標でも売買推奨でもない。
人間がEntry地点を十分な頻度で観察し、
ルールを育てられる状態を作るための検証目安である。

Close / Position Managementはv0.5を継続する。

```text
Close Policy default = COMMON_SCALE_OUT
Stop基準 = Entryに使用したHSI起点
損益・初期リスク・R換算をSimulation Traceへ記録
```
