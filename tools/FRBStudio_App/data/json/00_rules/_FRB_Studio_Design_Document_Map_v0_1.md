# FRB Studio 設計文書体系とファイル実態マップ v0.1

## 1. 概念と現在のファイル実態

| 概念 | 一言定義 | 概念上の軸 | 現在の主な実ファイル | 現在のファイル実態 | 現時点の整理 |
|---|---|---|---|---|---|
| 憲法 | 正しさと変更を統治する | 最上位の権威・適用範囲 | `data/json/00_rules/frb_coding_constraints_data_v0_3.json` | `document_type: studio_constitution_review`、タイトルは「Studioくん憲法 レビュー記録」。理念と恒久的なコーディング制約を同じ `rules[]` に保持する | 憲法の実体は存在する。ただし、憲法原則とアーキテクチャ制約が同居している |
| Foundation | 製品群の共通土台を定義する | 製品群共通の適用範囲 | `data/json/00_rules/frb_foundation_rules_data_v0_1.json` | Studio系ツール群に共通する命名、設定、Version、Incident、ルール管理、Markdown Exportなどの基本原則を23件の `rules[]` として保持する | Foundationの実体として妥当。共通土台に関する原則・ルールの正本 |
| 制約 | 越えてはいけない境界を示す | 文の役割・設計情報の種類 | 主に `frb_coding_constraints_data_v0_3.json`。レビュー候補箱として `frb_constraint_spec_v0_6.json` | 前者には本物のアーキテクチャ制約がある。後者は12グループ・84明細だが、制約だけでなく仕様、現行制限、GAP、将来候補、レビュー方針も混在する | 制約は独立階層ではなく、憲法・Foundation・製品仕様の各レベルに存在する内容種別 |
| ルール | 条件に応じた判断を決める | 文の役割・設計情報の種類 | `frb_viewdef_generation_rules_data_v0_1.json`、`frb_test_evidence_rules_data_v0_1.json`、`studio-overlay-manifest_rules_data_v0_1.json`、`frb_foundation_rules_data_v0_1.json` | ViewDef生成、テスト証跡、Overlay、Foundationなど、ドメインごとに `rules[]` を分けて管理している | 現在のドメイン別分割は妥当。ルールは一つの階層名ではなく、各領域に存在する判断規則 |
| 仕様 | 制約とルールを特定製品の振る舞いへ確定する | 対象固有の契約・振る舞い | `frb_view_def_schema_v0_9.json`、各 `defs/**/*.json`、元仕様文書 `No-Code JSON Studiov0.3-draft.md` | Schemaは許可される構造の機械可読契約。個別ViewDefは具体的な表示・編集・Action体験を宣言する。`frb_constraint_spec_v0_6.json` は元仕様から抽出したレビュー用中間物 | 仕様はSchema、個別ViewDef、製品仕様文書に分散している。制約抽出JSONを仕様正本とは見なさない |

## 2. 二つの軸を分ける

### 適用範囲・権威の軸

```text
憲法
  ↓
Foundation
  ↓
製品
  ↓
機能
```

### 設計情報の種類の軸

```text
思想
判断軸
制約
ルール
責務・契約
仕様
判断ログ
```

この二軸は交差する。

| 適用範囲 | 制約の例 | ルールの例 | 仕様の例 |
|---|---|---|---|
| 憲法 | AIだけで正本を承認済みにしてはならない | 正本変更は人間承認後に確定する | 承認状態と変更履歴を必須項目として持つ |
| Foundation | Data原本へRuntime状態を混入させない | 構造化できるルールはData JSONを原本にする | ルールDataは `rules[]` と共通レビューViewDefを使用する |
| 製品 | 管理対象外ファイルを直接上書きしない | 管理対象外なら別名保存を選択する | 保存操作時にブラウザダウンロードを実行する |
| 機能 | Gridの `dataPath` は配列でなければならない | number検索の既定演算子は `gte` | 検索フォームと一覧結果の具体的なUI挙動 |

## 4. 結論

```text
憲法 / Foundation
= どの高さ・範囲で効くか

制約 / ルール / 仕様
= その設計情報が何を表すか
```

したがって、ファイルを一対一で次のように固定する必要はない。

```text
憲法ファイルには制約とルールが存在する。
Foundationファイルにも制約とルールが存在する。
製品仕様にも製品固有の制約とルールが存在する。
```

現在もっとも紛らわしい点は、`frb_coding_constraints_data_v0_3.json` が
「憲法」と「Foundation級アーキテクチャ制約」の両方を持っていることと、
`frb_constraint_spec_v0_6.json` が制約以外の設計情報まで制約として収容していることである。


憲法は、かなり薄くていい。

誰が正しさを決めるのか
正本をどう扱うのか
変更をどう承認するのか
何を追跡可能にしなければならないか

---

Foundation制約・ルール
        ↓ 関連ID
責務定義.json
  ├─ 責務
  ├─ 仕様的な契約
  ├─ 保証ID
  ├─ Interface参照
  ├─ ViewDef参照
  ├─ Schema参照
  └─ 必要ならサブ設計書参照
        ↓ 保証IDで接続
TestPattern.json
        ↓
Actual.json
        ↓
Diff.json


----

うん、**その整理でいこう。これが一番混乱しない**と思う。

> **制約・判断軸・ルールは、特定の階層専用ではない。**
> **憲法、Foundation、責務定義など、各高さの設計書に存在し得る。**

今まで混乱していたのは、判断軸の「専用ファイル」を探そうとしたからやね。
専用ファイルは不要で、**その判断軸が効く高さの設計書に置く**だけでいい。

## 判断軸を追加した表

| 適用範囲           | 判断軸の例                                 | 制約の例                          | ルールの例                     | 仕様・契約の例                                |
| -------------- | ------------------------------------- | ----------------------------- | ------------------------- | -------------------------------------- |
| **憲法**         | AIの生成速度より、人間が承認できることを優先する             | AIだけで正本を承認済みにしてはならない          | 正本変更は人間承認後に確定する           | 承認状態と変更履歴を必須情報として持つ                    |
| **Foundation** | 局所的な利便性より、Data・View・Runtimeの責務分離を優先する | 原本DataへRuntime状態を混入させない       | 構造化できるルールはData JSONを正本にする | ルールDataは `rules[]` と共通レビューViewDefを使用する |
| **責務・製品**      | 操作回数の少なさより、誤上書き防止を優先する                | 管理対象外ファイルを直接上書きしない            | 管理対象外なら別名保存を選択する          | 保存操作ではブラウザダウンロードとして出力する                |
| **機能**         | 検索対象の多さより、意味のない一致ノイズを減らすことを優先する       | Gridの `dataPath` は配列でなければならない | number検索の既定演算子は `gte` とする | 検索フォームと一覧結果を所定のUIで表示する                 |

この並び、かなり分かりやすい。

```text
判断軸
＝ 複数案があるとき、何を優先するか

制約
＝ どの案を選択肢から除外するか

ルール
＝ 条件に応じて、どの案を選ぶか

仕様
＝ 選ばれた結果が、対象上でどう成立・観測されるか
```

## ファイル実態

| 設計書                   |         判断軸 |             制約 |           ルール |                仕様的なもの |
| --------------------- | ----------: | -------------: | ------------: | --------------------: |
| Studioくん憲法JSON        |          あり |             あり |            あり |         統治上の契約として一部あり |
| Foundation Rules JSON |          あり |             あり |            あり |      共通構造・共通契約として一部あり |
| 責務定義JSON              |          あり |      関連制約IDを参照 |   責務固有ルールを持てる |  入出力・状態・異常時動作・保証として持つ |
| ViewDef / Schema      |   原則として持たない | 構造制約を表現することはある | 表示・入力ルールを表現する |             機械可読な具体仕様 |
| TestPattern JSON      |        持たない |        直接定義しない | 検証条件として具体化される | Input＋Expectedとして検証する |
| Incident JSON         | 適用軸ID・候補を記録 |        昇格候補を記録 |   今回採用した判断を記録 |            作業結果・差分を記録 |

## 各ファイルで同じ構造に揃える必要もない

概念として、

```text
decision_axes
constraints
rules
```

が存在すればいい。

たとえば憲法JSONなら、

```json
{
  "decision_axes": [],
  "constraints": [],
  "rules": []
}
```

Foundationも同様に持てる。

責務定義では、

```json
{
  "decision_axes": [],
  "related_constraint_ids": [],
  "responsibility_rules": [],
  "guarantees": []
}
```

の方が自然かもしれない。

つまり、**概念は共通でも、JSON構造まで無理に完全統一しなくてよい**。

## これで判断ログの昇格先も自然になる

```text
判断ログ
  ↓

この責務だけで使う判断軸
  → 責務定義へ昇格

複数責務・複数製品で使う判断軸
  → Foundationへ昇格

正本・承認・人間とAIの関係を統治する判断軸
  → 憲法へ昇格
```

制約も同じ。

```text
責務固有の境界
  → 責務定義または関連制約

製品群共通の境界
  → Foundation

正本や承認を統治する境界
  → 憲法
```

なので、当面の基本ルールはこれで十分やと思う。

> **制約・判断軸・ルールは各設計書に存在し得る。**
> **どのファイルへ置くかは、情報の種類ではなく、その適用範囲の高さで決める。**

これなら、「判断軸どこ置くねん問題」も「制約は全部Foundationなのか問題」も、一気に消える。ようやく棚が真っすぐ並んできたぞぉ〜笑
