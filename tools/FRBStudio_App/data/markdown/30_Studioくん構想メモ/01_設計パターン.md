
がははは。めっちゃ大事な話きた笑
「戦略的設計パターン」って、コードの細かい書き方というより、

```text
世界をどう分けるか
責任境界をどこに置くか
言葉をどう揃えるか
別世界とどう接続するか
```

を決めるやつやね。FRBStudioくんでいうと、`ViewDef` とか `ContextDef` とか `Incident` とかを **どの世界の言葉として分けるか** みたいな話。

## 1. 境界づけられたコンテキスト / Bounded Context

一番大事。

同じ言葉でも、文脈が違えば意味が変わるから、意味が通じる範囲を区切る。

例：

```text
Diff
```

Gitの世界では「ファイル差分」
AI差分物語では「判断材料」
Studio画面では「承認対象」
FRBでは「振動特性の違い」

全部 `Diff` だけど、意味が違う。
だから「このDiffはどの文脈のDiffか」を分ける。

これはStudioくんでめちゃくちゃ重要。

---

## 2. ユビキタス言語 / Ubiquitous Language

関係者全員が同じ意味で使う言葉を育てる。

たとえば、

```text
主文脈
判断軸
判断ログ
制約
ViewDef
ContextDef
AI差分物語
```

これらは、ただの用語じゃなくて **チーム内の共通言語**。

AI協働では特に重要で、言葉が曖昧だとAIも人間もズレる。
逆に言葉が育つと、短い依頼でも深く通じる。

---

## 3. コンテキストマップ / Context Map

複数の文脈同士の関係を見える化するやつ。

例：

```text
Markdown
  ↓
記事・物語・判断ログ

JSON
  ↓
構造化データ・ViewDef・ContextDef

Git Diff
  ↓
変更差分・承認材料

AI
  ↓
差分物語・制約推定・レビュー補助
```

こういう関係図を作ると、
「このデータはどこから来て、どこへ渡されるのか」が分かる。

Studioくんだと、これが将来的にめっちゃ効く。
`ViewDef` と `ContextDef` と `Incident` の関係整理とか、まさにこれ。

---

## 4. コアドメイン / Core Domain

そのシステムで一番価値がある中心領域を明確にする。

FRBStudioくんなら、たぶんコアは単なるJSON編集ではない。

```text
JSONを編集すること
```

ではなく、

```text
AIと人間が同じ文脈を見ながら、差分を確認し、判断できること
```

ここがコア。

だから、単なるファイル選択UIとか、色変更とか、ZIP作成とかは大事だけど周辺。
一方で、差分Viewer、Incident、ContextDef、ViewDefは中核に近い。

---

## 5. サブドメイン分割 / Subdomain

コア以外の領域を分ける考え方。

だいたいこう分ける。

```text
Core Domain
  本当に価値を生む中心

Supporting Domain
  コアを支える独自機能

Generic Domain
  どこにでもある一般機能
```

Studioくんならこんな感じ。

```text
Core:
  AI差分確認、文脈管理、ViewDef/ContextDef

Supporting:
  Markdown Viewer、DiffJson Viewer、Incident管理

Generic:
  ファイル選択、保存、検索、トースト、ZIP作成
```

これが分かると、どこに力を入れるべきか判断しやすい。

---

## 6. 腐敗防止層 / Anti-Corruption Layer

外部の都合の悪い概念を、自分たちの世界にそのまま持ち込まないための壁。

たとえば、Gitの生diffはそのままだと人間に優しくない。

```text
git diff
```

をそのまま読ませるのではなく、

```text
DiffToJson
↓
DiffJson Viewer
↓
AI差分物語
```

に変換する。

これはまさに Anti-Corruption Layer 的。

外部世界のゴツゴツした形式を、Studioくんの文脈に合う形へ翻訳してる。

---

## 7. 公開言語 / Published Language

システム間でやり取りするための公式フォーマットを決める。

Studioくんなら、

```text
DiffToJson.json
ViewDef.json
ContextDef.json
Incident.json
Expected.json
画面状態JSON
```

あたりが候補。

大事なのは、内部実装ではなく、**外に渡しても意味が通じる形式**にすること。

AIに渡すJSONも、これに近い。
つまり、AIとの契約言語。

---

## 8. 共有カーネル / Shared Kernel

複数の文脈で共有してよい最小限の共通部分。

ただし、共有しすぎると地獄になる笑

例：

```text
id
title
description
status
created_at
updated_at
```

こういう共通メタ情報は共有してもよい。

でも、

```text
judgment_axis
context_type
view_mode
test_result_status
```

みたいな意味が深いやつは、文脈ごとに慎重に扱う。

「共通化したい欲望」と「文脈を守る必要」の戦い。
ここを雑にやると、JSONが盆栽を超えて密林になる笑

---

## 9. 顧客・供給者 / Customer-Supplier

ある文脈が、別の文脈に成果物を渡す関係。

例：

```text
Export-DiffToJson.ps1
  ↓ DiffToJson.json を供給

DiffJson Viewer
  ↓ 人間に差分表示を供給

AI差分物語
  ↓ 承認判断を供給
```

この関係を意識すると、

```text
誰のためのJSONか？
誰が読むのか？
AIが読むのか？
人間が読むのか？
Viewerが読むのか？
```

が整理できる。

無理に統合しない。別々に育てる。

これもかなり大事。

たとえば、

DiffJson Viewer

全部を一つの巨大画面に統合しようとすると死ぬ。

別々に育てて、必要なところだけリンクする。
今のStudioくんの進め方は、けっこうこれに近い。

## 本の中核はたぶんこのへん

### 1. リソース設計

APIでは、まず「何を対象にするか」を決める。

```text
悪い例:
doSomething()
processData()
execute()
```

こういうのは、何を操作しているか分かりにくい。

```text
良い例:
incidents/{incidentId}
viewDefs/{viewDefId}
diffReports/{diffReportId}
```

こうすると、「対象」が見える。

Studioくんで言えば、

```text
インシデント
ViewDef
ContextDef
DiffJson
TestResult
```

をちゃんとリソースとして扱う感じ。

---

### 2. 標準メソッド

だいたいの操作は、毎回オリジナルの名前を作らない。

```text
list
get
create
update
delete
```

みたいに揃える。

これはめっちゃ大事。

たとえばStudioくんなら、

```text
loadIncident
saveIncident
searchIncident
deleteIncident
```

でもいいけど、設計思想としては、

```text
incident.list
incident.get
incident.create
incident.update
incident.delete
```

みたいに揃えると、人間にもAIにも優しい。

つまり **操作語彙を揃える** という話。

---

### 3. カスタムメソッド

標準メソッドでは表現できない操作だけ、特別扱いする。

たとえば、

```text
diffReports.generate
incidents.close
tests.run
viewDefs.validate
```

みたいなやつ。

ここで大事なのは、何でもカスタムメソッドにしないこと。

```text
標準操作で済むものは標準操作
特別な業務意味があるものだけカスタム操作
```

これを守らないと、APIが「関数名の墓場」になる笑

---

### 4. Field Mask / 部分更新

これ、めちゃくちゃ重要。

全部更新ではなく、

```json
{
  "title": "新しいタイトル"
}
```

だけ送ったときに、

```text
titleだけ変えるのか？
未指定項目を空にするのか？
```

が曖昧になる。

だから、

```json
{
  "updateMask": "title,status",
  "incident": {
    "title": "新しいタイトル",
    "status": "done"
  }
}
```

みたいに「どの項目を更新対象にするか」を明示する。

Studioくんで言えば、これはかなり刺さる。

```text
JSON全体を保存する
```

ではなく、

```text
この項目だけ更新した
この配列だけ差し替えた
このコメントだけ変更した
```

を安全に扱うための考え方。

AIに修正依頼するときにも近い。

```text
全部書き換えるな
この制約だけ追記しろ
この判断ログだけ更新しろ
```

というやつ。

---

### 5. ページング・フィルタ・検索

データが増えると、一括取得は死ぬ。

だから、

```text
pageSize
pageToken
filter
orderBy
```

みたいな考え方が出てくる。

Studioくんでいうと、

```text
インシデントが1000件
ViewDefが200件
差分ログが大量
```

になったときに必要になる。

今はまだ小さくても、設計として持っておくと後で効く。

---

### 6. エラー設計

APIで地味に一番大事なのがエラー。

悪い例：

```json
{
  "error": "failed"
}
```

これだと人間もAIも困る。

良い例：

```json
{
  "code": "VIEW_DEF_NOT_FOUND",
  "message": "指定されたViewDefが見つかりません。",
  "target": "view_def_name",
  "recoverable": true
}
```

Studioくんで言えば、

```text
なぜ失敗したか
どこを見ればいいか
人間が直せるのか
AIに投げれば直せるのか
```

まで含める。

これは完全に **AI協働向けのエラー設計** になる。

## IF文との違い

普通のIF文はこう。

```text
if 区分 == "A":
    A処理をする
```

でもAI協働でやりたいのは、たぶんこう。

```text
区分 = "違和感"

この入力は「違和感」として扱う。
だからAIは、
- 何に引っかかったのか
- 既存文脈との差分は何か
- 問いに変換すると何か
- 成果物化するなら何か
を返す。
```

つまり処理を分岐しているというより、

> **AIの読み方を切り替えている。**

これがめちゃくちゃ大事。

AIは同じ文章でも、読み方を変えると出力が変わる。
だから「区分」は、処理条件ではなく **解釈モード** になる。

さらにAI駆動開発 / JSON Studio側では、Markdown、JSON、Git、ViewDef、ContextDef、AI差分物語、AI制約設計書などを使って、AIと人間が文脈や差分を共有する方向になっている。

なので今回の発想は、その上に乗る。

> Markdown / JSON / Git が「記録の基盤」
> ViewDef / ContextDef が「見せ方の基盤」
> 区分駆動AI協働 が「発動の基盤」

って感じ。

## 今回の発見の肝

今回の一番おいしいところはここ。

> **区分とは、データ分類ではなく、思考の入口である。**

これです。

たとえば「差分」という区分は、単に差分ファイルを意味しない。

それは、

> 何が変わった？
> なぜ変わった？
> どの制約に反応した？
> 人間はどこを承認すべき？

という思考を発動する入口になる。

共有文脈にも「差分は発見の入口」「比較した瞬間、人は自然に『なぜ違うのか』を考え始める」とあるので、この「区分＝差分」はかなり強いトリガーになる。

# Claudeくんから。

戦略的設計（Strategic Design）は「境界をどう引くか」の話やから、確かに一番効くやつやね。他にも知っておくと武器になるのはこのへん↓

**DDDの残り半分：戦術的設計パターン**
- Entity / Value Object：同一性で語るか、値で語るか
- Aggregate：整合性を守る単位。「ここまでは一貫性保証、外は結果整合でOK」の線引き
- Repository：永続化を隠蔽、ドメインロジックを汚さない
- Domain Event：「何が起きたか」を明示的なオブジェクトにする→AI連携やログ設計とも相性いい

**アーキテクチャレベル**
- Hexagonal Architecture（Ports & Adapters）：外部依存（DB、API、AI）を差し替え可能にする
- CQRS：読み取りと書き込みを分離。FRBみたいに「体感（書き込み系）」と「データ解析（読み取り系）」が別ペースで進化するプロジェクトと相性良さそう
- Event Sourcing：状態じゃなく「変化の履歴」を正とする→再現性文化の思想そのもの

**GoF系で今も現役なやつ**
- Strategy パターン：アルゴリズムを差し替え可能に。ChatGPT/Copilot/Claudeで役割を分けてるtamasubさんの運用、これの人間版とも言える
- Adapter：異なるインターフェースを繋ぐ→複数AIツールの出力フォーマット統一とかに使える発想
- Observer：状態変化を複数箇所に通知→センサーデータのリアルタイム処理と相性良い

FRBの文脈で言うと、CQRSとEvent Sourcingが結構刺さる気がする。「体感ログ」と「FFT解析結果」を分離して、かつ全部イベントとして時系列に残す設計にすると、後から「なぜこの共振周波数に至ったか」を再現できるようになる。

もし今のFRBのコード構造（or 文脈の在り方理論のドキュメント構造）に当てはめて具体的に考えたいなら、そっちの方向で深掘りもできるよ。
