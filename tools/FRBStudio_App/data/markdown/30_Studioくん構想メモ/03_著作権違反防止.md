
> ソースにおける著作権違反の代表的な凡例とかある？？一般論がまずしりたい
>

----

あるある。まず大前提として、**ソースコードは著作権の対象になり得る**です。日本でもソフトウェアは「プログラムの著作物」として保護され、コピーは複製権、改変利用は翻案権の話になります。CRICも、ソフトウェアをコピーすることは複製であり、原則として権利者の許諾が必要と説明しています。([CRIC][1])

ただし、守られるのは基本的に**具体的なコード表現**です。機能・アイデア・アルゴリズム・プログラミング言語・規約そのものは、通常は著作権の保護対象ではありません。つまり「JSONを読み込んで一覧表示する」という発想は守られにくいけど、その具体的な実装コードを丸ごと持ってくると危ない、という整理です。([レバテック][2])

## 著作権違反になりやすい代表例

### 1. 既存コードのコピペ

一番分かりやすいやつです。

```text
OSSやブログ記事の関数を、そのまま自分のソースに貼る。
ライセンス表記も出典も残さない。
```

これは危険度高いです。
短い定型処理なら問題になりにくいこともありますが、長めの関数、独特な変数名、コメント、例外処理、処理順序まで一致しているとかなり怪しくなります。

### 2. 変数名だけ変えたコピー

```text
元コード:
function calculateScore(input) { ... }

コピー後:
function calcValue(x) { ... }
```

変数名や関数名だけ変えても、処理構造・分岐・順序・コメント・エラー処理がほぼ同じなら「実質コピー」と見られる可能性があります。

これはAIコードでもあり得ます。
AIがどこかのコードっぽいものを出して、それを人間が少し名前だけ変えて採用するパターン。地雷臭がなかなか強い。

### 3. 他言語への移植コピー

```text
JavaScriptの既存実装を見ながら、C#にほぼ同じ構造で移植する。
```

言語が違っても、元コードの創作的な表現・構造・処理順が強く残るなら危ないことがあります。

「JSをC#にしたからセーフ」ではないです。
これは翻案、つまり改変利用の問題になり得ます。

### 4. OSSライセンス違反

著作権侵害の実務でめちゃくちゃ多いのは、むしろこれです。

```text
MITライセンスのコードを使ったのに著作権表示・ライセンス文を消した
Apache-2.0のNOTICEを無視した
GPLコードを混ぜたのにソース公開条件を満たしていない
商用不可・改変不可のコードを組み込んだ
```

OSSは「無料」ではなく「条件付きで使っていい」です。
条件を守らないと、著作権の許諾条件を外れるので危ないです。

### 5. Stack Overflow / 個人ブログのコードを雑に貼る

```text
検索して出てきたブログのコードをそのまま貼る
Stack Overflowの回答コードを長めにコピーして使う
```

短い定型スニペットなら大きな問題になりにくいこともありますが、長いコードや独自実装は注意です。

特に「この人が苦労して作ったっぽい関数」は、そのまま持ってくると危ない。
AIに「このブログのコードをいい感じに改造して」と頼むのも、同じ方向で危険。

### 6. 前職・他社・顧客コードの持ち込み

```text
前の会社で書いた便利クラスを、今の個人プロジェクトにコピーする
受託案件で作ったコードを、自分のOSSに流用する
会社の社内コードを、個人GitHubに混ぜる
```

これはかなり危険です。著作権だけでなく、契約違反、秘密保持義務、営業秘密の問題も混ざります。

「自分が書いたコードだからOK」とは限らないです。
業務で書いたコードは会社に権利が帰属することがあります。([レバテック][2])

### 7. 有料製品・非公開コードの模倣

```text
有料ライブラリの中身を解析して同じ実装を作る
難読化JSを読んでロジックを再現する
競合製品の内部処理を真似る
```

これは著作権だけでなく、不正競争防止法、契約違反、リバースエンジニアリング禁止条項なども絡みやすいです。

仕様として互換実装を作るのと、内部コード表現をコピーするのは別物です。

### 8. AI生成コードが既存コードと長く一致する

```text
AIが出したコードに、既存OSSと同じコメント・同じ関数名・同じ処理順が出てくる
```

これがAI時代の新しい怖さです。
文化庁のAIと著作権に関する資料でも、AI生成物に既存著作物との「類似性」と「依拠性」が認められる場合、許諾や権利制限規定がなければ利用行為が著作権侵害となる可能性がある、という整理が示されています。([文化庁][3])

つまり、AIが出したからノーカン、ではないです。

## 逆に、著作権違反になりにくいもの

このへんは必要以上に怖がらなくてOKです。

```text
よくあるfor文
単純なCRUD
標準APIの呼び出し
一般的なバリデーション
短い定型スニペット
フレームワーク公式ドキュメントの基本例
アルゴリズムの考え方だけを参考にして、自分で実装したもの
```

著作権で守られるのは「アイデア」ではなく「表現」なので、機能が似ているだけでは直ちにアウトではありません。ソースコードの著作権侵害を判断するには、一般に実際のソースコードの表現を比較する必要があります。([コーポレート][4])

## 判断の芯

実務的には、この2つを見る感じです。

```text
1. 依拠性
   既存コードを見た、使った、参考にした、AIが再現した可能性があるか

2. 類似性
   具体的なコード表現がどれくらい似ているか
```

生成AIコードでも同じで、既存著作物との類似性・依拠性がないなら基本的には著作権侵害にはなりにくい。一方、似ていて、かつ依拠したと見られるなら危ない、という整理です。([レバテック][5])

次の一手は、**「公開候補コード台帳」を作ること**やね。
いきなりコードを戻すんじゃなくて、まず **棚卸し → 出所分類 → ライセンス確認 → 公開用に書き直し** の順が安全。

GitHub公式も、ライセンスを付けない場合はデフォルトの著作権法が適用され、作者が権利を保持する状態になると説明しています。つまり「GitHubにある＝自由に使っていい」ではないです。([GitHub Docs][1])

## まずやること：公開候補コード台帳を作る

リポジトリのルートでこれ。

```powershell
git ls-files "*.js" "*.cs" | Sort-Object > source_public_candidate_inventory.txt
```

今は `.gitignore` で外してるから、Git管理から外れた後なら出ないかもしれません。
その場合はローカルファイルから拾う。

```powershell
Get-ChildItem -Recurse -Include *.js,*.cs |
  Where-Object { $_.FullName -notmatch "\\(bin|obj|publish|dist|node_modules)\\?" } |
  Select-Object -ExpandProperty FullName |
  Sort-Object |
  Out-File source_public_candidate_inventory.txt -Encoding utf8
```

そして、この台帳に列を足す。ExcelでもMarkdownでもJSONでもOK。

```text
file_path
public_decision
origin_type
dependency_or_reference
license
risk_level
action
review_note
```

例：

```text
wwwroot/index.html内JS相当
public_decision: 公開候補
origin_type: 自作＋AI生成
dependency_or_reference: なし
license: 自分でMIT予定
risk_level: 中
action: 公開用に分離・短縮・再実装
review_note: 独自UIロジック。既存OSS酷似なしを確認する
```

## origin_type はこの5分類で十分

ここを曖昧にしないのが大事。

```text
A. 自分が一から書いた
B. AI生成だが、自分の仕様から生成した
C. 公式ドキュメントを参考にした
D. OSS・ブログ・Stack Overflow等を参考にした
E. 出所不明・昔のコード・覚えてない
```

公開していい順は、基本こう。

```text
A → B → C → D → E
```

**Eは一旦公開禁止**でいいです。
「昔の俺が書いた気がするけど、どこから来たか覚えてない」は危険枠。ここは情け容赦なく隔離でOK笑

## 次に依存ライブラリを洗う

`.cs` 側なら：

```powershell
dotnet list package --include-transitive
```

`.js` 側で `package.json` があるなら：

```powershell
npm ls --all
```

依存関係については、GitHubの Dependency Review Action が、PR内の依存関係変更をスキャンし、脆弱性や無効なライセンスが混ざる場合にエラーにできる仕組みを提供しています。([GitHub][2])

ただし、自動スキャンだけで完全に安心ではないです。ライセンス義務は「どう使うか」「配布するか」「改変したか」で変わるので、ツール＋人間レビューが必要です。これは実務でもかなり大事な観点です。([Reuters][3])

## SPDX表記を入れる

公開するファイルには、先頭にこれを入れるのがよいです。

C#：

```csharp
// SPDX-License-Identifier: MIT
// Copyright (c) 2026 tamasub
```

JavaScript：

```javascript
// SPDX-License-Identifier: MIT
// Copyright (c) 2026 tamasub
```

SPDXは、ライセンス識別子・正式名称・ライセンス本文への標準化された参照を提供しているので、ライセンス表記のブレを減らせます。([SPDX][4])

## 公開用コードに落とし込む手順

怪しいコードをそのまま戻すのではなく、こうする。

```text
1. 元コードを見る
2. 「何をしたいコードか」を日本語仕様にする
3. その仕様だけを見て、公開用コードを新規に書く
4. 変数名・構造・コメントを自分の設計語彙に寄せる
5. 既存コードとの長い一致がないか確認する
6. LICENSE / NOTICE / THIRD_PARTY_NOTICES を整える
7. 公開専用フォルダへ置く
```

これが「自分の設計に落とし込む」の実務版。

たとえば Studioくんなら、公開用の考え方はこれ。

```text
private:
  FRBStudio本体
  開発中の .cs
  開発中の .js
  バッチ
  インシデント処理ロジック

public:
  README
  仕様
  サンプルJSON
  ViewDefサンプル
  ContextDefサンプル
  公開用に整理したViewer
```

## LICENSE を決める

公開するなら、リポジトリに `LICENSE` を置く。
オープンソースライセンスは、利用・改変・共有を許可する代わりに条件を付けるものです。([Choose a License][5])

迷ったら最初はこのどちらか。

```text
MIT:
  軽い。使いやすい。表示義務中心。

Apache-2.0:
  少し堅い。特許まわりも明示される。
```

FRB / Studioくんの思想公開なら、**コードはMIT、文章はCC BY 4.0系**みたいに分ける案もあり。
ただし、会社や将来展開を考えるなら、先に「何を自由に使ってほしいか」を決めた方がいいです。

まずこれだけでOK。

```powershell
# 1. 公開候補ソース一覧を作る

  Where-Object { $_.FullName -notmatch "\\(bin|obj|publish|dist|node_modules)\\?" } |
  Select-Object -ExpandProperty FullName |
  Sort-Object |
  Out-File source_public_candidate_inventory.txt -Encoding utf8

# 2. .NET依存関係を見る
dotnet list package --include-transitive

# 3. npmがある場合だけ
npm ls --all
```

そのあと、`source_public_candidate_inventory.txt` を見ながら、まずは3分類。

```text
公開する
公開しない
公開用に書き直す
```

## 判断基準

```text
公開する:
  自作・短い・出所明確・依存明確・ライセンス付与可能

公開しない:
  業務転用色が強い・昔のコード・出所不明・独自ノウハウが濃い

公開用に書き直す:
  便利だがAI生成比率が高い・既存実装に似てそう・構造がまだ汚い
```

## 最初にやるべき「一手」はこれ

**Studioくん本体を公開するかどうかではなく、まず `public/` か `docs/` に置く “公開用ミニ版” を作る。**

```text
docs/
  README.md
  samples/
    sample_data.json
    sample_view_def.json
  public-viewer/
    viewer.html
    viewer.public.js
    LICENSE
    THIRD_PARTY_NOTICES.md
```

これなら、武器庫本体は守りつつ、外に見せたい思想・仕様・サンプルだけ出せる。

今のフェーズなら、これが一番いいと思う。

**次の一手は「全ソース公開」ではなく、公開候補コード台帳を作って、公開用ミニ版を切り出すこと。**
これでいこう。
